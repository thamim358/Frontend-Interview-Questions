CSS Box Model — content-box vs border-box, margin collapsing, React component dimensions
Beginner P1 — Critical
Short Interview Answer

The CSS box model defines how every HTML element is rendered as a rectangular box. It has four layers from inside out: content → padding → border → margin. With box-sizing: content-box (default), width only applies to the content area — padding and border are added on top, causing unexpected overflow. With box-sizing: border-box, width includes content, padding, and border — this is the universal reset every project should use. Margin collapsing occurs when vertical margins of adjacent block elements overlap: the larger margin wins instead of adding together. This only happens with block elements in normal flow, and only vertically — never horizontally, and never inside flex/grid containers.

Easy Explanation

Think of an Amazon package. The content is the item you bought. The padding is the bubble wrap inside the box. The border is the cardboard box itself. The margin is the space between your box and your neighbor's boxes on the delivery truck. With content-box, saying "I want a 200px box" means the item is 200px — the bubble wrap adds more size. With border-box, the whole package (item + bubble wrap + cardboard) is 200px. Margin collapsing is like two people in a hallway — they don't need double the space between them; they just stand at arm's length.

Real-World Example

Amazon's product grid needs cards to fit exactly 4 per row at 25% width. With content-box, adding 12px padding to each card pushes the 4th card to the next row because 25% + padding exceeds 100%. With border-box, the padding is absorbed into the 25% width, and the cards stay perfectly aligned. This is why every CSS reset (including Tailwind's Preflight) sets *, *::before, *::after { box-sizing: border-box; }.

Common Mistake

Forgetting that margin collapsing only applies to block elements in normal flow. Flexbox children, grid children, absolutely positioned elements, and inline-block elements never collapse margins. Also, it's vertical only — horizontal margins always add together.

Code Example
Universal border-box reset
/* Should be at the top of every stylesheet */
*,
*::before,
*::after {
  box-sizing: border-box;
}

/* Margin collapsing example */
.block1 { margin-bottom: 30px; }
.block2 { margin-top: 20px; }
/* Gap between block1 and block2 is 30px, NOT 50px */
/* The larger margin (30px) wins — they collapse */

/* No collapse in flex container */
.flex-container {
  display: flex;
  flex-direction: column;
  gap: 20px; /* Use gap instead — predictable! */
}
Senior Developer Insight

In React, the box model interacts with the component model. A common trap: setting width: 100% on a child component's root element while passing padding as a prop. If the grandchild also uses width: 100%, you get a cascade of unintended overflows. The fix: either use border-box (always) or avoid percentage widths on deeply nested elements — prefer flex: 1 or auto in flex/grid layouts.

Memory Trick: "content-box = width measures the baby. border-box = width measures baby + clothes + stroller. Always use border-box."
  • Box model layers: content → padding → border → margin
  • border-box: width includes content + padding + border (use this)
  • content-box: width applies to content only (legacy default)
  • Margin collapsing: vertical only, block only, larger margin wins
  • Flex/Grid children never collapse margins — use gap instead

Flexbox Complete Guide — justify-content, align-items, common patterns
Beginner P1 — Critical
Short Interview Answer

Flexbox is a one-dimensional layout system that distributes space along either a row (horizontal) or column (vertical). The container controls children with: justify-content (main axis alignment), align-items (cross-axis alignment for all children), align-self (cross-axis for individual child), flex-wrap (whether items wrap to new lines), gap (spacing between items), and flex-direction (row/column, normal/reverse). Children control their own sizing with: flex-grow (expand to fill space), flex-shrink (shrink when needed), flex-basis (initial size before grow/shrink), and the shorthand flex: grow shrink basis. The most common shorthand: flex: 1 = flex: 1 1 0% (grow, shrink, start from zero).

Easy Explanation

Imagine a row of people sitting on a bench. justify-content decides how they spread across the bench (packed left, centered, spaced out evenly). align-items decides if they sit at the front edge, back edge, or center of the bench. flex-grow is like giving some people permission to take up more room if the bench is wider. gap is the minimum personal space between people. If the bench is a column instead of a row (flex-direction: column), just rotate everything 90 degrees in your head.

Real-World Example — Three Classic Patterns

Netflix's navbar: display: flex; justify-content: space-between; align-items: center; pushes the logo to the left, nav links to the right, and vertically centers everything. Pinterest's masonry-adjacent grid: display: flex; flex-wrap: wrap; gap: 16px; with each card having flex: 0 0 calc(25% - 12px) for a responsive 4-column layout. Instagram's post footer: display: flex; align-items: center; gap: 12px; for the like/comment/share/ save icon row with the bookmark icon pushed right via margin-left: auto.

Common Mistake

Using justify-content: center on a flex container with wrapping children and more items than fit on one row. The last partial row gets centered, creating a jagged, orphaned-look layout. Use CSS Grid with auto-fill for wrapping grids instead — it handles partial rows properly.

}

}

}

}

}

}
Pro Tip

The margin-left: auto trick: When you have a flex container and want to push one item to the far end, give it margin-left: auto (for row) or margin-top: auto (for column). Flexbox treats auto margins as "absorb all remaining space." This is cleaner than using spacer divs or complex justify-content calculations.

Memory Trick: "justify = main axis (think 'justify text' is horizontal). align = cross axis. flex: 1 = 'take all available space'. gap = 'personal space'."
  • Flexbox = one-dimensional layout (row or column)
  • justify-content: main axis; align-items: cross axis
  • flex: 1 = flex-grow: 1; flex-shrink: 1; flex-basis: 0%
  • margin-left: auto = push item to right; margin-top: auto = push down
  • Use gap instead of margin for spacing between flex children

CSS Grid Complete Guide — grid-template, auto-fill vs auto-fit, minmax, dashboard layout
Intermediate P1 — Critical
Short Interview Answer

CSS Grid is a two-dimensional layout system that works in both rows and columns simultaneously. Define grid tracks with grid-template-columns and grid-template-rows, place items with grid-column/grid-row or named grid-area. The real power comes from responsiveness without media queries: auto-fill creates as many tracks as fit (leaving empty tracks), while auto-fit collapses empty tracks to zero. minmax(min, max) gives each track a dynamic size range. Together: grid-template-columns: repeat(auto-fit, minmax(250px, 1fr)) creates a responsive card grid that flows from 4 columns to 3 to 2 to 1 as the viewport shrinks — no media queries needed.

Easy Explanation

Flexbox is like arranging books on a single shelf — you control how they spread out along one dimension. CSS Grid is like arranging furniture in a room — you define rows AND columns, and place items wherever you want on that 2D grid. auto-fit is like having smart shelves that disappear when empty. Flexbox dominates for UI components (navbars, button groups); Grid dominates for page layouts (dashboards, card grids, magazine-style designs).

Flexbox vs Grid — When to Use Which
ScenarioFlexboxCSS Grid
Navbar (logo left, links right)Perfect — one row, two groupsOverkill — grid for 1 row?
Card grid (4 per row responsive)Works, but partial row centering issuesPerfect — auto-fill/minmax
Dashboard layout (sidebar + header + content)Awkward — nested flexboxesPerfect — named grid areas
Centering a single elementPerfect — 2 lines of codeAlso works — equally simple
Magazine layout (overlapping items)Not possiblePerfect — grid-row/column
Variable item height rowsRequires JS or fixed heightPerfect — align to row tracks
Real-World Example

Stripe's dashboard uses CSS Grid for its analytics layout. The page is a 4x3 grid with named areas: "revenue-chart" spans 2 columns, "recent-transactions" spans 1 column and 2 rows, and the remaining cells hold smaller metric cards. When the viewport shrinks, the grid-template-areas change to stack everything vertically. GitHub's explore page uses repeat(auto-fill, minmax(300px, 1fr)) for its repository card grid — the cards resize smoothly from 3 columns to 2 to 1 without any breakpoints.

Common Mistake

Confusing auto-fill and auto-fit. auto-fill creates empty tracks when items don't fill the row (visual gaps). auto-fit collapses empty tracks and stretches existing items to fill the row. Use auto-fit 90% of the time — it gives you the responsive behavior you actually want.

Code Example — Dashboard Layout with Grid Areas
Dashboard Grid with Named Areas
.dashboard {
  display: grid;
  grid-template-columns: 250px 1fr 1fr;
  grid-template-rows: auto 1fr 1fr;
  grid-template-areas:
    "sidebar header  header"
    "sidebar chart1  chart2"
    "sidebar stats   activity";
  gap: 1rem;
  min-height: 100vh;
}
.sidebar  { grid-area: sidebar; }
.header   { grid-area: header; }
.chart1   { grid-area: chart1; }
.chart2   { grid-area: chart2; }
.stats    { grid-area: stats; }
.activity { grid-area: activity; }

/* Responsive card grid — no media queries! */
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 1.5rem;
}
Senior Developer Insight

The true power of Grid isn't just layout — it's the separation of visual order from DOM order. You can place your main content first in the HTML (for SEO and accessibility) but display it in the center column visually. Screen readers follow DOM order, while sighted users see the visual Grid order. This is impossible with Flexbox alone.

Memory Trick: "Flexbox = one-dimensional (row OR column). Grid = two-dimensional (rows AND columns). auto-fill leaves gaps, auto-fit fills them. minmax = 'at least X, at most Y'."
  • CSS Grid: two-dimensional layout, rows + columns simultaneously
  • grid-template-areas: visual layout with named zones
  • auto-fit vs auto-fill: collapse vs keep empty tracks
  • minmax(): responsive tracks without media queries
  • Grid for page layouts; Flexbox for UI components

CSS Position — static, relative, absolute, fixed, sticky, stacking context (z-index)
Intermediate P1 — Critical
Short Interview Answer

CSS position controls how an element is placed in the document flow. static (default) follows normal flow — top/left/z-index have no effect. relative stays in flow but can be offset from its original position with top/left/right/bottom — the original space is preserved. absolute removes the element from flow and positions it relative to the nearest positioned ancestor (or the initial containing block if none). fixed removes from flow and positions relative to the viewport — stays put during scrolling. sticky is a hybrid: it behaves as relative until it reaches a scroll threshold, then "sticks" like fixed. Z-index only works on positioned elements (not static), and it creates a stacking context — children within that context are isolated from elements outside it.

Easy Explanation

Think of a classroom seating chart. static students sit in their assigned seats (normal flow). relative students are in their seat but leaning to one side — their desk (space) is still there. absolute students are out of their seat, standing relative to the teacher's desk (nearest positioned ancestor) or the classroom wall (viewport). fixed students are stuck to the classroom window — they don't move when the teacher rearranges seats. sticky students stay in their seat until the teacher walks past, then they follow the teacher — once the teacher's zone passes, they return to their seat.

Position Values Reference
ValueIn Flow?Positioned Relative ToSpace Preserved?Common Use
staticYesN/AN/ADefault — no special positioning
relativeYesIts own normal positionYesOffset tweaks, z-index stacking
absoluteNoNearest positioned ancestorNoDropdowns, modals, tooltips
fixedNoViewportNoSticky headers, cookie banners, chatbots
stickyYes (until threshold)Nearest scrolling ancestorYesTable headers, section titles
Real-World Example

Twitter's compose button uses position: fixed; bottom: 24px; right: 24px; so it's always accessible regardless of scroll position. Airbnb's search bar uses position: sticky; top: 0; — it scrolls with the page but locks to the top when you scroll past it, keeping search always available. Notion's dropdown menus use position: absolute relative to their trigger button (which has position: relative) — the dropdown appears exactly below the button regardless of where it is on the page.

Common Mistake

Assuming z-index: 9999 will always work. Z-index only operates within a stacking context, and a new stacking context is created by any element with position + z-index (not auto), opacity < 1, transform, filter, isolation: isolate, or will-change. A child with z-index: 9999 inside a stacking context with z-index: 1 can never appear above a sibling with z-index: 2. The numbers are relative to the stacking context, not global.

Code Example
Stacking Context Trap and Fix
/* TRAP: z-index: 9999 won't beat this */
.parent {
  position: relative;
  z-index: 1; /* Creates stacking context */
  opacity: 0.99; /* Also creates stacking context! */
}
.child {
  position: absolute;
  z-index: 9999; /* Trapped inside parent's context */
}

/* Sticky header that works */
.sticky-header {
  position: sticky;
  top: 0;
  z-index: 100; /* Stays above scrolling content */
  background: white; /* Required! Transparent sticky = visible overlap */
}

/* Dropdown relative to button */
.dropdown-wrapper {
  position: relative; /* Positioning anchor */
}
.dropdown-menu {
  position: absolute;
  top: 100%;
  left: 0;
}
Senior Developer Insight

The most common z-index battle is modals vs. sticky headers vs. dropdowns. Establish a z-index scale as CSS custom properties: --z-dropdown: 100; --z-sticky: 200; --z-modal-backdrop: 300; --z-modal: 400; --z-toast: 500;. This prevents the arms race of z-index: 1, 10, 100, 1000, 10000. Everyone on the team uses the same scale, and debugging stacking issues becomes trivial.

Memory Trick: "static = in seat. relative = in seat leaning. absolute = out of seat, relative to parent. fixed = stuck to wall. sticky = stays until pushed, then follows. z-index only works on non-static, and creates isolation chambers (stacking contexts)."
  • static: default, normal flow, z-index ignored
  • relative: stays in flow, offset from self, creates positioning anchor
  • absolute: removed from flow, relative to nearest positioned ancestor
  • fixed: removed from flow, relative to viewport, survives scroll
  • sticky: hybrid — relative until scroll threshold, then sticks
  • Stacking context: z-index is local, not global — watch for opacity/transform traps

CSS Specificity — How calculated, !important dangers, cascade order
Intermediate P1 — Critical
Short Interview Answer

Specificity is calculated as a four-part value (a, b, c, d): a = inline styles (style attribute), b = ID selectors, c = class/attribute/pseudo-class selectors, d = element/pseudo-element selectors. Higher specificity wins; if equal, the later rule wins (cascade order). !important overrides everything except another !important with higher specificity. The universal selector (*) and combinators (>, +, ~) contribute zero specificity. :is() and :not() use the specificity of their most specific argument. :where() always has zero specificity — it's the "specificity eraser."

Easy Explanation

Think of specificity as a scoring system. Inline styles are a 1000-point bonus. Each ID is 100 points. Each class is 10 points. Each element tag is 1 point. When two rules conflict, the one with more points wins. If it's a tie, the one that appears later in the stylesheet wins. !important is like bribing the referee — it always wins, but overusing it makes everyone hate you and debugging impossible.

Specificity Examples
SelectorSpecificity (a,b,c,d)Score
* (universal)(0,0,0,0)0
div(0,0,0,1)1
.card(0,0,1,0)10
div.card.active(0,0,2,1)21
#header(0,1,0,0)100
style="color: red"(1,0,0,0)1000
:where(.card)(0,0,0,0)0
:is(#id, .class)(0,1,0,0)100 (takes highest)
Real-World Example

GitHub's code editor uses CSS specificity intentionally: base syntax highlighting uses element selectors (low specificity), language-specific themes use class selectors (medium), and user customizations use a wrapper with higher specificity to override. Tailwind CSS intentionally keeps all utility classes at the same specificity level ((0,0,1,0)), so the cascade order (last one wins) is predictable — unlike traditional CSS where deeply nested selectors accidentally override utilities.

Common Mistake

The !important cascade of doom: dev A can't override a style, adds !important. Dev B can't override dev A's !important, adds their own. Dev C uses an ID + !important. Now the stylesheet is unmaintainable. The fix: use BEM naming or CSS Modules to keep specificity flat, and use :where() for reset/default styles that should always be overridable.

Code Example
Specificity Battle and :where() Fix
/* High specificity — hard to override */
#sidebar .nav .link.active {  /* (0,1,2,0) = 120 */
  color: blue;
}

/* Trying to override — needs even higher specificity */
#sidebar .nav .link.active.highlighted {  /* (0,1,3,0) = 130 — messy! */
  color: red;
}

/* Better: flat BEM-style selectors */
.nav__link--active { color: blue; }       /* (0,0,1,0) = 10 */
.nav__link--highlighted { color: red; }  /* (0,0,1,0) = 10 — cascade wins */

/* Tailwind default reset using :where() — zero specificity */
:where(h1, h2, h3) {
  font-weight: normal; /* Always overridable by any class */
}
Memory Trick: "Inline (1000) > ID (100) > Class (10) > Element (1). :where() = 0. !important = cheat code (don't use). Cascade = tiebreaker (last rule wins)."
  • Specificity: (inline, ID, class, element) = (a,b,c,d)
  • :where() always has zero specificity — use for resets
  • :is()/:not() take the highest specificity of their arguments
  • !important creates unmaintainable code — avoid it
  • Keep specificity flat: use BEM, CSS Modules, or Tailwind

Responsive Design — Mobile-first, media queries, clamp(), container queries (@container)
Intermediate P1 — Critical
Short Interview Answer

Responsive design ensures web applications look and function well on any screen size. Mobile-first means you write base styles for mobile and use min-width media queries to add complexity for larger screens — the opposite of the old desktop-first approach. Media queries (@media (min-width: 768px)) apply styles conditionally based on viewport dimensions. clamp() enables fluid typography and spacing without media queries: clamp(min, preferred, max) — e.g., font-size: clamp(1rem, 2.5vw, 2rem) scales smoothly between 1rem and 2rem. Container queries (@container) are the next evolution: they style elements based on their parent container's size, not the viewport — enabling truly reusable, context-independent components.

Easy Explanation

Mobile-first is like designing a shirt that fits a small person first, then adding extra fabric for larger sizes. Media queries are like tailoring instructions: "If the person is wider than 768px, use this seam." clamp() is like elastic fabric that stretches between a minimum and maximum size. Container queries are revolutionary: instead of asking "how big is the window?" you ask "how big is MY parent?" — which is what components actually care about. A card component doesn't know if it's in a sidebar or full page; with container queries, it adapts automatically.

Real-World Example

Spotify's web player uses container queries for its playlist grid. When the sidebar is collapsed, the main content area grows, and individual playlist cards expand from 3 columns to 5 columns — all based on the parent container's width, not the viewport. Without container queries, you'd need JavaScript to detect the sidebar's state and toggle classes. Notion uses clamp() for its heading sizes: h1 { font-size: clamp(1.5rem, 4vw, 2.5rem); } — the headings grow smoothly as the window widens, with no jump between breakpoints.

Common Mistake

Using max-width media queries (desktop-first) in new projects. This means you're writing all the complex desktop styles as defaults, then overriding them for mobile — more code, harder maintenance. Mobile-first (min-width) means your default styles are the simplest mobile layout, and you progressively enhance — less code, better performance on mobile, and a more natural thinking flow.

Code Example
Mobile-First with clamp() — No Media Queries
/* Mobile-first base styles */
.card {
  padding: clamp(0.75rem, 2vw, 1.5rem);
  font-size: clamp(0.875rem, 1.5vw, 1.125rem);
  display: grid;
  gap: 1rem;
}

/* Enhance for tablets */
@media (min-width: 768px) {
  .card {
    grid-template-columns: repeat(2, 1fr);
  }
}

/* Enhance for desktop */
@media (min-width: 1024px) {
  .card {
    grid-template-columns: repeat(4, 1fr);
  }
}
Container Query — Component adapts to PARENT width
/* Define a containment context */
.sidebar {
  container-type: inline-size;
  container-name: sidebar;
}

/* Card adapts based on sidebar's width, not viewport */
@container sidebar (min-width: 300px) {
  .card {
    display: grid;
    grid-template-columns: repeat(2, 1fr);
  }
}

@container sidebar (max-width: 299px) {
  .card {
    display: block;  /* Stack vertically in narrow sidebar */
  }
}
Pro Tip

clamp() replaces dozens of media queries for typography. Instead of setting font-size at 5 breakpoints, use clamp(1rem, 2.5vw, 2rem) once. It scales fluidly across all screen sizes. Combined with min() and max(), you can build entire responsive layouts with zero media queries.

Memory Trick: "Mobile-first = start small, enhance up (min-width). Desktop-first = start big, degrade down (max-width). clamp() = elastic sizing. Container queries = 'how big is MY parent?' not 'how big is the window?'"
  • Mobile-first: default styles for mobile, min-width media queries for larger
  • Media queries: @media (min-width: 768px) — conditionally apply styles
  • clamp(min, preferred, max): fluid scaling without breakpoints
  • Container queries (@container): style based on parent container width
  • Container queries enable truly reusable, context-independent components

Tailwind CSS vs CSS Modules vs Styled Components — Utility-first, scoped styles, runtime cost
Intermediate P1 — Critical
Short Interview Answer

Tailwind CSS is a utility-first framework: you compose designs using predefined classes (flex, p-4, text-lg) directly in JSX. Styles are extracted at build time — zero runtime cost, tiny production CSS (~5-10KB gzipped). CSS Modules (.module.css files) scope styles locally by auto-generating unique class names — no naming collisions, good for traditional CSS workflows. Styled Components (and Emotion) use tagged template literals to create React components with scoped styles injected at runtime via a style tag — great DX for dynamic styling but adds ~12-15KB bundle and runtime overhead. The industry has largely moved toward Tailwind + CSS Modules for new projects; Styled Components is in decline due to React Server Components not supporting runtime CSS-in-JS.

Real-World Example

Vercel's marketing site and dashboard use Tailwind CSS. Every component is built with utility classes, and the design system (colors, spacing, typography) is configured in tailwind.config.ts. Facebook's old codebase used CSS Modules extensively — each component had a .module.css file with scoped class names. Vercel (again) is a prime example of the shift: they initially used Styled Components for their dashboard, then migrated to Tailwind because of Server Components compatibility and bundle size concerns. The entire dashboard's CSS is now 7KB versus 45KB with Styled Components.

Common Mistake

Choosing Styled Components for a new Next.js 13+ project. The library doesn't work with React Server Components (styled-components requires client-side JavaScript to inject styles). You'll be forced to use "use client" everywhere, losing all RSC benefits. Use Tailwind or CSS Modules for new projects — they work everywhere, including Server Components.

Code Example
Tailwind CSS — Utility-first in JSX
export function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <div className="bg-white dark:bg-gray-800 rounded-xl shadow-md p-6 hover:shadow-lg transition-shadow">
      <h3 className="text-lg font-semibold">{title}</h3>
      <p className="text-gray-600 dark:text-gray-300">{children}</p>
    </div>
  );
}
CSS Modules — Scoped styles
/* Card.module.css */
.card {
  background: white;
  border-radius: 12px;
  padding: 1.5rem;
  box-shadow: 0 2px 8px rgba(0,0,0,0.1);
}

// Card.tsx
import styles from './Card.module.css';
export function Card() { return <div className={styles.card}>...</div>; }
Styled Components — CSS-in-JS (Declining)
import styled from 'styled-components';

const Card = styled.div`
  background: white;
  border-radius: 12px;
  padding: 1.5rem;
  /* Dynamic via props — but runs at runtime */
`;
Senior Developer Insight

The CSS-in-JS vs utility-first debate is settled for most use cases. React Server Components make runtime CSS-in-JS non-viable. But CSS Modules still have their place: complex animations with @keyframes, print stylesheets, and projects where designers write CSS directly are better with CSS Modules. Tailwind wins for speed, consistency, and bundle size. The pragmatic approach: use Tailwind for 90% of styles, CSS Modules for the 10% that need CSS features Tailwind can't express (complex keyframe animations, scroll-driven animations, intricate pseudo-element styling).

Memory Trick: "Tailwind = build-time, zero runtime, utility classes. CSS Modules = build-time, scoped .css files. Styled Components = runtime, CSS-in-JS, dying. Choose Tailwind for new Next.js projects."
  • Tailwind: utility-first, zero runtime, tiny bundle, perfect for RSC
  • CSS Modules: scoped .css files, traditional workflow, zero runtime
  • Styled Components: CSS-in-JS, runtime injection, incompatible with RSC
  • Industry trend: Tailwind + CSS Modules for new projects
  • Choose based on: SSR requirement, dynamic styling needs, team expertise

CSS Custom Properties (Variables) — Theming, dynamic styling, design tokens
Intermediate P1 — Critical
Short Interview Answer

CSS Custom Properties (variables) are defined with --name: value and accessed with var(--name). Unlike Sass variables (which are static and compile away), CSS custom properties are live at runtime — they can be changed with JavaScript, respond to media queries, and cascade through the DOM. This makes them perfect for theming (dark/light mode), design tokens (colors, spacing, typography), and dynamic styling (animating with CSS variables). They're also inheritable — a variable set on :root is available everywhere; one set on a parent is available to all children. @property registration gives them types and enables smooth transitions.

Easy Explanation

Sass variables are like a photocopier — the value is baked into the paper at build time and can't change. CSS custom properties are like a dimmer switch — you can adjust them live, and everything using them updates instantly. Set --button-color: blue on the root, and every button turns blue. Change it on hover to red — only that button turns red, because the variable cascades locally. This is why CSS variables enable dark mode without JavaScript: just swap --bg from white to black inside a prefers-color-scheme: dark media query.

Real-World Example

Stripe's design system uses CSS custom properties as design tokens: --color-primary: #635BFF; --spacing-md: 1rem; --radius-sm: 4px;. Every component references these tokens, so changing the primary color in one place updates the entire application. GitHub's dark mode uses CSS custom properties: the variables are defined once in :root (light) and overridden in [data-color-mode="dark"]. The actual components just use var(--bg-primary) — they don't know or care what the current theme is.

Common Mistake

Thinking CSS variables work exactly like Sass variables. Sass variables are compiled away and can't be changed at runtime. CSS variables are live and cascade — which also means they can cause unexpected behavior if you set a variable too high in the tree (e.g., on :root) and a child component accidentally inherits it. Always scope theme variables to their appropriate context (e.g., theme-specific classes).

CSS Animations vs Transitions — @keyframes, transform, will-change, GPU-friendly properties
Intermediate P1 — Critical
Short Interview Answer

Transitions animate between two states (A to B) when a CSS property changes — perfect for hover effects, class toggles, and state changes. Animations (@keyframes) define multi-step sequences that can loop, reverse, or run independently of state changes — perfect for spinners, loading skeletons, entrance effects. For smooth 60fps performance, only animate GPU-friendly properties: transform (translate, scale, rotate) and opacity. Avoid animating width, height, top, left, margin — these trigger layout recalculations and paint on every frame, causing jank. Use will-change sparingly to hint the browser to optimize an element before it animates.

Easy Explanation

Transitions are like a dimmer switch — you move it and the lights smoothly change from bright to dim. Animations are like a washing machine cycle — predefined steps that run automatically (wash, rinse, spin, repeat). Transitions react to changes; animations run on their own. The golden rule: only animate transform and opacity because the GPU handles them without bothering the CPU. Animating width or left is like asking the browser to re-measure and re-paint the entire room every frame — that's how you get janky animations.

Real-World Example

Apple's product pages are masters of GPU-friendly animations. Discord's loading screen uses @keyframes with rotation and opacity on a simple SVG — the spinner runs at 60fps because it only animates transform. Twitter's "like" heart animation uses @keyframes with scale() — it bursts out from 0 to 1.2, then settles at 1.0, all on the GPU.

Common Mistake

Animating width on a collapse/expand component. Every frame the browser recalculates layout, repaints, and potentially re-composites — the holy trinity of jank. Senior Developer Insight

will-change is a double-edged sword. It tells the browser "this element is going to animate" which creates a new GPU layer, making the animation buttery smooth. But if you apply it to everything, you're creating GPU layers for elements that never animate, consuming VRAM and potentially causing worse performance. The rule: add will-change just before the animation starts (via JavaScript or a class toggle), and remove it after the animation ends. Never put it on everything by default.

Memory Trick: "Only animate transform and opacity — the GPU handles these for free. Transitions = reaction to change. Animations = scripted performance. will-change = performance hint (use sparingly)."

What happens when you type a URL in the browser? — DNS, TCP, TLS, HTTP, and the Critical Rendering Path
Intermediate P1
Answer

This classic question tests your full-stack understanding of how the browser turns a URL into pixels. The sequence:

1. DNS Resolution: Browser checks caches (browser → OS → router → ISP DNS → recursive lookup). Converts example.com → IP like 93.184.216.34. Takes 20-120ms.

2. TCP Connection: Three-way handshake: SYN → SYN-ACK → ACK. One round trip (~50ms).

3. TLS Negotiation (HTTPS): Client Hello → Server Hello + Certificate → Key Exchange → Secure Connection. Takes 2-3 round trips (~100-200ms). TLS 1.3 reduces to 1 RTT (0-RTT for returning visitors).

4. HTTP Request: Browser sends GET / HTTP/1.1 or HTTP/2 (multiplexed) or HTTP/3 QUIC (UDP, 0-RTT).

5. HTML Parsing: Browser parses incrementally. CSS is render-blocking — pauses parsing. Scripts without async/defer block. Modern: <link rel="preload"> for critical resources, <script defer> for non-blocking JS.

6. Critical Rendering Path: DOM tree → CSSOM tree → Render Tree (visible nodes only) → Layout (geometry) → Paint (pixels) → Composite (GPU layers). Optimize: inline critical CSS, defer non-critical, preload key resources.

Senior Insight — Optimization by Reducing Round Trips

On 3G (400ms RTT): DNS (50ms) + TCP (50ms) + TLS (150ms) + HTTP (50ms) + response (1000ms) = ~1.3s before parsing begins. Reducing round trips is the highest-leverage perf optimization. Use: (1) preconnect to warm DNS+TLS early, (2) preload for critical CSS/fonts, (3) modulepreload for critical JS, (4) HTTP/3 (QUIC) for 0-RTT on repeat visits. This question is asked at every level at Google, Meta, Amazon, Apple, Microsoft — Scrimba 2026 lists it as the key browser/networking question.

Memory Trick: "URL → DNS (name to IP) → TCP (handshake) → TLS (encrypt) → HTTP (request) → Parse → Render (DOM + CSSOM + Layout + Paint + Composite). Reduce round trips: preconnect, preload, HTTP/3."

CSS — Hiding strategies
.gone {
  display: none; /* layout removal, no space */
}
.invisible {
  visibility: hidden; /* space preserved, layout hole */
}
.transparent {
  opacity: 0; /* invisible but still interactive — can be clicked */
}
Common Mistake

Using display: none vs visibility: hidden interchangeably. Use display: none for conditionally rendered UI (tabs, modals). Use visibility: hidden when layout must not shift (skeleton placeholders, reserved icon slots). Use opacity: 0 only for transitions — never for hiding interactive elements, since they stay clickable and focusable.

Memory Trick: "display:none = gone from layout. visibility:hidden = invisible but holding its seat. opacity:0 = invisible but still clickable."
