01
What is a Closure?
Intermediate P1
Short Answer

A closure is a function that remembers the variables from its outer lexical scope even when the function is executed outside that scope. In simple terms: a function bundled with its surrounding state — a "backpack" of variables it carries with it.

Easy Explanation

When you create a function inside another function, JavaScript gives that inner function a backpack containing all the variables from the outer function that the inner one references. Even after the outer function finishes running, the inner function holds onto that backpack. Every call to the outer function creates a new, independent backpack.

Real-World Example

React's useEffect cleanups, event handlers accessing stale state, debounce/throttle implementations, module patterns (encapsulating private data), and memoization/currying all rely on closures.

Why Asked

Interviewers want to see if you understand JavaScript's scoping model, can debug "stale closure" bugs in React, and can implement common patterns like memoization or once().

Common Mistakes

Creating closures inside loops without let or an IIFE (classic var i problem). Confusing closure with scope — scope determines what's visible; closure is what a function remembers. Creating closures inside React effects without the correct dependency array, leading to stale closures.

Senior Insight

Closures are how JavaScript achieves data privacy without classes. Every module system (CommonJS, ESM) relies on closures to isolate module scope. In React, understanding closures is essential to understanding why useCallback and useMemo exist.

JavaScript — Basic Closure & the "Stale Closure" React Problem
// Classic closure: counter factory
function createCounter() {
  let count = 0;                     // Private variable
  return function() {
    count += 1;
    return count;
  };
}
const counterA = createCounter();
const counterB = createCounter();
counterA(); // 1
counterA(); // 2
counterB(); // 1 — each has its own "backpack"

// React stale closure — classic pitfall
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      // BUG: count is always 0 — the closure captured the initial value
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps = closure never updates
}

// Fix: functional update
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1); // Always latest state
  }, 1000);
  return () => clearInterval(id);
}, []);
Follow-up Questions
  1. Why does let fix the loop closure problem that var has?
  2. What happens to memory when a closure keeps a reference to a large object?
  3. How do closures enable the module pattern? Write a simple module with private and public members.
  4. Explain why useCallback(fn, []) fails when fn references changing state.
Memory Trick: "Function born inside, remembers its outside." Every function in JavaScript is a closure. The scope you see when reading the code is exactly what the function captures, forever.
Summary
  • Closure = function + its lexical environment (the "backpack")
  • Each outer function call creates a new, independent closure
  • Core to React hooks, module patterns, and event handlers
  • "Stale closure" is the #1 React bug — use functional updates or proper deps
02
How does the Event Loop work?
Advanced P1
Short Answer

The event loop is JavaScript's mechanism for handling asynchronous operations. It continuously checks the call stack — if empty, it pulls the oldest callback from the microtask queue (Promises, queueMicrotask) first, then the macrotask queue (setTimeout, setInterval, I/O). This creates JavaScript's non-blocking, single-threaded concurrency model.

Easy Explanation

Imagine a restaurant. The chef (call stack) cooks one dish at a time. Orders (callbacks) wait on two counters: the VIP counter (microtask queue) and the regular counter (macrotask queue). The chef always checks the VIP counter first and clears ALL of it before taking one order from the regular counter, then checks VIP again, and so on.

Real-World Example

Explains why Promise.resolve().then(() => console.log(2)) runs before setTimeout(() => console.log(3), 0) even with zero delay. Also critical for understanding React's useEffect timing and setState batching.

Why Asked

This is the #2 most-asked JavaScript interview question worldwide (after closures). It tests deep understanding of async behavior, essential for frontend performance debugging.

Common Mistakes

Thinking setTimeout(fn, 0) runs immediately. Thinking there's only one queue. Not knowing microtasks exist. Confusing the order of microtask execution — the entire microtask queue drains before any macrotask.

Senior Insight

Microtask starvation is a real problem: if a microtask keeps adding more microtasks, the macrotask queue (including rendering) never runs. React's flushSync is essentially forcing synchronous work to avoid letting the event loop tick. requestAnimationFrame runs before paint, which is neither micro nor macro.

JavaScript — Event Loop Order
// What is the output?
console.log('1: sync');

setTimeout(() => console.log('2: macrotask'), 0);

Promise.resolve()
  .then(() => {
    console.log('3: microtask 1');
    Promise.resolve().then(() =>
      console.log('4: microtask 2 — chained')
    );
  });

setTimeout(() => console.log('5: macrotask 2'), 0);

console.log('6: sync');

// Output: 1, 6, 3, 4, 2, 5
// Microtasks queue completely drains between macrotasks
// Cycle: Sync -> ALL Microtasks -> ONE Macrotask -> ALL Microtasks -> ...
Follow-up Questions
  1. What happens if a microtask recursively adds itself? (UI freezes, macrotasks never run)
  2. Where does requestAnimationFrame fit? (Rendering phase, before paint)
  3. How does queueMicrotask() differ from process.nextTick in Node.js?
  4. Why does React batch setState calls? (Synchronous completion prevents intermediate renders)
Memory Trick: "One macrotask, drain microtasks, repeat." Like a restaurant chef: clear all VIP orders (microtasks) before checking the regular queue (macrotasks) again.
Summary
  • JavaScript is single-threaded — one call stack, one thing at a time
  • Microtask queue drains completely before next macrotask
  • Macrotask queue processes one at a time
  • Rendering happens between event loop iterations, never during a task
  • Critical for debugging React timing, race conditions, and UI freezes

Explain var vs let vs const and Hoisting
Beginner P1
Short Answer

var is function-scoped, hoisted and initialized to undefined, and allows redeclaration. let and const are block-scoped, hoisted but NOT initialized (Temporal Dead Zone), and do not allow redeclaration. const additionally prevents reassignment but not mutation of objects/arrays. All three are hoisted — the difference is what happens during hoisting.

Easy Explanation

var is like leaving keys on the kitchen counter in a shared house — anyone in the house (function) can use them. let and const are like locking your keys in a specific room (block). The TDZ is like being told "your key exists but you cannot touch it yet" until you actually reach the declaration line.

Real-World Example

React's useState returns a const tuple because you never reassign — you call the setter. In for loops, let creates a fresh binding per iteration (critical for closures in loops).

Why Asked

Tests whether you understand JavaScript's fundamental scoping model. Misunderstanding this leads to unpredictable bugs, especially with async code in loops and React closures.

Common Mistakes

Using var in for loops with setTimeout — all callbacks see the final value. Thinking let isn't hoisted (it is — the TDZ proves it). Mutating const objects and thinking that violates const (const prevents reassignment, not mutation).

JavaScript — Hoisting & TDZ in Action
// var hoisting — initialized to undefined
console.log(a); // undefined — NOT ReferenceError
var a = 5;

// let/const hoisting — TDZ
console.log(b); // ReferenceError: Cannot access before initialization
let b = 10;

// Block scope vs function scope
if (true) {
  var x = 1;   // leaks out of the block
  let y = 2;   // block-scoped — not visible outside
}
console.log(x); // 1
console.log(y); // ReferenceError

// const with objects — mutation allowed
const user = { name: 'Alice' };
user.name = 'Bob';        // Ok — mutating property
user = { name: 'Charlie' }; // TypeError — reassignment

// let in for loop — fresh binding per iteration
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 0, 1, 2
}
Follow-up Questions
  1. Why does let i inside a for loop create a fresh binding each iteration?
  2. What exactly is the Temporal Dead Zone? When does it begin and end?
  3. How does hoisting affect function declarations vs function expressions?
  4. Why does React use const [state, setState] = useState()?
Memory Trick: "var is the messy roommate, let/const respect your personal space. All are hoisted, but var gets a free undefined upgrade. TDZ = elevator door that won't open until you reach your floor."
Summary
  • var: function-scoped, hoisted + initialized to undefined, redeclarable
  • let: block-scoped, hoisted but uninitialized (TDZ), not redeclarable
  • const: same as let + no reassignment (but objects/arrays are still mutable)
  • Always prefer const by default, let when you need reassignment, never var

Explain Promise.all vs allSettled vs race vs any
Intermediate P1
Short Answer

Promise.all resolves when all succeed, rejects immediately if any fail (fast-fail). Promise.allSettled waits for all to finish, never rejects, returns array of {status, value|reason} objects. Promise.race settles with the first to settle (resolve or reject). Promise.any resolves with the first to fulfill, rejects with AggregateError only if all reject.

Easy Explanation

Promise.all: "Everyone must succeed or we all fail." Promise.allSettled: "I will wait for everyone, tell you who succeeded and who failed." Promise.race: "First to the finish line wins, whether carrying a trophy or a bomb." Promise.any: "Give me the first trophy — ignore explosions unless all are bombs."

Real-World Example

React dashboards: Promise.all for critical parallel data (profile + posts + settings). Promise.allSettled for non-critical widgets (show partial data even if some fail). Promise.race for timeouts. Promise.any for fallback API servers.

Why Asked

Real apps have multiple concurrent API calls. Knowing which combinator to use is the difference between a working app and one that crashes because one endpoint is down.

Common Mistakes

Using Promise.all when you need partial results (use allSettled). Using Promise.race thinking it returns only the winner — a rejected promise can win. Not knowing promies aren't cancellable — a rejected promise in .all doesn't stop the others from executing.

JavaScript — Four Promise Combinators
const p1 = Promise.resolve('Data A');
const p2 = new Promise(r => setTimeout(r, 100, 'Data B'));
const p3 = Promise.reject('Error');

// Promise.all — fast-fail (all must succeed)
const all = await Promise.all([p1, p2, p3])
  .catch(e => `Failed: ${e}`); // -> "Failed: Error"

// Promise.allSettled — never rejects, get all results
const settled = await Promise.allSettled([p1, p2, p3]);
// [{ status: 'fulfilled', value: 'Data A' },
//  { status: 'fulfilled', value: 'Data B' },
//  { status: 'rejected',  reason: 'Error' }]

// Filter successes from allSettled (React pattern)
const successes = settled
  .filter(r => r.status === 'fulfilled')
  .map(r => r.value);

// Promise.race — first to settle wins (resolve OR reject)
const timeout = new Promise((_, rej) =>
  setTimeout(rej, 3000, 'Timeout')
);
await Promise.race([fetchData(), timeout]); // 3s timeout pattern

// Promise.any — first to fulfill (ignore rejections)
const result = await Promise.any([fetchFromCDN(), fetchFromBackup()]);
Follow-up Questions
  1. How would you implement your own Promise.all from scratch?
  2. What happens to the other promises when Promise.all rejects? (They still run — promises aren't cancellable)
  3. How does Promise.allSettled handle a mix of sync and async values?
  4. When would you use Promise.any in a real React app?
Memory Trick: "All or nothing (all), everyone's report card (allSettled), first to the finish (race), first to succeed (any). React dashboard = allSettled, critical page = all, timeout = race, fallback = any."
Summary
  • Promise.all: parallel, fast-fail — use for dependent data loading
  • Promise.allSettled: parallel, never rejects — use for dashboard widgets
  • Promise.race: first to settle — use for timeouts
  • Promise.any: first to fulfill — use for redundant API endpoints

How does Async/Await work?
Intermediate P1
Short Answer

async/await is syntactic sugar over Promises and generators. An async function always returns a Promise. await pauses execution within the function until the Promise settles, yielding control back to the event loop. It makes asynchronous code read like synchronous code while preserving non-blocking behavior.

Easy Explanation

Without async/await, you chain .then() calls — like passing notes through a chain of people. Async/await lets you write the same thing line by line. Under the hood, the engine slices your function into segments that resume when each awaited promise resolves.

Real-World Example

React useEffect callbacks can't be async directly — you define an inner async function. Sequential vs parallel awaits dramatically affect load performance.

Why Asked

Virtually every production React app fetches data. Interviewers want to see that you understand the performance implications of await (blocking in-sequence) vs Promise.all, and that you handle errors properly.

Common Mistakes

Awaiting parallel requests sequentially — each blocks the next, doubling/tripling load times. Forgetting try/catch, leading to unhandled rejections. Making useEffect async (you cannot — the cleanup function must be synchronous).

Senior Insight

Async/await is built on generators and Promises. Every await is a yield point. await pauses only the enclosing async function — not the caller, not the global scope. The event loop continues running while the function is suspended.

JavaScript — Sequential vs Parallel & React Patterns
// Sequential — each await blocks the next (anti-pattern for independent calls)
async function loadSlow() {
  const user   = await fetchUser();     // 300ms
  const posts  = await fetchPosts();    // 300ms
  const photos = await fetchPhotos();   // 300ms => Total: 900ms
}

// Parallel — all fire at once
async function loadFast() {
  const [user, posts, photos] = await Promise.all([
    fetchUser(), fetchPosts(), fetchPhotos()
  ]);
  // Total: ~300ms
}

// React useEffect pattern — cannot be async directly
useEffect(() => {
  async function load() {
    try {
      const data = await fetchAPI();
      setData(data);
    } catch (e) {
      setError(e.message);
    } finally {
      setLoading(false);
    }
  }
  load();
}, []);

// Graceful error handler pattern (Go-style)
async function safeAwait(promise) {
  try {
    const data = await promise;
    return [data, null];
  } catch (error) {
    return [null, error];
  }
}
// Usage: const [data, err] = await safeAwait(fetchUser());
Follow-up Questions
  1. What does Babel/TypeScript compile async/await to? (generators + promises)
  2. Can you use await inside a non-async function? What about at the module top level?
  3. How do you handle concurrent async operations with Promise.all while still using await?
  4. What happens to the event loop while an async function is awaiting?
Memory Trick: "Async = sugar for Promises. Await = pauses this function only (not the world). Sequential = water buckets in a line. Parallel = all buckets filled simultaneously."
Summary
  • async function always returns a Promise — use try/catch for error handling
  • await yields control to the event loop; only the enclosing function pauses
  • Sequential awaits = performance anti-pattern for independent calls
  • Parallel = Promise.all() wrapped in a single await
  • React: useEffect callbacks cannot be async — use inner async function

What is the difference between Debounce and Throttle?
Intermediate P1
Short Answer

Debounce delays execution until after a series of calls has stopped for a specified time. Only the last call runs. Throttle limits execution to at most once per specified interval — the first call runs immediately, then subsequent calls within the interval are ignored.

Easy Explanation

Debounce is like an elevator door — it keeps resetting the timer every time someone enters. It only closes (executes) after people stop entering for a moment. Throttle is like a bouncer at a club — people can enter one at a time, with a minimum gap between each entry.

Real-World Example

Debounce: search-as-you-type (don't hit the API on every keystroke). Throttle: scroll-based infinite loading (check scroll position at most every 200ms). Window resize handlers also use throttle.

Why Asked

Every interviewer has debugged a search box that fires 300 API calls per minute. They want to know you think about API costs and browser performance.

Common Mistakes

Using debounce for scroll handlers (user never "stops" scrolling — the callback may never fire). Using throttle for search input (multiple intermediate calls still fire). Not cleaning up timers on component unmount in React.

JavaScript — Debounce & Throttle Implementations
// Debounce — wait for pause, then execute once
function debounce(fn, delay = 300) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// Throttle — at most once per {limit}ms
function throttle(fn, limit = 200) {
  let inThrottle = false;
  return function(...args) {
    if (!inThrottle) {
      fn.apply(this, args);
      inThrottle = true;
      setTimeout(() => (inThrottle = false), limit);
    }
  };
}

// React custom hook with cleanup
function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cleanup on unmount/re-render
  }, [value, delay]);
  return debounced;
}
Follow-up Questions
  1. Implement a debounce with leading edge (fire immediately, then debounce subsequent calls).
  2. How would you throttle API calls in a React app without a custom hook?
  3. Why does React's useEffect cleanup solve the stale timer problem?
  4. What is the difference between debounce and a requestAnimationFrame approach?
Memory Trick: "Debounce = delay until done (search input). Throttle = throttle the flow (scroll, resize)."
Summary
  • Debounce: wait for pause, fire once — search inputs, resize end
  • Throttle: fire at fixed rate — scroll, mousemove, game loops
  • Always clean up timers in React useEffect returns
  • Debounce leading edge variant: fire immediately, ignore subsequent rapid calls

Explain the this keyword and call/apply/bind
Intermediate P1
Short Answer

this is determined by how a function is called, not where it is defined. Rules in priority order: (1) new binding (new instance), (2) explicit binding (call/apply/bind), (3) implicit binding (obj.method()), (4) default binding (global/undefined in strict mode). Arrow functions break all rules — they inherit this from the enclosing lexical scope at definition time.

Easy Explanation

Arrow functions are like pre-recorded messages — the "this" was decided when the message was recorded, not when it gets played. Regular functions determine "this" based on who called them at runtime. If nobody called them (bare function call), "this" defaults to global (or undefined in strict mode).

Real-World Example

React class components used this.handleClick = this.handleClick.bind(this) to preserve this in event handlers. Modern React uses arrow functions in functional components, which naturally inherit the correct context.

Why Asked

If you have worked with class-based React, you have been burned by this. Interviewers test whether you understand why .bind was necessary and how arrow functions fixed it.

Common Mistakes

Calling a method as a callback loses the object context (setTimeout(obj.method, 0) — this becomes global). Using arrow functions as object methods (they do not get the object as this). Confusing bind (returns new function) with call/apply (invokes immediately).

JavaScript — this Binding Rules
// Rule 1: new binding (highest priority)
function Person(name) { this.name = name; }
const alice = new Person('Alice'); // this -> new instance

// Rule 2: explicit binding — call, apply, bind
function greet() { return `Hi ${this.name}`; }
const user = { name: 'Bob' };
greet.call(user);               // "Hi Bob" — call: comma-sep args, invokes immediately
greet.apply(user);              // "Hi Bob" — apply: array of args, invokes immediately
const bound = greet.bind(user);   // returns new function, doesn't invoke
bound();                       // "Hi Bob"

// Rule 3: implicit binding — obj.method()
const counter = {
  count: 0,
  increment() { this.count++; } // this -> counter
};

// Rule 4: default — global (or undefined in strict mode)
function loose() { console.log(this); }
loose(); // window (sloppy), undefined (strict)

// Arrow functions — ignore all rules, lexical this
const obj = {
  name: 'Eve',
  regular: function() { return this.name; },   // works: this -> obj
  arrow:   () => this.name                        // broken: this -> outer scope
};

// Memory aid: Call = Commas, Apply = Array
Follow-up Questions
  1. What does bind return? Can you re-bind a bound function?
  2. Why did React class components need .bind(this) in the constructor?
  3. How do arrow functions get their this? Can you change it?
  4. What happens with this inside a nested function inside a method?
Memory Trick: "Who's on the left of the dot? That's this." (Except for arrow functions — they ignore the dot.) Call = Commas, Apply = Array.
Summary
  • 4 rules (priority): new → call/apply/bind → obj.method() → global/undefined
  • Arrow functions are lexically bound — inherit this from surrounding non-arrow scope
  • call(thisArg, a, b, c) — comma-separated, invokes immediately
  • apply(thisArg, [a, b, c]) — array of args, invokes immediately
  • bind(thisArg, a, b) — returns a new function, does not invoke

Explain Prototype and Prototypal Inheritance
Intermediate P1
Short Answer

Every JavaScript object has an internal [[Prototype]] link (accessible via __proto__ or Object.getPrototypeOf). When you access a property that does not exist on the object, JavaScript follows this chain upward to find it. This is prototypal inheritance — objects inherit directly from other objects, not from classes.

Easy Explanation

It is a "if I do not have it, ask my parent" system. When you ask for arr.map(), arr does not have map — but Array.prototype does. JavaScript walks the chain: arr -> Array.prototype -> Object.prototype -> null. The class keyword is just sugar over this chain.

Real-World Example

Every array gets .map, .filter, .reduce from Array.prototype. Every object gets .toString(), .hasOwnProperty() from Object.prototype. React class components (extends React.Component) are prototypal inheritance in action.

Why Asked

Understanding prototypes is understanding JavaScript's DNA. It explains how methods work, why instanceof exists, and what React class components actually do under the hood.

Senior Insight

Prototypal delegation is more powerful than classical inheritance. You can compose behaviors by mixing multiple prototypes (mixins) without the brittle hierarchies of Java-style classes. React's move from class components to hooks is essentially a move from inheritance-based sharing to composition-based sharing.

JavaScript — Prototype Chain & Class Sugar
// The prototype chain
const arr = [1, 2, 3];
arr.map(x => x * 2);            // method lives on Array.prototype
arr.toString();               // lives on Object.prototype
// Chain: arr -> Array.prototype -> Object.prototype -> null

// Constructor function pattern (pre-ES6)
function Animal(name) { this.name = name; }
Animal.prototype.speak = function() { return `${this.name} speaks`; };

function Dog(name, breed) {
  Animal.call(this, name); // call parent constructor
  this.breed = breed;
}
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;

const rex = new Dog('Rex', 'Lab');
rex.speak(); // "Rex speaks" — inherited from Animal.prototype

// Class syntax is sugar for the above
class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} speaks`; }
}
class Dog extends Animal {
  constructor(name, breed) { super(name); this.breed = breed; }
}
Follow-up Questions
  1. What is the end of every prototype chain? (null)
  2. What is the difference between __proto__ and prototype?
  3. How does Object.create(null) differ from {}?
  4. Why did React move away from class components?
Memory Trick: "If I do not have it, ask __proto__. Continue until null. class is just prettier syntax for constructor + prototype." .prototype lives on functions (constructors); .__proto__ lives on instances (objects).
Summary
  • Every object delegates to another object (its prototype)
  • Property lookup walks the chain: obj -> proto -> proto -> ... -> null
  • class syntax = sugar over constructor functions + prototype
  • Composition (mixins) often beats deep inheritance hierarchies

Explain Map, Filter, Reduce
Beginner P1
Short Answer

Three core array methods for immutable data transformation. map transforms each element (same length array). filter selects elements by condition (subset array). reduce combines all elements into a single value (any type). All return new arrays/values — they do not mutate the original.

Easy Explanation

Map = assembly line: every item transformed, same count out. Filter = bouncer: only items passing the test get through. Reduce = shopping cart: start with total, process each item, end with single result. Reduce can implement map and filter — it is the Swiss Army knife.

Real-World Example

React list rendering: array.map(item => <li key={item.id}>{item.name}</li>). Filter active users: users.filter(u => u.active). Sum cart total: cart.reduce((sum, item) => sum + item.price * item.qty, 0).

Why Asked

These are the backbone of React data transformations. If you cannot solve a problem with map/filter/reduce, you probably reached for for loops too quickly.

Common Mistakes

Using map to iterate without returning (use forEach). Not providing an initial value to reduce when the array might be empty. Forgetting the key prop in React map. Mutating the original array inside a map callback.

JavaScript — Map, Filter, Reduce + React Patterns
const prices  = [10, 20, 30];
const withTax = prices.map(p => p * 1.2); // [12, 24, 36]

const users = [{ name: 'A', active: true }, { name: 'B', active: false }];
const active = users.filter(u => u.active); // [{ name: 'A', active: true }]

const total = prices.reduce((sum, p) => sum + p, 0); // 60

// Chaining — React data pipeline
const activeTotal = users
  .filter(u => u.active)
  .map(u => u.name)
  .reduce((acc, name) => acc + `, ${name}`, '');

// Reduce as groupBy
const byStatus = users.reduce((acc, u) => {
  const key = u.active ? 'active' : 'inactive';
  acc[key] = [...(acc[key] || []), u];
  return acc;
}, {});

// React: derived state
// const completedCount = todos.filter(t => t.done).length;
Follow-up Questions
  1. Implement your own map function using reduce.
  2. What does flatMap do? When would you use it in React?
  3. How would you remove duplicates from an array using reduce?
  4. Why is reduce the most powerful of the three? (It can implement the other two.)
Memory Trick: "Map = same length, different shape. Filter = smaller subset. Reduce = single value from many." React: map creates JSX lists, filter hides/shows, reduce computes aggregates.
Summary
  • map: 1:1 transformation, returns array of same length
  • filter: subset based on predicate, returns smaller or equal-length array
  • reduce: accumulates to any value (number, object, array, string)
  • All are immutable — they do not modify the original array
  • Chain them for React data pipelines; always provide initial value to reduce

Explain == vs === and Type Coercion
Beginner P1
Short Answer

=== (strict equality) checks value AND type without coercion. == (loose equality) performs type coercion first, then compares. Coercion follows the Abstract Equality Comparison Algorithm — a specific set of rules (string -> number, boolean -> number, object -> primitive via valueOf/toString). Always prefer ===.

Easy Explanation

=== is like a strict bouncer: "Show ID AND it must match exactly." == is a lazy bouncer: "You look 21? Come in." JavaScript's coercion engine tries to be "helpful" by converting types, creating some of the most infamous bugs ([] == ![] = true).

Real-World Example

React conditional rendering: {data.length && <List />} — if data.length is 0, React renders "0" because 0 is falsy. Safer: {data.length > 0 && <List />}.

Why Asked

Coercion bugs are subtle and pervasive. Interviewers want to know you understand truthy/falsy values and will not write if (x == true) when if (x) suffices.

Common Mistakes

Trusting == in any non-trivial comparison. Not knowing the falsy values: false, 0, -0, 0n, "", null, undefined, NaN. NaN === NaN is false — use Number.isNaN().

JavaScript — Coercion & React Pitfalls
// The infamous coercion table
0 == '0'          // true  — string '0' -> 0
0 == []           // true  — [] -> "" -> 0
'0' == []        // false — [] -> "", "0" != ""
[] == ![]          // true  — ![] -> false -> 0, [] -> "" -> 0
null == undefined  // true  — special rule
null == 0         // false — null only equals undefined and itself

// Falsy values (complete list): false, 0, -0, 0n, '', null, undefined, NaN
// Everything else is truthy — including {}, [], 'false', '0'

// React conditional rendering trap
const arr = [];
{arr.length && 'Rendered!'}   // -> renders "0" (React renders falsy numbers)
{arr.length > 0 && 'Rendered!'} // -> renders nothing (correct)

// NaN — the only value not equal to itself
NaN === NaN             // false
Number.isNaN(NaN)     // true  — proper check
Object.is(NaN, NaN)   // true  — strictest comparison

// Object.is — even stricter than ===
Object.is(0, -0) // false (=== says true)

  2. Why does React render 0 when you write {items.length && <List />}?
  3. What does !! do? Is it good or bad practice?
  4. How would you write a safe isEqual that handles NaN?

Summary
  • === — no coercion, always use this
  • == — coercion, only null == undefined is arguably useful
  • 8 falsy values: false, 0, -0, 0n, "", null, undefined, NaN
  • React: never use .length directly in conditionals — use > 0
  • Object.is() for strictest comparison (handles NaN and -0)

Explain Spread, Rest, and Destructuring
Beginner P1
Short Answer

Spread (...) expands an iterable or object properties into individual elements/properties. Rest (...) collects remaining elements/properties into a new array/object — opposite of spread, used in function params and destructuring. Destructuring unpacks values from arrays/objects into distinct variables.

Easy Explanation

Spread is pouring a bag of marbles onto a table — the bag disappears and you have individual marbles. Rest is sweeping leftover marbles back into a bag. Destructuring is taking specific marbles and naming them: "I will call this one Bob, this one Alice."

Real-World Example

React state updates: setUser({...user, name: 'New'}). Props destructuring: function Card({title, children, ...rest}). Merging configs: const config = {...defaults, ...overrides}.

Why Asked

These are the 3 most common syntax patterns in modern React code. Interviewers want to see you write them effortlessly — no looking up syntax.

Senior Insight

Spread is shallow — it does not clone nested objects. For deep clones use structuredClone(). In TypeScript, rest parameters with generics give precise type narrowing.

JavaScript — Spread, Rest & Destructuring
// Spread — expand arrays
const nums = [1, 2, 3];
const more = [0, ...nums, 4];   // [0, 1, 2, 3, 4]
Math.max(...nums);               // replaces Math.max.apply(null, nums)

// Spread — merge/copy objects (shallow!)
const defaults = { theme: 'dark', font: 14 };
const overrides = { font: 16 };
const config = { ...defaults, ...overrides }; // { theme: 'dark', font: 16 }

// Rest — function parameters (replaces 'arguments')
function sum(multiplier, ...numbers) {
  return multiplier * numbers.reduce((a, b) => a + b, 0);
}
sum(2, 1, 2, 3); // 12 — numbers = [1, 2, 3]

// Rest in destructuring
const { a, b, ...rest } = { a: 1, b: 2, c: 3, d: 4 }; // rest = { c: 3, d: 4 }
const [first, second, ...restArr] = [10, 20, 30, 40]; // restArr = [30, 40]

// Destructuring — objects with rename + default
const { name, age: userAge = 18 } = { name: 'Alice', age: 25 };

// React patterns
// Props: function Card({ title, children, ...props }) {}
// State: setUser(prev => ({ ...prev, name: 'New' }))
// Hooks: const [state, setState] = useState(init)
Follow-up Questions
  1. Is spread deep or shallow? How do you deeply clone?
  2. What happens if you spread a non-iterable value? (TypeError at runtime)
  3. How does rest parameter differ from the arguments object?
  4. Can you use rest in the middle of a destructuring pattern?
Memory Trick: "Spread EXPANDS, Rest COLLECTS. Same syntax (...), but spread is on the right side of = or inside function calls, rest is on the left side or in function parameters."
Summary
  • Spread (...arr, ...obj) — expands elements, shallow copy
  • Rest (...args) — collects remaining items into array or object
  • Destructuring — unpacks into variables, supports defaults and renaming
  • React: props destructuring, immutability via spread, useState destructuring
  • Rest parameters are true arrays (unlike arguments)

Explain Closures in React — The Stale Closure Problem
Advanced P1
Short Answer

The stale closure problem is the most common React bug involving closures. When a useEffect or useCallback captures a state value, it forms a closure over that specific value. If the dependency array is missing or incomplete, the closure never updates and always sees the original value — even after multiple re-renders.

Easy Explanation

Imagine taking a photo of a whiteboard. The board keeps changing, but your photo (closure) is frozen at the moment you took it. If you keep referencing the photo instead of looking at the actual board, you are working with stale data. React's dependency arrays tell it when to take new photos.

Real-World Example

Timer that increments state but uses stale value. Event listener attached in useEffect with empty deps reading stale props. WebSocket handler using an old callback. Passed callback prop that is wrapped in useCallback but does not re-create when dependencies change.

Why Asked

This is the #1 React-specific closure question. If you have done React for more than 6 months, you have fought this bug. Interviewers want to see you can explain and fix it.

Three Fixes for Stale Closures

(1) Add correct dependencies to the array. (2) Use functional update: setCount(c => c + 1) — no dependency on count needed. (3) Use a ref for values that should always be current without triggering re-render (useRef).

React — Stale Closure Patterns & Fixes
// PROBLEM 1: Timer with stale state
function StaleTimer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // count is always 0!
    }, 1000);
    return () => clearInterval(id);
  }, []); // stale closure — sees initial count forever
}

// FIX A: Functional update — no dependency needed
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1); // always gets latest state
  }, 1000);
  return () => clearInterval(id);
}, []); // clean — no deps needed for count

// FIX B: useRef for always-current values
function EventCallback({ onEvent }) {
  const onEventRef = useRef(onEvent);
  useEffect(() => { onEventRef.current = onEvent; }, [onEvent]);

  useEffect(() => {
    const handler = (e) => onEventRef.current(e);
    window.addEventListener('keydown', handler);
    return () => window.removeEventListener('keydown', handler);
  }, []); // no re-attach, always gets latest callback
}

// PROBLEM 2: useCallback with missing deps
const handleSubmit = useCallback(() => {
  submit(data); // data is stale if not in deps!
}, [submit]); // missing: data => stale closure
Follow-up Questions
  1. Why does not ESLint's exhaustive-deps warn about functional updates?
  2. When should you reach for useRef instead of useState to avoid stale closures?
  3. How does React Compiler (auto-memoization) solve stale closure issues?
  4. What is the performance cost of adding every dependency to the array?
Memory Trick: "Stale closure = old photo of state. Fixes: (1) correct deps, (2) functional setState, (3) ref. If your handler reads state and does not re-register, you have a bug."
Summary
  • Stale closure = function captures a value that is since been updated
  • Root cause: missing or static dependency array in useEffect/useCallback
  • Fix 1: Use functional setState updates (setCount(c => c + 1))
  • Fix 2: Use useRef for values that should always be current
  • Fix 3: Add all referenced variables to the dependency array
  • eslint-plugin-react-hooks catches most stale closure bugs

What is Event Delegation?
Intermediate P1
Short Answer

Event delegation is attaching a single event listener to a parent element to handle events for all current AND future children, using event bubbling. Instead of attaching listeners to each child, you attach one to the common ancestor and check event.target to determine which child triggered the event.

Easy Explanation

Instead of a guard at every door in a building (expensive), you post one guard at the front desk who checks IDs and routes. When someone arrives, the guard checks e.target to see which door they should enter.

Real-World Example

React's SyntheticEvent system uses event delegation internally — React attaches one listener per event type at the root. Vanilla JS: a todo list with click-to-delete — attach one listener to <ul>, not each <li>.

Why Asked

Shows you understand DOM performance and the event system. React itself is built on this pattern.

Senior Insight

React 17+ no longer attaches events to document — it uses the root container to support multiple React roots. Not all events bubble (focus, blur, scroll on some elements) — delegation only works with bubbling events.

JavaScript — Event Delegation & React SyntheticEvent
// Vanilla JS: delegate click on a list
const list = document.querySelector('#todo-list');
list.addEventListener('click', (e) => {
  const li = e.target.closest('li'); // find actual li (handles nested clicks)
  if (!li) return;                     // click was not on a list item

  if (e.target.matches('.delete-btn')) {
    li.remove(); // delete button was clicked
  } else {
    toggleDone(li); // item itself was clicked
  }
});

// Without delegation (anti-pattern): each li needs its own listener
// document.querySelectorAll('li').forEach(li => li.addEventListener('click', fn))

// React handles delegation internally via SyntheticEvent
function TodoList({ items }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id} onClick={() => handleDelete(item.id)}>
          {item.text}
        </li>
      ))}
    </ul>
  );
  // React internally uses one root-level listener per event type
}

// Non-bubbling events: use capture phase
// parent.addEventListener('focus', fn, { capture: true })
Follow-up Questions
  1. Which events do not bubble and therefore cannot use delegation?
  2. How does React's SyntheticEvent system relate to event delegation?
  3. How would you delegate a non-bubbling event like focus? (use capture phase)
  4. What is the performance difference between 1000 listeners vs 1 delegated listener?
Memory Trick: "One listener to rule them all. Parent listens, e.target tells you which child. React does this automatically — you write per-element handlers and React batches them."
Summary
  • Attach one listener to parent instead of many to children
  • Uses event bubbling — e.target identifies the origin element
  • Handles dynamically added children without re-attaching listeners
  • React SyntheticEvent uses delegation internally
  • Non-bubbling events need capture phase: { capture: true }

Explain Execution Context and the Call Stack
Advanced P1
Short Answer

The Execution Context is the environment in which JavaScript code is evaluated. Every time a function is called, a new execution context is created and pushed onto the Call Stack. Each context has two phases: creation (hoisting, scope chain, this binding) and execution (code runs line by line). When the function returns, its context is popped off.

Easy Explanation

Stack of plates. Program starts with one plate (global context). Call a function, put a new plate on top. If that function calls another, another plate on top. Function finishes, plate removed. Only the top plate is active. Too many plates = stack overflow.

Real-World Example

Recursion: each call creates a new context — no base case = RangeError: Maximum call stack size exceeded. Error stack traces show the call stack at crash time. Async callbacks do not go on the stack directly — they wait in queues until the stack is empty.

Why Asked

This is the foundation for understanding hoisting, closures, this, scope chains, and the event loop. Without it, you are memorizing rules without understanding why they exist.

Senior Insight

The creation phase is why hoisting works: during creation, all variable declarations are registered (var = initialized to undefined, let/const = uninitialized/TDZ), function declarations are fully hoisted with their bodies. Understanding this phase explains every "why?" moment in JavaScript.

JavaScript — Execution Context Phases
// Call Stack in action
function outer() {
  function inner() { console.log('inner'); }
  inner();  // context pushed/popped
}
outer();      // context pushed/popped

// Stack: [Global] -> [outer()] -> [inner()] -> [outer()] -> [Global]

// Creation phase (happens first, before any code runs):
//   1. Variable declarations hoisted (var = undefined, let = TDZ)
//   2. Function declarations hoisted entirely (name + body)
//   3. Scope chain established, this binding determined

// Execution phase:
//   5. Code runs line by line, assignments execute

// Stack overflow in recursion
function infinite() { return infinite(); }
// infinite(); // RangeError: Maximum call stack size exceeded

// Async — same stack model, different timing
console.log('1');
setTimeout(() => console.log('2'), 0);
console.log('3');
// Output: 1, 3, 2 — setTimeout callback only runs when stack is empty
Follow-up Questions
  1. What is stored in Variable Environment vs Lexical Environment?
  2. How does the call stack relate to the error stack trace?
  3. What happens to the call stack during async/await?
  4. How do closures keep their variable environment alive after the function returns?
Memory Trick: "Stack of plates = call stack. Creation phase = setting the table (hoisting, scope, this). Execution phase = eating (code runs). Async callbacks wait until table is cleared (stack empty)."
Summary
  • Execution Context = environment for executing JS code (global, function, eval)
  • Call Stack = LIFO data structure tracking active contexts
  • Creation phase: hoisting, scope chain, this binding, memory allocation
  • Execution phase: code runs, assignments happen, functions invoked
  • Async callbacks only execute when call stack is empty (event loop)

Deep Clone vs Shallow Clone
Intermediate P1
Short Answer

Shallow clone copies only top-level properties — nested objects/arrays are shared by reference. Deep clone recursively copies all nested values, creating a completely independent copy. Shallow cloning is fast and sufficient for flat React state updates; deep cloning is needed for deeply nested data.

Easy Explanation

Shallow clone = photocopying the cover of a book but not the pages — pages are shared. Deep clone = photocopying every single page — the two books are completely independent.

Real-World Example

React state: setUser({...user, name: 'New'}) — shallow is enough (only changing top-level). Redux reducers: spread at each nesting level being modified. Anti-pattern: deep cloning in every setState (unnecessary re-renders).

Why Asked

Mutating state bugs (accidentally sharing nested references) are some of the hardest to debug. Understanding shallow vs deep cloning shows you know how to handle immutability correctly.

Common Mistakes

Using JSON.parse(JSON.stringify(obj)) as universal deep clone — it silently drops undefined, functions, Symbols, Dates (become strings), Maps, Sets, and circular references.

JavaScript — Shallow vs Deep Clone
const obj = { a: 1, b: { c: 2 } };

// Shallow clone methods
const spread = { ...obj };           // shallow — b.c is shared
const assign = Object.assign({}, obj); // shallow
spread.b.c = 99;
obj.b.c; // 99 — mutated! Both point to same nested object

// Deep clone — structuredClone (modern, built-in)
const deepStructured = structuredClone(obj);
deepStructured.b.c = 42;
obj.b.c; // 2 — unchanged, fully independent copy

// structuredClone handles:
// OK: Dates, Maps, Sets, RegExp, ArrayBuffer, Blob
// NO: Functions, Symbols, DOM nodes, class instances

// JSON.parse(JSON.stringify()) — lossy, avoid for complex data
const data = { date: new Date(), fn: function() {}, undef: undefined };
const jsonClone = JSON.parse(JSON.stringify(data));
// { date: '2024-...' } — fn, undef gone, date is string!

// Custom deep clone with circular reference handling
function deepClone(obj, seen = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj;
  if (seen.has(obj)) return seen.get(obj); // circular ref
  const clone = Array.isArray(obj) ? [] : {};
  seen.set(obj, clone);
  for (const key in obj) {
    if (Object.hasOwn(obj, key)) clone[key] = deepClone(obj[key], seen);
  }
  return clone;
}
Follow-up Questions
  1. Implement structuredClone polyfill using recursion and a WeakMap.
  2. Why cannot structuredClone clone functions? (Not serializable in structured clone algorithm)
  3. How does Immer (Redux Toolkit) handle immutability without deep cloning?
  4. What is the performance cost of deep clone vs shallow spread for a 10-level nested object?
Memory Trick: "Spread is shallow — one level deep. structuredClone is the real deal. JSON clone is the cheap hack that breaks on dates, functions, and maps. React: shallow is enough 95% of the time."
Summary
  • Shallow: {...obj}, Object.assign() — copies top-level, nested = shared refs
  • Deep: structuredClone() (modern), recursion, lodash _.cloneDeep
  • structuredClone handles Dates, Maps, Sets, circular refs — but not functions
  • JSON.parse(JSON.stringify()) is lossy — avoid for anything beyond simple data
  • React: shallow spread at the nesting level being modified is preferred

Splice vs Slice — What is the difference?
Beginner P2
Short Answer

splice() mutates the original array — it adds, removes, or replaces elements in-place and returns the removed elements. slice() is immutable — it returns a shallow copy of a portion without modifying the original. For React: always use slice (or spread + filter) to maintain immutability.

JavaScript — Splice vs Slice
const arr = [1, 2, 3, 4, 5];

// splice(start, deleteCount, ...items) — MUTATES
const removed = arr.splice(2, 1, 99);
// removed = [3], arr = [1, 2, 99, 4, 5] arrow mutated!

// slice(start, end) — IMMUTABLE
const copy = arr.slice(1, 3); // [2, 99] — original unchanged

// React: remove item immutably
// arr.splice(index, 1) — mutates, React will not detect change
const newArr = [...arr.slice(0, index), ...arr.slice(index + 1)];
// Key: slice is read-only, splice is read-write-delete
Key Points
  • splice(i, n, ...items): mutates, removes n items at i, inserts items, returns removed
  • slice(i, j): immutable, returns copy from i to j (exclusive), original untouched
  • React: NEVER use splice on state arrays — always create new references
  • Both work on strings too (slice creates substring; splice does not exist on strings)

localStorage vs sessionStorage vs Cookies
Beginner P2
Short Answer

localStorage: persists indefinitely until explicitly cleared, ~5MB, accessible from any tab of same origin. sessionStorage: cleared when tab/window closes, ~5MB, isolated per tab. Cookies: sent with every HTTP request to same domain, ~4KB, support expiration and HttpOnly/Secure flags — crucial for auth. All are synchronous APIs.

JavaScript — Storage Options
// localStorage — persists across sessions, 5MB
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme');

// sessionStorage — dies on tab close, survives refreshes
sessionStorage.setItem('form-draft', JSON.stringify(formData));

// Cookies — sent with every HTTP request, 4KB
document.cookie = 'token=abc; max-age=3600; Secure; SameSite=Strict';

// React: sync state with localStorage
const [theme, setTheme] = useState(() =>
  localStorage.getItem('theme') || 'light'
);
useEffect(() => { localStorage.setItem('theme', theme); }, [theme]);

// For auth tokens: prefer HttpOnly cookies (XSS-safe) over localStorage
Key Points
  • localStorage: 5MB, infinite persistence, same-origin, synchronous, string-only
  • sessionStorage: 5MB, tab-lifetime, isolated per tab, good for form drafts
  • Cookies: 4KB, sent on every request, HttpOnly for auth, Secure for HTTPS
  • Auth tokens: prefer HttpOnly cookies (XSS-safe) over localStorage (vulnerable)
  • For large data: use IndexedDB; for cache: use Cache API or Service Worker

WeakMap vs Map — When to use which?
Advanced P2
Short Answer

Map: keys can be any type, iterable, holds strong references (prevents GC). WeakMap: keys must be objects, not iterable, holds weak references — if the key object becomes unreachable elsewhere, it is garbage collected. WeakMap is perfect for private data, caching, and DOM metadata — where you do not want to force objects to stay alive.

JavaScript — Map vs WeakMap
// Map: any key type, iterable, strong references
const map = new Map();
map.set('name', 'Alice');
map.set({ id: 1 }, 'metadata');
map.forEach((v, k) => console.log(k, v)); // iterable
map.clear();

// WeakMap: object keys only, not iterable, weak references
const wm = new WeakMap();
let obj = { id: 42 };
wm.set(obj, 'secret');
wm.get(obj); // 'secret'
obj = null; // obj is GC'd — WeakMap entry disappears too

// React internals: Fiber uses WeakMap for node metadata
// Pattern: private data with WeakMap
const _private = new WeakMap();
class Person {
  constructor(name, ssn) { _private.set(this, { name, ssn }); }
  getName() { return _private.get(this).name; }
  // ssn is not accessible from outside
}
Key Points
  • Map: strong refs, iterable, any key type, .size, .forEach()
  • WeakMap: weak refs (GC-friendly), object keys only, no iteration, no .size
  • WeakMap will not prevent garbage collection — use for caching, private data, DOM metadata
  • React internals use WeakMap for Fiber node metadata (no memory leaks)
  • No .clear() on WeakMap — entries disappear when keys are GC'd

Object.freeze vs Object.seal vs Object.preventExtensions
Intermediate P2
Short Answer

Three levels of object immutability: preventExtensions (no new properties), seal (no add/delete, existing properties writable/configurable), freeze (no add/delete/modify — fully immutable at top level). All are shallow — nested objects are NOT affected. All are irreversible.

JavaScript — Freeze, Seal, preventExtensions
const obj = { name: 'Alice', meta: { city: 'NYC' } };

// preventExtensions — no new properties
Object.preventExtensions(obj);
obj.newProp = 1;    // silently fails (TypeError in strict)
obj.name = 'Bob';     // OK — existing props still writable
delete obj.name;       // OK — can still delete

// seal — no add, no delete, existing props still writable
Object.seal(obj);
obj.newProp = 1;    // silently fails
delete obj.name;       // silently fails
obj.name = 'Charlie';  // OK — existing props writable
Object.isSealed(obj);    // true

// freeze — no add, no delete, no modify (top-level)
Object.freeze(obj);
obj.name = 'Dave';           // silently fails
obj.meta.city = 'LA';       // THIS WORKS — freeze is shallow!
Object.isFrozen(obj);          // true

// All three silently fail (no error) unless in strict mode
// Redux Toolkit uses freeze in dev to catch accidental mutations
Key Points
  • preventExtensions: blocks new props, allows modify + delete
  • seal: blocks add + delete, allows modify (makes props non-configurable)
  • freeze: blocks add + delete + modify, props non-writable + non-configurable
  • ALL are shallow — nested objects remain mutable
  • All are irreversible and silently fail unless in strict mode

ES Modules vs CommonJS
Intermediate P2
Short Answer

CommonJS (CJS): require()/module.exports, synchronous, runtime resolution, dynamic, Node.js default. ES Modules (ESM): import/export, statically analysable (enables tree shaking), asynchronous, runs in strict mode automatically. ESM is the modern standard; CJS is legacy but still ubiquitous in Node.js.

JavaScript — CJS vs ESM
// CommonJS (CJS)
const express = require('express');   // synchronous, runtime
const { sum } = require('./math.js');
module.exports = { sum, PI: 3.14 };

// Dynamic require — cannot be tree-shaken
const mod = require(condition ? './a' : './b');

// ES Modules (ESM) — package.json needs "type": "module"
import express from 'express';
import { sum, multiply } from './math.js'; // named import => tree-shakable
export const PI = 3.14;
export default function sum(a, b) { return a + b; }

// Dynamic import — async, returns Promise
const mod = await import(condition ? './a.js' : './b.js');

// ESM: imports are hoisted, strict mode by default
// ESM: statically analysable => tree shaking possible
// CJS: exports are copies, ESM: exports are live bindings
Key Points
  • CJS: require() sync, runs at require-time, no tree shaking, Node.js default
  • ESM: import/export async, statically analysable, tree-shakable, strict mode
  • Tree shaking: bundlers can eliminate unused ESM exports
  • CJS require() can be called conditionally; ESM import must be at top level
  • Dynamic import() works in both but returns a Promise in ESM
  • React apps: always use ESM for tree shaking and modern tooling

Rapid Fire Questions

10 quick Q&A — the ones that catch you off guard. Read them the morning of your interview.

RF1
What is the difference between null and undefined?

undefined means a variable has been declared but not assigned. null is an intentional assignment representing "no value." typeof null returns "object" — a famous JS bug. null == undefined is true, but null === undefined is false.

RF2
What is the output of typeof NaN?

"number". NaN stands for "Not-a-Number" but is technically of type number. It is the only JavaScript value not equal to itself. Use Number.isNaN() (not isNaN()) for reliable checks: Number.isNaN(NaN) === true, Number.isNaN("hello") === false.

RF3
What is the difference between function declaration and function expression?

Function declarations (function foo() {}) are hoisted entirely — you can call them before the line they are defined. Function expressions (const foo = function() {}) are NOT hoisted — the variable is hoisted as undefined (or TDZ for let/const), so calling before assignment throws an error.

RF4
How does optional chaining (?.) work?

obj?.prop returns undefined if obj is null or undefined, instead of throwing a TypeError. Works for properties (user?.address?.city), methods (obj.method?.()), and arrays (arr?.[0]). Essential for safely accessing deeply nested API data in React.

RF5
What does "use strict" do?

Enables strict mode: eliminates silent errors by throwing exceptions, fixes mistakes that make optimizations difficult, and prohibits syntax likely to be defined in future ECMAScript. Prevents accidental globals, makes this undefined in functions, disallows duplicate parameter names, and more. ESM is always strict by default.

RF6
What is the difference between for...in and for...of?

for...in iterates over enumerable property keys (including inherited ones — use hasOwnProperty to filter). for...of iterates over values of iterable objects (arrays, strings, Maps, Sets, generators). for...in on arrays gives indices (strings!), for...of gives actual values.

RF7
What are IIFEs and why were they used?

Immediately Invoked Function Expressions: (function() { /* code */ })(). They created a private scope before ES6 modules and block-scoped let/const existed — preventing variable leakage into the global scope. Popular in the jQuery era. Today mostly replaced by modules and block scope, but still useful for async IIFEs: (async () => { await fetch(); })().

RF8
What is a Polyfill?

A polyfill is code that implements a modern feature on older browsers that do not natively support it. Example: Promise.allSettled polyfill for IE11, Array.prototype.flat for older Safari. Tools like core-js and babel/preset-env automate polyfill injection based on your browser targets.

RF9
What is the difference between document.readyState and DOMContentLoaded?

DOMContentLoaded fires when HTML is fully parsed and the DOM is ready — but before stylesheets, images, and subframes finish loading. load fires when everything (images, styles, frames) is fully loaded. document.readyState can be "loading", "interactive" (same timing as DOMContentLoaded), or "complete" (same as load).

RF10
How do you check if an object is an array?

Use Array.isArray(value) — it is the most reliable method and works across iframes. value instanceof Array fails across different JavaScript realms (like iframes). Object.prototype.toString.call(value) === '[object Array]' also works but is verbose. Always prefer Array.isArray().

RF11
What are Generator Functions and when would you use them?

Generator functions (function* () { yield value; }) can pause execution with yield and resume later, maintaining their state across pauses. They produce iterators that can be consumed with for...of or the spread operator. Real uses: infinite data streams (paginated API with auto-next), state machines (wizard steps), custom iterables (tree traversal without recursion), and async flow control (redux-saga). Asked frequently in senior frontend loops — Deloitte, Amazon, and Google have all asked this in 2025-2026.

RF12
Why were arrow functions introduced? How are they different from regular functions?

Arrow functions (() => {}) provide: (1) Lexical this — they don't bind their own this, instead inheriting from the enclosing scope, solving the classic var self = this pattern. (2) Implicit return — concise one-liners. (3) No arguments object — use rest params instead. (4) Cannot be used as constructors — no new keyword. Use arrow functions for callbacks, event handlers, and array methods. Use regular functions for methods that need dynamic this (object methods, class constructors). Asked at Deloitte 2026, multiple LinkedIn reports.

RF13
How do you cancel an in-flight API call?

Use AbortController: create a controller (const controller = new AbortController()), pass { signal: controller.signal } to fetch, and call controller.abort() when needed — the fetch promise rejects with AbortError. Essential for cleanup in useEffect (unmount cancels request), search-as-you-type (previous request aborted on new input), and race conditions (stale responses ignored). Axios supports the same pattern via CancelToken (deprecated) or signal (modern). Rated "common" by Capgemini and Swiggy interview reports 2025-2026.

RF14
What are the different callback queues in the Event Loop? Which has highest priority?

Three queues: Microtask queue (Promise.then/catch/finally, MutationObserver, queueMicrotask) — highest priority, drained completely after every macrotask before rendering. Macrotask queue (setTimeout, setInterval, setImmediate, I/O, UI rendering events). Animation frame queue (requestAnimationFrame) — runs before rendering but after microtasks. Order: 1 macrotask → all microtasks → rAF → render → repeat. This microtask/macrotask ordering is one of the most commonly tested output-based concepts. Asked at Deloitte 2026, multiple FAANG screens.

RF15
What will this output? — Classic event loop + promise + timeout puzzle

console.log(1); setTimeout(() => console.log(2), 0); Promise.resolve().then(() => console.log(3)); console.log(4);
Output: 1, 4, 3, 2. Synchronous code first (1, 4), then microtasks (Promise.then = 3), then macrotasks (setTimeout = 2). This exact question — or variations mixing async/await, setTimeout, and Promise chains — appears in nearly every frontend interview loop. Practice: "sync first, microtask second, macrotask third." Reported in EY, Deloitte, Primathon, Swiggy, and MakeMyTrip interview experiences 2025-2026.

RF16
How does JavaScript memory management work? What is the Mark-and-Sweep algorithm?

JavaScript uses automatic memory management via garbage collection. The Mark-and-Sweep algorithm: (1) The GC starts from root objects (global `window`/`global`, DOM tree, stack variables) and "marks" all objects reachable from them. (2) Unmarked objects (unreachable) are "swept" — memory reclaimed. Memory leaks happen when objects are still referenced (thus reachable) but no longer needed — e.g., uncleaned event listeners, detached DOM nodes, closures holding large data, and forgotten `setInterval` references. WeakMap/WeakSet hold weak references that don't prevent GC — ideal for DOM metadata and caches. Browser DevTools Memory tab (heap snapshots, allocation timelines) is how you debug leaks. This question is increasingly asked at senior levels — Mavis Digital 2026, Google Frontend Engineer guide 2026.

RF17
What is the difference between structuredClone, JSON.parse(JSON.stringify()), and a manual deep clone?

structuredClone(value) is the modern native Web API — handles Map, Set, Date, RegExp, ArrayBuffer, circular references, and transfers MessagePort/ImageBitmap. Cannot clone functions, DOM nodes, or WeakRefs. Fastest built-in option. JSON.parse(JSON.stringify(obj)) is the legacy approach — loses functions, undefined, Symbol, Date (becomes string), Map/Set (become empty objects), circular refs (throws). Senior-level tip: Prefer structuredClone everywhere it's supported (all modern browsers since 2022). Only implement manual deep clone when you need to handle functions, custom class instances, or non-transferable types. 2026 trend: interviewers ask this to test whether you know the native API vs. still reaching for JSON hacks.
