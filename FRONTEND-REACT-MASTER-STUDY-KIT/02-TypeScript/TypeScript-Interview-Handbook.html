Interface vs Type Alias — When to use each in React?
Intermediate P1
Short Answer

Both describe object shapes, but with key differences: Interface supports declaration merging (useful for library augmentation), extends via extends, and is preferred for public API types. Type Alias is more flexible — it can represent unions, intersections, primitives, tuples, and mapped types. For React props: use interface by default, type when you need unions or computed types.

Easy Explanation

Interface is like a contract that can be amended later (someone can add more terms). Type is like a snapshot — once created, it is immutable. Interfaces play well with OOP patterns (extends); types excel at functional/composition patterns (unions, intersections).

Real-World Example

React component props: the React community convention is to use interface Props { ... }. Union types for state: type Status = 'loading' | 'success' | 'error' — interfaces cannot express this. Intersection for composing types: type AdminUser = User & { role: 'admin' }.

Why Asked

Interviewers want to see you understand the practical tradeoffs, not just memorize differences. This question tests whether you have built real TypeScript applications.

Common Mistakes

Always using type for everything or always using interface. Not knowing that interfaces can be merged (useful for augmenting third-party types). Using type where declaration merging would be beneficial (like extending Window or Express types).

Senior Insight

TypeScript's own performance differs: interfaces are checked by name (faster for complex object types), while types are checked by structure. For large codebases, prefer interfaces for object shapes and types for unions/intersections. React's type definitions use interfaces for props, state, and context.

TypeScript — Interface vs Type
// Interface: best for object shapes, extendable
interface UserProps {
  name: string;
  age: number;
  email?: string; // optional
}

// Declaration merging — only interfaces can do this
interface Window {
  // augment built-in Window type
  analytics: { track(event: string): void };
}

// Type: best for unions, intersections, primitives, tuples
type Status = 'loading' | 'success' | 'error';     // union — interface cannot do this
type StringOrNum = string | number;                // primitive union
type Point = [number, number];                       // tuple
type AdminUser = User & { role: 'admin' };         // intersection

// React component props — community convention: interface
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant: 'primary' | 'secondary' | 'ghost';
  isLoading?: boolean;
}
const Button: React.FC<ButtonProps> = ({ variant, isLoading, ...rest }) => {
  return <button {...rest} disabled={isLoading} />;
};
Follow-up Questions
  1. How does declaration merging work and when would you use it?
  2. Can a type alias extend an interface? Can an interface extend a type?
  3. Why does the React community prefer interface for props?
  4. What happens if you try to merge two types with the same name?
Memory Trick: "Interface = contract you can amend. Type = snapshot, frozen. If it looks like an object shape and might be extended -> interface. If it is a union, tuple, or primitive -> type."
Summary
  • Interface: object shapes, declaration merging, extends, preferred for React props
  • Type: unions, intersections, tuples, primitives, mapped types, conditional types
  • Interfaces are checked by name (faster); types by structure
  • Both can extend each other (type can extend interface, interface can extend type)
  • Default: interface for objects, type for everything else

Explain Generics in TypeScript — with React examples
Advanced P1
Short Answer

Generics allow you to write functions, classes, and types that work with any data type while preserving type safety. Instead of using any (which loses type info), generics capture the type at the call site and carry it through, giving you autocompletion and type checking. The classic example is an identity function: function identity<T>(arg: T): T { return arg; }.

Easy Explanation

Think of generics as a "type variable" — like a function parameter, but for types. When you call identity("hello"), TypeScript fills in T = string. The function now knows it receives and returns a string. Compare to any: with generics you keep type information; with any you throw it away.

Real-World Example

React: generic components (<Select<T> options={...} />), generic hooks (useFetch, useLocalStorage), generic utility functions (debounce with preserved types), API response wrappers, and strongly-typed event handlers.

Why Asked

Generics are the gateway to advanced TypeScript. If you understand generics, you can read and write library-grade type definitions. Without them, you are stuck writing any and losing type safety.

Common Mistakes

Over-complicating with too many type parameters. Using any inside generic functions when unknown or proper constraints would work. Not constraining generics when needed (leading to runtime errors). Confusing generic types with generic components in React.

TypeScript — Generics in React
// Basic generic: identity function
function identity<T>(arg: T): T { return arg; }
const str = identity('hello'); // T = string
const num = identity(42);     // T = number

// Generic constraints — restrict what T can be
function getLength<T extends { length: number }>(arg: T): number {
  return arg.length;
}
getLength('hello');  // 5 — OK
getLength([1, 2]);   // 2 — OK
// getLength(123);    // Error: number doesn't have .length

// Generic React component — type-safe Select
interface SelectProps<T> {
  options: T[];
  value: T;
  onChange: (value: T) => void;
  getLabel: (option: T) => string;
}
function Select<T>({ options, value, onChange, getLabel }: SelectProps<T>) {
  return options.map(opt => (
    <option
      selected={opt === value}
      onClick={() => onChange(opt)}
    >{getLabel(opt)}</option>
  ));
}

// Generic hook — typed useLocalStorage
function useLocalStorage<T>(key: string, initial: T): [T, (val: T) => void] {
  const [value, setValue] = useState<T>(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initial;
  });
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);
  return [value, setValue];
}
// Usage: const [theme, setTheme] = useLocalStorage('theme', 'light');
// theme is typed as string, not any
Follow-up Questions
  1. What is the difference between <T> and <T extends SomeType>?
  2. Can you have generic default values? (<T = string>)
  3. How do generics work with arrow functions in .tsx files? (The <T extends unknown> trick)
  4. How would you type a generic useFetch hook?
Memory Trick: "Generics = type parameters. Like function params, but for types. T is the conventional name (Type). In .tsx files, add extends unknown to avoid JSX parsing ambiguity."
Summary
  • Generics preserve type information through functions, classes, and types
  • Constraints (extends) limit what types are accepted
  • React: generic components, hooks, event handlers
  • In TSX files, use <T extends unknown> for arrow function generics
  • Multiple generics: function pair<K, V>(key: K, value: V)

Explain Utility Types — Partial, Pick, Omit, Record, ReturnType
Intermediate P1
Short Answer

TypeScript's built-in utility types transform existing types without rewriting them. Partial<T> makes all properties optional. Pick<T, K> selects specific properties. Omit<T, K> excludes specific properties. Record<K, V> creates an object type with keys K and values V. ReturnType<T> extracts the return type of a function. These are essential for React: form state (Partial), API responses (Pick), component refactoring (Omit), and hook return types (ReturnType).

Easy Explanation

Partial = "every field is now optional" — perfect for form drafts where not all fields are filled yet. Pick = "I only want these columns" — like selecting specific columns from a table. Omit = "remove these columns" — like deleting columns. Record = "create a lookup table" — like building a dictionary. ReturnType = "what does this function give back?" — useful when wrapping existing functions.

Real-World Example

Update forms: Partial<User> allows submitting only changed fields. API responses: Pick<User, 'id' | 'name'> for a user list endpoint. React component props extending HTML: Omit<ButtonHTMLAttributes, 'type'>. Type-safe reducers: Record<ActionType, (state) => state>. Extracting hook return types for context values.

Why Asked

Utility types are the most used TypeScript feature in real React codebases. Not knowing them means writing duplicate types constantly.

TypeScript — Utility Types in React
interface User {
  id: number;
  name: string;
  email: string;
  role: 'admin' | 'user';
  createdAt: Date;
}

// Partial — all optional (form state before submission)
type UserForm = Partial<User>;
const draft: UserForm = { name: 'Alice' }; // OK — no other fields required

// Pick — select specific fields (API response for list view)
type UserCard = Pick<User, 'id' | 'name' | 'role'>;

// Omit — exclude specific fields (remove sensitive data)
type PublicUser = Omit<User, 'email' | 'createdAt'>;

// Record — typed lookup objects (Redux action handlers)
type StatusLabel = Record<'loading' | 'success' | 'error', string>;
const labels: StatusLabel = {
  loading: 'Loading up...',
  success: 'Done!',
  error: 'Something went wrong',
};

// ReturnType — extract return type of hooks/functions
type ThemeFromHook = ReturnType<typeof useLocalStorage<string>>;
// ThemeFromHook = [string, (val: string) => void]

// React: component with Omit (replace HTML attributes)
interface InputProps extends Omit<React.InputHTMLAttributes<HTMLInputElement>, 'size'> {
  size: 'sm' | 'md' | 'lg'; // own size with different values
}
Follow-up Questions
  1. What is the difference between Pick and Omit in terms of maintainability?
  2. How would you implement Partial<T> as a custom mapped type?
  3. What does Required<T> do? What about Readonly<T>?
  4. When is Record<string, T> better than { [key: string]: T }?
Memory Trick: "Partial = optional. Pick = select columns. Omit = delete columns. Record = key-value map. ReturnType = function's output type. All save you from rewriting type definitions."
Summary
  • Partial<T>: all properties optional — forms, updates
  • Pick<T, K>: select specific properties — API responses, list views
  • Omit<T, K>: exclude properties — strip sensitive fields, override HTML attrs
  • Record<K, V>: typed lookup objects — reducers, configuration maps
  • ReturnType<T>: extract function return type — hook types, factory functions

What are Discriminated Unions? Exhaustive checking in React state
Advanced P1
Short Answer

A discriminated union (or tagged union) is a union type where each member has a common literal property (the discriminant) that TypeScript can use to narrow the type. By checking the discriminant, TypeScript automatically narrows to the specific variant, enabling exhaustive checking — the compiler ensures you handle every case. In React, this is the gold standard for modeling async state (loading/success/error) and complex component variants.

Easy Explanation

Imagine a package delivery. All packages have a "type" label. Opening a "Document" package means you know exactly what is inside (papers). Opening a "Fragile" package means something different. By checking the label (discriminant), you know what to expect inside (narrowed type). If you forget to handle a package type, TypeScript yells at you.

Real-World Example

Async state in React: { status: 'idle' } | { status: 'loading' } | { status: 'success', data: T } | { status: 'error', error: Error }. Redux actions: | { type: 'ADD_TODO', text: string } | { type: 'TOGGLE_TODO', id: number }. Modal variants: | { variant: 'confirm', onConfirm: () => void } | { variant: 'alert', message: string }.

Why Asked

This pattern eliminates entire categories of bugs — impossible states become unrepresentable. Interviewers at companies with large codebases (FAANG) ask this because it is how they model state.

Senior Insight

The never type is the key to exhaustive checking: in the default case of a switch, assign the value to a never type variable. If any case is unhandled, TypeScript will error. This is called the "exhaustiveness check pattern" and catches bugs at compile time when you add new union variants.

TypeScript — Discriminated Unions in React
// Async state — the canonical React example
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

function UserProfile() {
  const [state, setState] = useState<AsyncState<User>>({ status: 'idle' });

  switch (state.status) {
    case 'idle':    return <p>Click to load</p>;
    case 'loading': return <Spinner />;
    case 'success': return <UserCard user={state.data} />; // data is typed!
    case 'error':   return <ErrorMessage error={state.error} />;
    default: {
      // Exhaustive check — compiler errors if we miss a case
      const _exhaustive: never = state;
      return _exhaustive;
    }
  }
}

// Action type pattern — each action has a type discriminant
type TodoAction =
  | { type: 'ADD_TODO'; text: string }
  | { type: 'TOGGLE_TODO'; id: number }
  | { type: 'DELETE_TODO'; id: number }
  | { type: 'CLEAR_COMPLETED' };

function todoReducer(state: Todo[], action: TodoAction): Todo[] {
  switch (action.type) {
    case 'ADD_TODO':       return [...state, { id: Date.now(), text: action.text, done: false }];
    case 'TOGGLE_TODO':    return state.map(t => t.id === action.id ? { ...t, done: !t.done } : t);
    case 'DELETE_TODO':    return state.filter(t => t.id !== action.id);
    case 'CLEAR_COMPLETED': return state.filter(t => !t.done);
  }
}
// If we add a new action type, TypeScript forces us to handle it here
Follow-up Questions
  1. How does the never check ensure exhaustive matching?
  2. Can you use a discriminated union without a type field? (Yes, any literal property works: kind, status, variant)
  3. How would you model a multi-step form wizard with discriminated unions?
  4. What is the advantage over using boolean flags like isLoading + isError + data?
Memory Trick: "One status field to rule them all. Check it -> TypeScript narrows -> impossible states become impossible. The never check in the default case is your compile-time safety net."
Summary
  • Discriminant = a shared literal property (type, status, kind)
  • TypeScript narrows automatically when you check the discriminant
  • Exhaustive checking via never in the default case catches missing variants
  • React: async state, action types, modal variants, form steps
  • Eliminates entire class of bugs — impossible states are literally unrepresentable

Type Guards and Narrowing in TypeScript
Intermediate P1
Short Answer

Type narrowing is how TypeScript reduces a broad type to a more specific one based on runtime checks. Type guards are the mechanisms: typeof (primitives), instanceof (classes), in operator (property existence), equality checks, discriminant property checks, and custom type predicates (arg is Type). After a successful guard, TypeScript narrows the type within that branch.

Easy Explanation

TypeScript starts with a broad assumption about a value's type (e.g., string | number). When you write if (typeof x === 'string'), TypeScript says "inside this if-block, I know x is a string." That is narrowing — you proved what type it is, so TypeScript treats it as that type going forward.

Real-World Example

React: processing form input (Event.target.value), handling API responses (checking shape with in), null checks before rendering (user !== null), union type narrowing in component props, and filtering undefined from arrays (.filter(Boolean) as a type guard).

Why Asked

Without type narrowing, union types are useless. Interviewers want to see that you can safely handle polymorphic data (APIs returning different shapes, component props with multiple variants).

TypeScript — Type Guards & Narrowing
// typeof — narrows primitives
function format(input: string | number): string {
  if (typeof input === 'number') {
    return input.toFixed(2); // input is number here
  }
  return input.toUpperCase();   // input is string here
}

// Custom type predicate — the "is" keyword
interface Cat { meow(): void; lives: number; }
interface Dog { bark(): void; breed: string; }
type Animal = Cat | Dog;

function isDog(animal: Animal): animal is Dog {
  return (typeof animal === 'object') && 'breed' in animal;
}
const pet: Animal = { bark() {}, breed: 'Lab' };
if (isDog(pet)) { pet.bark(); } // narrowed to Dog

// instanceof — narrows class instances
class ApiError extends Error { code: number; }
try { /* ... */ } catch (e) {
  if (e instanceof ApiError) {
    e.code; // typed access to .code
  }
}

// Discriminated union narrowing (most common in React)
type Result<T> = { ok: true; data: T } | { ok: false; message: string };
function handle<T>(result: Result<T>) {
  if (result.ok) { result.data; }     // narrowed to success
  else          { result.message; }    // narrowed to error
}

// Filtering null/undefined with .filter(Boolean)
const items: (string | undefined)[] = ['a', undefined, 'b'];
const filtered: string[] = items.filter((item): item is string => item !== undefined);
Follow-up Questions
  1. How does the is keyword work in a custom type predicate?
  2. What is the difference between typeof narrowing and instanceof narrowing?
  3. Can type guards return false positives? (Yes — they are runtime checks, TypeScript trusts them)
  4. How would you narrow an array of mixed types to only string elements?
Memory Trick: "typeof for primitives, instanceof for classes, is for custom logic, in for properties, discriminant for unions. After the check, TypeScript narrows automatically."
Summary
  • typeof: primitives (string, number, boolean, symbol, undefined, object, function, bigint)
  • instanceof: class instances (Error, custom classes)
  • Custom predicate: arg is Type — return true to narrow
  • in operator: check if property exists on an object
  • Discriminant: check shared literal property to narrow union
  • Truthiness: if (value) removes null and undefined

any vs unknown vs never — Why unknown is better than any
Intermediate P1
Short Answer

any: opt out of type checking entirely — you can do anything with it, no safety. unknown: the type-safe version of any — you CANNOT do anything with it until you narrow it via a type guard. never: the type of values that can never exist — the empty set, used for exhaustive checks and functions that throw/never return.

Easy Explanation

any = "I give up, TypeScript, leave me alone." unknown = "I do not know what this is yet, but I promise to check before using it." never = "This cannot possibly happen — if it does, the universe is broken."

Real-World Example

Parsing JSON responses: JSON.parse() returns any — use unknown instead via a generic wrapper. Error handling: catch (e: unknown) forces you to type-check before accessing properties. React error boundaries: the error type should be unknown, not any. Exhaustive check in switch statements uses never.

Why Asked

Moving from any to unknown is the single biggest maturity indicator in TypeScript developers. It shows you value type safety.

Common Mistakes

Using any as the catch clause error type (catch (e: any)) — it should be unknown. Defaulting to any when unknown with a guard would work. Not understanding that never allows assignment to anything (bottom type).

TypeScript — any vs unknown vs never
// any — complete type escape hatch (DANGEROUS)
let a: any = 42;
a.toUpperCase();     // No error! Crash at runtime
a = 'hello';
const b: string = a; // any infects other types silently

// unknown — type-safe alternative (RECOMMENDED)
let u: unknown = 42;
// u.toUpperCase();   // Error! Must narrow first
if (typeof u === 'string') { u.toUpperCase(); } // OK
// const c: string = u; // Error! unknown not assignable to string

// React: safe JSON parsing with unknown
function parseJSON<T>(json: string, validator: (data: unknown) => data is T): T {
  const data: unknown = JSON.parse(json);
  if (validator(data)) return data;
  throw new Error('Invalid data');
}

// React: proper error handling (since TS 4.0)
try {
  await fetchData();
} catch (e: unknown) {
  if (e instanceof Error) {
    console.log(e.message); // safe — narrowed to Error
  }
}

// never — values that never occur (exhaustive checks)
function assertNever(x: never): never {
  throw new Error(`Unexpected: ${x}`);
}
// never absorbs all types — string | never = string
Follow-up Questions
  1. Why is unknown assignable only to unknown and any?
  2. How does never differ from void? (never = function does not finish, void = returns undefined)
  3. What is the NoInfer utility and how does it relate to unknown?
  4. When would you intentionally use any over unknown?
Memory Trick: "any = party mode (no rules). unknown = quarantine (must test before use). never = void (impossible). Upgrade from any to unknown and your TypeScript maturity doubles."
Summary
  • any: disables type checking — avoid in production, use only for migration boundaries
  • unknown: type-safe any — must narrow before use, ideal for API responses and error handling
  • never: empty set — functions that throw, infinite loops, exhaustive checks
  • unknown is assignable only to unknown and any — not even to string
  • React: use unknown for catch clauses, API responses, and third-party data

as const and satisfies — Modern TypeScript Essentials
Intermediate P1
Short Answer

as const makes a value deeply readonly and narrows its type to literal types. An array becomes a readonly tuple, an object's properties become readonly with literal types. satisfies (TS 4.9+) validates that a value matches a type WITHOUT widening the value's type — you keep the narrower inferred type while ensuring it conforms to the wider one. Both are invaluable for config objects, Redux actions, and React component patterns.

Easy Explanation

as const = "treat this value as the most specific type possible." [1, 2] becomes readonly [1, 2] instead of number[]. satisfies = "check that this fits the shape, but do not forget the details." You get both validation AND precise type inference.

Real-World Example

Redux action constants: const ACTIONS = ['ADD', 'DELETE'] as const creates a 'ADD' | 'DELETE' union. Config objects with satisfies: validate the shape against Record<string, Config> while keeping individual config details. Color palette objects where you want both validation and autocomplete on hex values.

Why Asked

as const and satisfies are relatively new additions that dramatically improve DX. Not knowing them means you write more verbose types and lose type information.

TypeScript — as const & satisfies
// as const — narrow to literal types
const colors = ['red', 'green', 'blue'] as const;
// type: readonly ['red', 'green', 'blue']
type Color = typeof colors[number]; // 'red' | 'green' | 'blue'

// as const on objects — all properties become readonly literals
const config = {
  api: 'https://api.example.com',
  timeout: 5000,
  retries: 3,
} as const;
// type: { readonly api: 'https://api.example.com'; readonly timeout: 5000; ... }

// satisfies — validate without widening (TS 4.9+)
type ColorConfig = Record<string, { hex: string; rgb: string }>;

const palette = {
  red:   { hex: '#FF0000', rgb: 'rgb(255,0,0)' },
  green: { hex: '#00FF00', rgb: 'rgb(0,255,0)' },
} satisfies ColorConfig; // validated but NOT widened

palette.red.hex; // type: '#FF0000' — exact literal, not just string!
// palette.blue // Error — missing from palette

// satisfies with as const — the ultimate combo
const routes = {
  home:    '/',
  about:   '/about',
  profile: '/user/:id',
} as const satisfies Record<string, string>;
// Each value has its literal type, AND all values are validated as strings
type RoutePath = typeof routes[keyof typeof routes]; // '/' | '/about' | '/user/:id'
Follow-up Questions
  1. What is the difference between as const and Object.freeze?
  2. Can satisfies be combined with as const?
  3. How does as const affect arrays differently from objects?
  4. What version of TypeScript introduced satisfies? (4.9)
Memory Trick: "as const = lock it down (readonly + literal types). satisfies = check the shape but keep the details. Combine them: as const satisfies Type = the ultimate type-safe config pattern."
Summary
  • as const: deeply readonly + literal type narrowing for objects, arrays, and primitives
  • satisfies: validate against a type without losing narrower inferred type
  • Perfect combo: as const satisfies Type — gets validation + narrowest types
  • Redux: action type unions from as const arrays
  • Config: satisfies ensures shape while keeping exact values for autocomplete

keyof and Mapped Types — Type-safe object transformations
Advanced P1
Short Answer

keyof T produces a union of all keys in type T — a string literal union of property names. Mapped types ({ [K in keyof T]: NewType }) iterate over keys to create a new type, transforming each property. They are the foundation for almost all utility types (Partial, Required, Readonly, Pick, Record) and enable type-safe object transformations without runtime code.

Easy Explanation

keyof = "give me all the key names as a union." If User has id, name, email, then keyof User = 'id' | 'name' | 'email'. Mapped type = a for-loop over those keys to build a new type: "for each key in User, make it optional" is exactly how Partial<T> works.

Real-World Example

Creating a type-safe form validation schema: { [K in keyof T]: (value: T[K]) => string | null }. Readonly deep: making nested objects immutable. API response wrappers: wrapping each property in { data: T[K]; loading: boolean }. Event handler typing based on component props.

Why Asked

Mapped types are the gateway to understanding how TypeScript's type system is built. Partial, Pick, Record — all utility types are implemented with mapped types. This question separates juniors from seniors.

TypeScript — keyof & Mapped Types
// keyof — union of property names
interface User {
  id: number;
  name: string;
  email: string;
}
type UserKeys = keyof User; // 'id' | 'name' | 'email'

// Generic property access with keyof
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
getProp(user, 'name'); // returns string
getProp(user, 'id');   // returns number
// getProp(user, 'invalid'); // Error!

// Mapped type — iterate over keys, transform each one
type Nullable<T> = { [K in keyof T]: T[K] | null };
type NullableUser = Nullable<User>;
// { id: number | null; name: string | null; email: string | null }

// Built-in Partial is just a mapped type:
// type Partial<T> = { [K in keyof T]?: T[K] };

// React: typed validation schema
type ValidationSchema<T> = {
  [K in keyof T]: (value: T[K]) => string | null;
};
const userValidation: ValidationSchema<User> = {
  id:    (v) => v > 0 ? null : 'Invalid ID',
  name:  (v) => v.length > 0 ? null : 'Name required',
  email: (v) => v.includes('@') ? null : 'Invalid email',
};

// Mapped type with key remapping (TS 4.1+)
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
// Getters<User> = { getId: () => number; getName: () => string; getEmail: () => string }
Follow-up Questions
  1. Implement your own Pick<T, K> using mapped types.
  2. How does key remapping (as NewKey) work in mapped types?
  3. What is the difference between [K in keyof T] and [K in K]?
  4. How would you type an object where every key maps to its own validation function?
Memory Trick: "keyof = key names as a union. Mapped type = for-loop over keys, creating new properties. [K in keyof T]: Transform<T[K]> = the foundation of all utility types."
Summary
  • keyof T: union of all keys in T (string literal union)
  • Mapped type: { [K in keyof T]: NewType } — iterate + transform each property
  • Built-in utility types (Partial, Required, Readonly, Record) are all mapped types
  • Key remapping (TS 4.1+): as NewKey to rename keys during iteration
  • React: type-safe validation schemas, event handler maps, form state types

Typing React Components — Props, useState, useRef, Event Handlers
Beginner P1
Short Answer

React components in TypeScript require typing: props (interface or type with React.FC or direct parameter typing), useState (inferred or explicit generic), useRef (3 overloads: for DOM elements, mutable values, and read-only refs), and event handlers (using React.ChangeEvent, React.MouseEvent, React.FormEvent, etc.). Understanding these patterns prevents the most common React/TypeScript errors.

Easy Explanation

Think of typing React as labeling everything that flows: props come in (label them), state lives inside (label the shape), refs point to things (label what they reference), events carry data (label what triggered them). If everything is labeled, TypeScript catches misalignments before runtime.

Real-World Example

Every React component you build needs typed props. Every form needs typed event handlers. Every hook (useState, useRef, useContext) benefits from explicit typing. Third-party component libraries (MUI, Ant Design) rely on generic component types.

Why Asked

This is the "can you actually build a React app in TypeScript?" question. If you cannot type these patterns, you cannot work on a production React/TS codebase.

TypeScript — Typing React Components
// Props — two approaches (prefer interface)
interface CardProps {
  title: string;
  children: React.ReactNode; // most flexible children type
  onClick?: () => void;
}

// Option A: React.FC (includes children implicitly)
const Card: React.FC<CardProps> = ({ title, children }) => (
  <div><h2>{title}</h2>{children}</div>
);

// Option B: Direct parameter typing (preferred in React 18+)
function Card({ title, children }: CardProps) {
  return <div><h2>{title}</h2>{children}</div>;
}

// useState — inferred is usually enough
const [count, setCount] = useState(0); // inferred: number
const [user, setUser] = useState<User | null>(null); // explicit generic needed for null

// useRef — three overloads
// 1. DOM element ref (read-only)
const inputRef = useRef<HTMLInputElement>(null);
// inputRef.current?.focus(); — current is read-only

// 2. Mutable value ref
const timerRef = useRef<number>(0); // mutable, no re-render
timerRef.current = 42; // OK — writable

// 3. Without initial argument — current is readonly
const ref = useRef<string>(); // current: string | undefined (readonly)

// Event handlers — React provides typed events
const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  e.target.value; // typed as string
};
const handleClick = (e: React.MouseEvent<HTMLButtonElement>) => {
  e.currentTarget; // typed as HTMLButtonElement
};
const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => {
  e.preventDefault();
  // FormData: const data = new FormData(e.currentTarget);
};

// Extending native HTML props
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant: 'primary' | 'secondary';
}

  1. Why is React.FC falling out of favor? (Implicit children, does not work with generics well)
  2. What is the difference between ReactNode, ReactElement, and JSX.Element?
  3. How do you type a useCallback with generic event handlers?
  4. How do you type forwardRef for polymorphic components?
Memory Trick: "Props = interface. useState = inferred or explicit generic for null. useRef = DOM element = readonly, primitive = mutable. Events = React.ChangeEvent/ClickEvent/FormEvent. Extend HTML = extends React.ComponentPropsWithoutRef."
Summary
  • Props: interface with React.FC<Props> or direct parameter typing
  • useState: inferred for simple types, explicit generic for unions with null
  • useRef: HTMLInputElement for DOM, primitive for mutable values
  • Events: React.ChangeEvent<HTMLInputElement>, React.MouseEvent, React.FormEvent
  • Children: React.ReactNode (most flexible), React.ReactElement (specific)

Conditional Types and infer — API response unwrapping
Advanced P1
Short Answer

Conditional types (T extends U ? X : Y) select a type based on a condition — like a ternary for types. The infer keyword captures a type variable within the condition, enabling powerful extraction patterns. Together, they form the basis for utility types like ReturnType, Parameters, Awaited, and custom unwrapping of API responses, React component props, and promise chains.

Easy Explanation

"If this type looks like X, then give me Y, otherwise Z." infer is like saying "if this type matches this pattern, capture that part into a new type variable." Example: "If this is a Promise that resolves to something, give me that something" — that is exactly Awaited<T>.

Real-World Example

Unwrapping Axios/Fetch responses: extracting the data type from AxiosResponse<T>. Extracting component prop types from React.FC<Props>. Unwrapping Promise return types from async functions. Building a typed useQuery hook that infers the data type from the fetcher function.

Why Asked

Conditional types separate TypeScript power users from average developers. They enable writing library-grade type utilities that make entire APIs type-safe with a single type parameter.

TypeScript — Conditional Types & infer
// Basic conditional type — ternary for types
type IsString<T> = T extends string ? 'yes' : 'no';
type A = IsString<string>;  // 'yes'
type B = IsString<number>;  // 'no'

// infer — capture a type out of a pattern
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;
type Result = UnwrapPromise<Promise<string>>; // string
type NotPromise = UnwrapPromise<number>;    // number (falls through)

// Recursive conditional — deeply unwrap (TS 4.1+)
type DeepUnwrap<T> =
  T extends Promise<infer U> ? DeepUnwrap<U> : T;
type Deep = DeepUnwrap<Promise<Promise<string>>>; // string

// React: extract component prop types
type ComponentProps<T> =
  T extends React.ComponentType<infer P> ? P : never;

// React: typed API response unwrapping
interface ApiResponse<T> { data: T; status: number; }
type UnwrapApi<T> = T extends ApiResponse<infer D> ? D : never;

// Distribute over unions — conditional types distribute automatically
type StringOrNumber<T> = T extends string | number ? T : never;
type Filtered = StringOrNumber<string | boolean | number>; // string | number
// Distribution: (string extends S|N ? ...) | (boolean extends S|N ? ...) | (number extends S|N ? ...)
Follow-up Questions
  1. How does conditional type distribution work with union types?
  2. What is the infer keyword and how does it relate to extends?
  3. Can conditional types be recursive? (Yes, since TS 4.1 — but depth limited)
  4. How would you unwrap multiple levels of API response wrapping?
Memory Trick: "T extends Pattern ? TrueType : FalseType = type-level if/else. infer U = extract U from the pattern. Distributive = union input becomes individual checks. Recursive conditional = repeat until base case."
Summary
  • Conditional type: T extends U ? X : Y — type-level ternary
  • infer: captures a type variable from a pattern match
  • Distribution: T extends U distributes over union types automatically
  • Built on this: ReturnType, Parameters, Awaited, Exclude, Extract
  • React: unwrap API responses, extract component props, type query hooks

Readonly and Immutability in TypeScript
Beginner P2
Short Answer

Readonly<T> makes all properties of T readonly (shallow). readonly modifier on individual properties or array types prevents reassignment. as const creates deeply readonly values. For React: Readonly<Props> is standard; useState returns state that should not be mutated directly.

TypeScript — Readonly Patterns
// Readonly utility type (shallow)
interface Config { theme: 'dark' | 'light'; port: number; }
const config: Readonly<Config> = { theme: 'dark', port: 3000 };
// config.theme = 'light'; // Error — read-only at compile time

// readonly arrays — prevent push/pop/splice
const items: readonly string[] = ['a', 'b'];
// items.push('c'); // Error

// DeepReadonly — recursive mapped type
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
Key Points
  • Readonly<T> = shallow readonly utility type
  • readonly T[] = prevents array mutations (push, pop, splice)
  • as const = deeply readonly + literal type narrowing
  • All readonly is compile-time only — no runtime enforcement
  • React: Readonly<Props> is conventional for component props

Enums vs Union Types
Beginner P2
Short Answer

String literal unions (type Status = 'loading' | 'success' | 'error') are simpler, lighter, and produce no runtime code. Enums generate runtime objects, support reverse mapping, and are familiar from Java/C#. The React/TypeScript community strongly prefers string literal unions — they integrate better with the type system and produce smaller bundles.

TypeScript — Enums vs Unions
// String literal union — preferred in modern TS/React
type Status = 'loading' | 'success' | 'error';
// Zero runtime cost — pure type

// Numeric enum (AVOID in most cases)
enum Direction { Up, Down, Left, Right } // Up=0, Down=1, ...
// const enum generates no runtime code but breaks with isolatedModules

// Union with as const — best of both worlds
const SIZES = ['sm', 'md', 'lg'] as const;
type Size = typeof SIZES[number]; // 'sm' | 'md' | 'lg'
// SIZES is a runtime array you can iterate over
Key Points
  • String unions: zero runtime cost, better type integration, community preference
  • Enums: generate runtime code, reverse-mapping, but can bloat bundles
  • const enum: inlined at compile time, but breaks with isolatedModules/Babel
  • Need runtime iteration? Use as const array + typeof[number] pattern

Function Overloads in React
Advanced P2
Short Answer

Function overloads define multiple call signatures for the same function with different parameter/return types. The implementation handles all cases. In React, overloads enable hooks that return different types based on input (useStorage with/without default value) and callback props with varied signatures.

TypeScript — Function Overloads
// Overload signatures (public API)
function getValue(key: string, defaultValue: string): string;
function getValue(key: string): string | undefined;

// Implementation (handles all cases)
function getValue(key: string, defaultValue?: string): string | undefined {
  const val = localStorage.getItem(key);
  return val ?? defaultValue;
}
const a = getValue('theme', 'dark'); // string
const b = getValue('theme');        // string | undefined
Key Points
  • Overload signatures = public API; implementation = hidden, handles all cases
  • React: use for hooks returning different types based on input args
  • Implementation signature must be compatible with ALL overload signatures
  • Often avoidable with generics + conditional types — use overloads sparingly

Type-safe React Context API
Intermediate P2
Short Answer

A type-safe Context requires: a typed value interface, a provider component, and a custom hook wrapping useContext with a null check to enforce provider usage. The custom hook pattern catches the "forgot to wrap in Provider" bug — without it, useContext returns the default value which may be undefined.

TypeScript — Type-safe Context
interface AuthContextType {
  user: User | null;
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}

// Create context with undefined default — force provider usage
const AuthContext = React.createContext<AuthContextType | undefined>(undefined);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const login = async (email: string, password: string) => { /* ... */ };
  const logout = () => { setUser(null); };
  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom hook — enforces provider usage with a runtime check
export function useAuth(): AuthContextType {
  const context = React.useContext(AuthContext);
  if (context === undefined) {
    throw new Error('useAuth must be used within an AuthProvider');
  }
  return context;
}
// Consumer: const { user, login } = useAuth(); — fully typed, never undefined
Key Points
  • Use undefined as default context value to catch missing providers
  • Always export a custom hook that checks for undefined and throws
  • Provider component encapsulates state management logic
  • Catches the "forgot to wrap in Provider" bug at runtime with a clear error

Template Literal Types — CSS-in-JS type safety
Advanced P2
Short Answer

Template literal types (TS 4.1+) use template literal syntax at the type level to construct new string literal types from existing ones. Combined with mapped types and Capitalize, Uppercase, they enable type-safe strings for CSS-in-JS, routing, event names, and API endpoints.

TypeScript — Template Literal Types
// Basic template literal types
type Color = 'red' | 'green' | 'blue';
type Shade = '50' | '100' | '500';
type ColorClass = `text-${Color}-${Shade}`;
// 'text-red-50' | 'text-red-100' | 'text-red-500' | ...

// Intrinsic string manipulation types
type Greeting = 'hello';
type Shout = Uppercase<Greeting>;     // 'HELLO'
type Proper = Capitalize<Greeting>; // 'Hello'

// Event name pattern: onEventName
type Events = { click: void; change: string; focus: void };
type Handlers = {
  [K in keyof Events as `on${Capitalize<string & K>}`]: (e: Events[K]) => void;
};
// { onClick: () => void; onChange: (e: string) => void; onFocus: () => void }
Key Points
  • Construct string literal types using ${Type}` at the type level
  • Intrinsic types: Uppercase, Lowercase, Capitalize, Uncapitalize
  • CSS-in-JS: typed class names (Tailwind, Styled Components)
  • Route params: `/user/${string}` for typed URL patterns
  • TS 4.1+ required; unions in template positions produce cartesian products

Declaration Merging
Intermediate P2
Short Answer

Declaration merging is when TypeScript combines multiple same-named declarations into one. Only interfaces and namespaces merge — type aliases do not. Used for augmenting third-party types (Window, Express Request), organizing large type definitions, and adding properties to library exports.

TypeScript — Declaration Merging
// Interface merging — both declarations combine
interface User { name: string; }
interface User { age: number; }
// Final User: { name: string; age: number }

// Augmenting global Window (common in React)
declare global {
  interface Window {
    __APP_CONFIG__: { apiUrl: string; env: string };
  }
}
// Now window.__APP_CONFIG__ is typed everywhere

// Augmenting Express Request (auth middleware)
declare namespace Express {
  interface Request {
    user?: { id: string; role: string };
  }
}
Key Points
  • Only interfaces and namespaces merge — type aliases produce an error
  • Common uses: augment Window, Express Request, Redux Dispatch, library types
  • Module augmentation: declare module 'some-lib' { interface SomeType {} }
  • Requires declare global for modifying global scope types

tsconfig.json — The important options for React projects
Beginner P2
Short Answer

Most impactful tsconfig.json options for React: strict (enables all strict checks — non-negotiable), target (ES2022+), module (ESNext for bundlers), jsx (react-jsx for React 17+), paths (@/components aliases), strictNullChecks (most impactful single flag), and noUncheckedIndexedAccess.

TypeScript — Essential tsconfig.json for React
{
  "compilerOptions": {
    "strict": true,                     // All strict checks — non-negotiable
    "target": "ES2022",                // Modern JS output
    "module": "ESNext",                // For bundlers (Vite, webpack)
    "moduleResolution": "bundler",   // For Vite, Turbopack
    "jsx": "react-jsx",              // React 17+ JSX transform

    "noUncheckedIndexedAccess": true, // arr[0] might be undefined

  • strictNullChecks: forces null/undefined handling — single most important flag

  • jsx: react-jsx for React 17+ (no more import React needed)
  • moduleResolution: bundler for Vite; node16/nodenext for Node.js

Brand/Nominal Typing — Making primitives unique
Advanced P2
Short Answer

Brand types simulate nominal types in TypeScript's structural system by intersecting a base type with a unique brand property. This prevents accidentally using a string where a UserId is expected. Essential for domain modeling: UserId vs PostId, Email vs string, Meters vs Feet.

TypeScript — Brand Types
// Brand type utility
declare const brand: unique symbol;
type Brand<T, TBrand> = T & { [brand]: TBrand };

// Create branded types
type UserId = Brand<string, 'UserId'>;
type PostId = Brand<string, 'PostId'>;
type Email  = Brand<string, 'Email'>;

// Factory — only way to create branded values
function createUserId(id: string): UserId { return id as UserId; }
function createEmail(email: string): Email {
  if (!email.includes('@')) throw new Error('Invalid email');
  return email as Email;
}

// Type system catches these mistakes
const uid = createUserId('abc');
function getPost(postId: PostId) {}
// getPost(uid);   // Error: UserId is not PostId
// getPost('abc'); // Error: string is not PostId
Key Points
  • TypeScript is structural — brand types add nominal checking
  • Use unique symbol brand to prevent accidental compatibility
  • Great for IDs, validated strings (Email, URL), units (Meters, Feet)
  • Factory functions with validation ensure only valid branded values exist
  • Brands are compile-time only — use classes for runtime enforcement if needed
