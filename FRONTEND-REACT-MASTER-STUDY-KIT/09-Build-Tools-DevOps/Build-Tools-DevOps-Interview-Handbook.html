Vite vs Webpack — When, Why, and How?
Advanced P1
Short Answer

Vite leverages native ES modules in the browser during development — it serves unbundled source code, transforming files on-demand via esbuild. Webpack bundles everything upfront (or through persistent caching). This gives Vite near-instant cold starts and HMR regardless of project size, while Webpack's startup time grows linearly with module count. In production, Vite uses Rollup for bundling; Webpack has its own production pipeline.

Architecture Breakdown

Webpack dev flow: Read all files → resolve dependency graph → bundle everything → serve. Cold start for a large app (3000+ modules) can take 30-60 seconds. HMR is fast on small files but slows as the bundle grows because Webpack must re-bundle affected chunks.

Vite dev flow: Pre-bundle dependencies with esbuild once (fast — esbuild is written in Go, ~100x faster than Babel). Source code is served as individual ESM files via the browser's native import. Each file is transformed on-the-fly by esbuild only when the browser requests it. HMR updates exactly the changed module without re-bundling — sub-50ms updates even in massive projects.

When to Choose What

Choose Vite when: Greenfield React/Vue/Svelte projects, you value developer experience, you're not targeting IE11, you want zero-config startup. Vite is the default for new projects in 2025.

Choose Webpack when: You're maintaining a mature codebase, need advanced code-splitting strategies, have a highly customized build pipeline, need require.context, or work in a large organization with existing webpack customizations. Next.js uses Webpack (or Turbopack) under the hood — you're often already using Webpack without realizing it.

Senior Insight

Vite's "unbundled dev" architecture is the real innovation here, not esbuild speed. The browser-native ESM approach means the dependency graph is inherently incremental — no need to rebuild the world when one file changes. This architectural advantage cannot be replicated by making Webpack's internals faster. Webpack's persistent cache (filesystem cache in v5) gets close to Vite on rebuilds but still pays the initial bundle cost. If you're on Webpack, enabling cache: { type: 'filesystem' } is the single biggest DX improvement you can make.

Configuration Comparison — Vite vs Webpack
// vite.config.js — zero-config philosophy
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: { port: 3000, open: true },
  build: { rollupOptions: { output: { manualChunks: {
    vendor: ['react', 'react-dom']
  }}}}
}); // Done. That's the whole config.

// webpack.config.js — explicit pipeline
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  entry: './src/index.js',
  output: { path: path.resolve(__dirname, 'dist'), filename: '[name].[contenthash].js' },
  resolve: { extensions: ['.js', '.jsx'] },
  module: { rules: [
    { test: /\.jsx?$/, exclude: /node_modules/, use: 'babel-loader' },
    { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    { test: /\.(png|svg)$/, type: 'asset/resource' }
  ]},
  plugins: [new HtmlWebpackPlugin({ template: './public/index.html' })],
  cache: { type: 'filesystem' }    // Critical for DX parity with Vite on rebuilds
};
Pro Tip

You don't have to choose — many teams run Vite for local dev and fall back to Webpack for production builds in CI if they need specific plugins. CRA (Create React App) has been deprecated; the React docs now recommend frameworks like Next.js, Remix, or Vite-based setups.

Tree Shaking and Code Splitting — How Do Bundlers Eliminate Dead Code?
Advanced P1
Short Answer

Tree shaking is dead code elimination at the module level — bundlers analyze the import/export graph and remove code that is never imported. It depends on ES Module static structure (imports/exports are known at parse time, unlike CommonJS require()). Code splitting is the deliberate separation of your bundle into smaller chunks that load on demand, typically at route boundaries or interaction points. Together they minimize both initial and total JavaScript shipped.

How Tree Shaking Works

1. Static analysis: The bundler parses your code, builds a dependency graph from import/export statements. Because ESM imports are static (no dynamic strings), the bundler knows exactly what's used before any code runs.

2. Mark and sweep: Starting from the entry point, the bundler marks every imported function/variable/class as "used." After traversing the entire graph, any export that was never marked is "dead code" and is removed.

3. The sideEffects flag: If your package.json declares "sideEffects": false, the bundler can safely delete entire files that export unused symbols. Without this flag, the bundler must be conservative — a module might execute side effects on import (like polyfills or CSS imports), so it cannot be removed even if no exports are used.

Code Splitting Strategies
StrategyExampleWhen to Use
Route-basedReact.lazy + Suspense on route componentsEvery SPA — the default starting point
Component-basedLazy-load heavy chart library only when tab is openedComponents below the fold or behind interaction
Vendor splittingSeparate chunk for react + react-domLarge dependencies that change infrequently
Dynamic importsimport('./locale/' + lang)Conditional dependencies like locale files
Boundary-basedSuspense boundaries in critical rendering pathsSelective hydration, streaming SSR
Why Tree Shaking Fails (and How to Fix It)

1. CommonJS: require() calls are dynamic — the bundler cannot statically determine what's used. Use ESM everywhere. 2. Side effects in modules: If index.js does import './styles.css', that file has a side effect and cannot be shaken. Mark CSS imports as side effects in package.json. 3. Barrel exports: export * from './module' forces all exports to be evaluated. Name your exports explicitly. 4. Classes with decorators: Babel-compiled decorators often inject runtime helpers that defeat tree shaking. Use SWC or esbuild for cleaner output.

JavaScript — Tree Shaking Patterns vs Anti-patterns
// BAD: Barrel re-exports — everything is imported even if unused
export * from './utils';     // All utils pulled in

// GOOD: Named imports — bundler sees exactly what's needed
export { debounce, throttle } from './utils';

// BAD: Importing entire library
import _ from 'lodash';
_.debounce(fn, 300);            // Ships all 70+ KB of lodash

// GOOD: Direct path import or tree-shakeable named import
import debounce from 'lodash/debounce';
// or if using lodash-es (ESM build):
import { debounce, throttle } from 'lodash-es';

// Route-based code splitting (React)
const Dashboard = React.lazy(() => import('./pages/Dashboard'));
const Settings  = React.lazy(() => import('./pages/Settings'));

// Conditional dynamic import — locale files shipped on demand
async function loadLocale(lang) {
  const messages = await import(`./locales/${lang}.js`);
  return messages.default;
}

// package.json — tell the bundler this package has no side effects
{
  "name": "my-library",
  "sideEffects": false
  // or: "sideEffects": ["*.css", "*.scss"] — CSS imports have side effects
}
FAANG Reality Check

At Netflix scale, the web app ships ~200KB gzipped JavaScript on initial load. Without tree shaking and code splitting, it would be 3-5MB. The technique isn't optional — it's the difference between a 10-second load and a 1-second load on 3G. Google ranks pages by Core Web Vitals; tree shaking and code splitting directly impact your LCP and TBT scores.

  • Tree shaking depends on ESM static imports — use ESM, avoid barrel files
  • Mark "sideEffects": false in package.json for library packages

  • Use bundle analyzer to verify tree shaking worked (don't trust, verify)
  • Dynamic import() creates a new split point — use it for conditional dependencies

Babel and SWC — JavaScript Transpilation Explained
Intermediate P1
Short Answer

Babel is a JavaScript-to-JavaScript compiler written in JavaScript. It uses a parse → transform → generate pipeline with a plugin architecture. SWC (Speedy Web Compiler) is a Rust-based transpiler that performs the same transformations but runs 20-70x faster because Rust compiles to native machine code. Both translate modern JS/TS into browser-compatible code, but SWC is increasingly becoming the default in performance-critical tooling (Next.js, Parcel, Deno).

Why Transpilation Exists

Browser vendors implement new JavaScript features at different paces. Your const x = y?.z ?? 'default' (optional chaining + nullish coalescing) crashes in Chrome 79. The transpiler converts this: Babel with @babel/preset-env reads your Browserslist config ("last 2 versions, > 1%") and transforms only the features those targets don't support. It also handles JSX transformation (<div> → React.createElement('div') or the new JSX runtime _jsx('div')), TypeScript stripping, and polyfill injection.

Babel vs SWC vs esbuild vs tsc
ToolLanguageSpeedTypeScriptBest For
BabelJavaScriptBaseline (1x)Strip only (no type-checking)Complex plugin chains, custom transforms
SWCRust~20x fasterStrip only (no type-checking)Next.js, replacing Babel in bundlers
esbuildGo~100x fasterStrip only (no type-checking)Vite dev server, pre-bundling deps
tscTypeScriptBaseline (1x)Full type-checking + emitCI type-checking, library builds

Critical distinction: SWC, esbuild, and Babel all strip TypeScript types without checking them. They treat .ts files as JavaScript with annotations removed at speed. For actual type checking, you still need tsc --noEmit — this is why most toolchains run tsc --noEmit in parallel with the bundler.

Why SWC is 20x Faster — The Real Reason

It's not just "Rust fast, JS slow" — though that's part of it. Babel operates on a full AST (Abstract Syntax Tree), allocating thousands of JavaScript objects per file. Each plugin traverses the entire tree independently. SWC processes files in a single pass and compiles directly to machine code. But the biggest factor: Babel's plugin system is inherently sequential — plugins transform the AST one at a time. SWC's transforms are composed at compile time (Rust macro composition), producing a single optimized transformation function with zero runtime overhead.

Babel Config vs SWC Config — Same Goal, Different Syntax
// babel.config.js — plugin-based pipeline
module.exports = {
  presets: [
    ['@babel/preset-env', {
      targets: '> 0.5%, last 2 versions, not dead',
      useBuiltIns: 'usage',       // Auto-import only needed polyfills
      corejs: 3
    }],
    ['@babel/preset-react', {
      runtime: 'automatic'      // New JSX transform (React 17+)
    }],
    '@babel/preset-typescript'
  ],
  plugins: [
    '@babel/plugin-proposal-optional-chaining',
    'lodash'                    // Tree-shake lodash imports
  ]
};

// .swcrc — Rust-native config (Next.js default)
{
  "jsc": {
    "parser": {
      "syntax": "typescript",
      "tsx": true,
      "decorators": false
    },
    "transform": {
      "react": {
        "runtime": "automatic"
      }
    },
    "target": "es2015",
    "loose": true              // Faster, slightly less spec-compliant output
  },
  "env": {
    "targets": "> 0.5%",
    "mode": "usage",
    "coreJs": 3
  }
}

// Type-checking: always use tsc --noEmit regardless of transpiler
// package.json scripts:
// "typecheck": "tsc --noEmit",
// "build": "tsc --noEmit && vite build"  // Check first, then build
Key Takeaway

You almost never need Babel in a new project. Vite uses esbuild for transforms. Next.js uses SWC. If you have a custom Babel plugin that hasn't been ported to SWC/esbuild, keep Babel for that specific transformation. Otherwise, let the native tools handle it — the speed difference is transformative for developer experience.

ESLint and Prettier — Static Analysis vs Formatting, and the CI Workflow
Intermediate P1
Short Answer

ESLint is a static analysis tool that finds problematic patterns in your code — unused variables, missing dependency arrays, accessibility violations, security issues. Prettier is an opinionated code formatter that rewrites your code with consistent spacing, quotes, line breaks, and semicolons. ESLint catches bugs and enforces conventions; Prettier makes code look uniform. They serve different purposes and complement each other when configured correctly.

ESLint Deep Dive

ESLint parses your code into an AST and runs rules against it. Each rule is a visitor function that inspects specific AST nodes. Core rules catch logic errors (no-unused-vars, no-constant-condition). Plugin rules extend to framework-specific patterns (react-hooks/exhaustive-deps, @typescript-eslint/no-unnecessary-type-assertion). ESLint can also auto-fix certain rule violations, but the primary value is catching bugs before runtime.

Flat config (eslint.config.js): ESLint v9+ uses the new flat config system — simpler, faster, and TypeScript-native. No more .eslintrc extends chains.

Prettier's Philosophy

Prettier is deliberately less configurable than ESLint. This is the point — it ends all bikeshedding about code style. The team picks a few options (tab width, semicolons, trailing commas) and Prettier enforces them uniformly. Prettier does not understand your code's logic — it only looks at characters and whitespace. This is why Prettier cannot detect bugs: it'll happily format useEffect(async () => {}, []) without knowing it's a React anti-pattern.

ESLint Flat Config + Prettier Integration
// eslint.config.js — ESLint v9+ flat config
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import reactHooks from 'eslint-plugin-react-hooks';
import prettierConfig from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    plugins: { 'react-hooks': reactHooks },
    rules: {
      'react-hooks/rules-of-hooks': 'error',
      'react-hooks/exhaustive-deps': 'warn',
      '@typescript-eslint/no-unused-vars': ['error', {
        argsIgnorePattern: '^_'
      }],
      'no-console': 'warn'
    }
  },
  prettierConfig // Must be last — disables ESLint rules that conflict with Prettier
];

// .prettierrc — minimal, opinionated
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100
}
The #1 Mistake: Letting ESLint and Prettier Fight

ESLint has formatting rules. Prettier has formatting rules. If both try to control the same thing, you get conflicting fixes — format, lint, format, lint, infinite loop. The fix: use eslint-config-prettier. This config disables all ESLint formatting rules, leaving formatting entirely to Prettier and logic/bug detection entirely to ESLint. The rule: "Prettier for how it looks, ESLint for what it does."

husky + lint-staged: The Gatekeeper

The problem with linting in CI is developer friction — a PR fails 10 minutes after push because of a trailing space. husky sets up Git hooks; lint-staged runs linters/formatters only on staged files. The pre-commit hook runs eslint --fix and prettier --write on changed files, ensuring nothing bad enters the repo. CI still runs the full check as a safety net, but the pre-commit hook catches 95% of issues instantly.

husky + lint-staged Setup
// .husky/pre-commit (generated by: npx husky init)
// npx lint-staged

// package.json or .lintstagedrc.json
{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": [
      "eslint --fix --max-warnings 0",
      "prettier --write"
    ],
    "*.{css,md,json}": [
      "prettier --write"
    ]
  }
}
Pro Tip

VS Code users: install the ESLint and Prettier extensions, enable "editor.formatOnSave": true and "editor.codeActionsOnSave": { "source.fixAll.eslint": true }. This makes formatting and basic lint fixes happen automatically on every save — you'll never think about semicolons again. But do NOT rely on editor-only fixes; the pre-commit hook is the safety net for team consistency.

CI/CD Pipeline for Frontend — Design a Production-Grade Workflow
Advanced P1
Short Answer

A frontend CI/CD pipeline is a series of automated checks and deployments that run on every push and PR. The canonical pipeline has 5 stages: lint (code quality), type-check (TypeScript), test (unit + integration), build (production bundle), and deploy (to preview/production). Each stage acts as a gate — if any fails, the pipeline stops and the PR cannot merge. The goal is to catch every possible failure before a human ever sees the preview URL.

Pipeline Architecture

Stage 1 — Lint (30s): ESLint, Prettier check, commitlint. Catches style violations and code smells. Fastest stage — run it first because it catches the most common errors.

Stage 2 — Type-check (60s): tsc --noEmit. Catches type errors that would be runtime crashes. Run in parallel with lint if using GitHub Actions matrix strategy.

Stage 3 — Test (2-5 min): Vitest/Jest with coverage thresholds. Unit tests for utils/hooks, integration tests for pages, snapshot tests for components. Fail if coverage drops below 80% or any test fails.

Stage 4 — Build (2-3 min): vite build / next build. Verifies the production bundle compiles. This catches import errors, broken dynamic imports, and CSS issues that tests might miss. Run Lighthouse CI here to assert performance budgets.

Stage 5 — Deploy (1-2 min): Push to preview environment (Vercel/Netlify for PRs, S3+CloudFront for staging). On merge to main, deploy to production with a canary or blue-green strategy.

GitHub Actions — Complete Frontend CI Pipeline
# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:    { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  # Stage 1+2: Fast checks running in parallel
  lint:
    name: Lint & Format
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint

  typecheck:
    name: TypeScript Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run typecheck

  test:
    name: Unit & Integration Tests
    runs-on: ubuntu-latest
    strategy:
      matrix: { shard: [1, 2, 3] }  # Parallelize tests across shards
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run test -- --shard=${{ matrix.shard }}/3
      - uses: actions/upload-artifact@v4
        if: failure()
        with: { name: test-results, path: test-results/ }

  # Stage 3: Build — depends on lint+typecheck passing
  build:
    name: Production Build
    runs-on: ubuntu-latest
    needs: [lint, typecheck, test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist/ }

  lighthouse:
    name: Lighthouse Audit
    runs-on: ubuntu-latest
    needs: [build]
    steps:
      - uses: actions/checkout@v4
      - uses: treosh/lighthouse-ci-action@v12
        with:
          urls: ${{ steps.deploy_preview.outputs.url }}
          budgetPath: ./lighthouse-budget.json
          serverBaseUrl: ${{ secrets.LHCI_SERVER }}
FAANG Pipeline Patterns

At scale, the biggest optimization is dependency caching. Use actions/setup-node with cache: 'npm' to cache node_modules across runs, cutting install time from 3 minutes to 10 seconds. Use test sharding (shown above) to split test suites across parallel runners — 1500 tests that take 10 minutes sequentially finish in 2 minutes across 5 shards. Use remote caching (Nx Cloud, Turborepo) to skip builds entirely when the dependency tree hasn't changed.

  2. Why run lint and type-check in parallel rather than sequentially?
  3. What is test sharding and when do you need it?
  4. How would you implement a canary deployment for a frontend app?
Memory Trick: "Lint → Type → Test → Build → Deploy. Each stage is a gate. Fast checks first (parallel lint + type-check), slow checks later (build). Fail fast, fail early, never merge broken code."
Summary
  • 5-stage pipeline: lint, type-check, test, build, deploy — each must pass to proceed
  • Run lint + type-check in parallel as fast gates; test + build as slower verification
  • Cache node_modules (30s savings), shard tests (2-5x faster), remote cache builds (skip when possible)
  • Lighthouse CI enforces performance budgets — the build fails if LCP exceeds 2.5s
  • Preview deployments for every PR; production deployment only on main merge

Docker for Frontend — Multi-Stage Builds, Nginx Serving, and Docker Compose Dev
Intermediate P1
Short Answer

Docker packages your application into a lightweight, portable container that runs identically on any machine — your laptop, CI, staging, production. For frontend apps, the typical Dockerfile uses a multi-stage build: Stage 1 builds the static assets (Node.js + bundler), Stage 2 copies only the built output into a tiny Nginx image for serving. The final image weighs ~20MB instead of ~300MB because it excludes node_modules and the build toolchain.

Why Docker for a Static Site?

It sounds like overkill — serving HTML/CSS/JS from S3 is simpler. But Docker becomes essential when: (1) you need environment parity — your local dev, staging, and production must behave identically for SSR/API routes; (2) you're deploying to containerized infrastructure (Kubernetes, ECS, Cloud Run); (3) you need custom Nginx configuration for caching headers, gzip, compression, rate limiting, or reverse proxying API calls; (4) your app has runtime environment variables that must be injected at container startup, not build time.

Docker — Multi-Stage Build for a React/Vite SPA
# Dockerfile — Multi-stage build for a Vite React app
# Stage 1: Build the static assets
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
ARG VITE_API_URL
ENV VITE_API_URL=$VITE_API_URL
RUN npm run build

# Stage 2: Serve via Nginx — tiny final image
FROM nginx:1.25-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

# nginx.conf — SPA routing + caching + compression
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Brotli/gzip compression for text assets
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml;

    # Immutable caching for hashed assets (contenthash in filename)
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA routing — serve index.html for all non-file paths
    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache, must-revalidate";
    }
}

Docker Compose for Local Dev

For full-stack apps, Docker Compose orchestrates multiple services: your Next.js dev server, a PostgreSQL database, Redis cache, and maybe a local S3 emulator. Each service runs in its own container but shares a network. Hot reload works if you bind-mount the source directory — edit a file on your host, see the change instantly in the container.

Docker Compose — Full-Stack Dev Environment
# docker-compose.yml — Local dev with hot reload
version: '3.8'

services:
  frontend:
    build:
      context: .
      target: development  # Use dev stage from multi-stage Dockerfile
    ports:
      - "3000:3000"
    volumes:
      - .:/app              # Bind mount for hot reload
      - /app/node_modules   # Anonymous volume — don't override node_modules
    environment:
      - NODE_ENV=development

Senior Insight: Build-Time vs Runtime ENV

Vite/Webpack inline environment variables at build time. If you change VITE_API_URL after the build, it won't take effect — the value is baked into the JavaScript bundle. This means you cannot use the same Docker image for staging and production with different env vars. The pattern at scale: inject runtime configuration via a /config.js file generated at container startup. Nginx serves it before your app bundle, and your app reads window.__APP_CONFIG__. This keeps the image identical across environments — true build-once-deploy-anywhere.

Monorepo Architecture — Turborepo vs Nx, pnpm Workspaces, and Shared Packages
Advanced P1
Short Answer

A monorepo is a single repository containing multiple projects (apps and libraries) that share tooling, configuration, and dependencies. pnpm workspaces handle dependency linking between packages. Turborepo and Nx add build orchestration — caching, parallelization, and the ability to only rebuild/test what changed (affected commands). The key trade-off: monorepos eliminate version-sync headaches but require disciplined tooling to avoid slow CI and tangled dependencies.

Why Monorepo?

In a polyrepo setup, updating a shared UI component library means: PR in component repo → publish new version → update dependency in 3 consuming apps → 3 more PRs. In a monorepo: one PR changes the component and all consumers get the update immediately — tests run across all affected packages, nothing ships until everything passes. This atomic change across packages is the killer feature.

pnpm Workspaces — The Foundation

pnpm uses a content-addressable store and hard links. When 10 apps depend on React 18, it's stored once on disk and linked into each project's node_modules. This eliminates "phantom dependencies" (accessing packages your package.json didn't declare) — pnpm enforces strict dependency resolution. The pnpm-workspace.yaml file defines which directories are workspace packages.

Monorepo Structure & Configuration
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

// Directory structure
monorepo/
├── apps/
│   ├── web/          // Next.js dashboard — main consumer app
│   ├── mobile/       // React Native — uses shared business logic
│   └── marketing/    // Astro landing page — uses shared UI
├── packages/
│   ├── ui/           // Shared React component library (package.json name: @acme/ui)
│   ├── utils/        // Shared utilities (package.json name: @acme/utils)
│   ├── config-eslint/// Shared ESLint config across all packages
│   ├── config-ts/    // Shared TypeScript config base
│   └── config-tailwind/// Shared Tailwind preset
├── package.json      // Root — workspace scripts only
└── turbo.json        // Turborepo pipeline definition

// Root package.json — scripts orchestrate workspaces
{
  "scripts": {
    "dev":     "turbo dev",
    "build":   "turbo build",
    "test":    "turbo test",
    "lint":    "turbo lint",
    "format":  "prettier --write .",
    "publish": "pnpm -r publish" // -r = recursive across workspace
  }
}

The "Affected" Superpower

Turborepo and Nx both understand the dependency graph. turbo run test --filter=[HEAD^1] runs tests only for packages that changed since the last commit — not the entire monorepo. In a repo with 50 packages where you changed only @acme/utils, only @acme/utils and packages that depend on it get tested. This keeps CI fast even as the monorepo grows to hundreds of packages.

Webpack Module Federation — Micro-Frontends at the Bundler Level
Expert P1
Short Answer

Module Federation (Webpack 5) allows multiple separate webpack builds to share modules at runtime. A host application loads remote modules from other applications dynamically, without a network request for each component — the remote's chunk is fetched, executed, and integrated into the host's module graph. Unlike iframes, federated modules share the same React instance, context, and state. Unlike npm packages, they can be deployed independently — updating the remote's deployment updates all consuming hosts instantly.

Architecture

Exposes (remote): The remote app declares which modules other apps can consume. Think of it as "public API" for your app.

Remotes (host): The host declares which remote apps to load from, at which URL. The host fetches the remote's entry point (a tiny JS manifest) at runtime.

Shared: Dependencies like react, react-dom, react-router are declared as shared — only one copy is loaded even if host and remote both use them. This is critical for React to work (only one React instance can own the DOM).

The flow: User hits host app → host loads → host sees remote declaration → fetches remoteEntry.js → parses the exposed module list → when a component from the remote is needed, fetches just that component's chunk → renders it as if it were local.

Module Federation — Host and Remote Configuration
// Remote app (dashboard-team) — webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

// Remote: exposes components for other apps to consume
new ModuleFederationPlugin({
  name: 'dashboard',             // Global scope name (must match host's remote key)
  filename: 'remoteEntry.js',     // Manifest file hosts fetch
  exposes: {
    './DashboardApp': './src/components/DashboardApp',
    './MetricsWidget': './src/components/MetricsWidget',
    './Charts': './src/charts'
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0' },
    'react-dom': { singleton: true },
    'react-router-dom': { singleton: true }
  }
})

// Host app (shell) — webpack.config.js
new ModuleFederationPlugin({
  name: 'shell',
  remotes: {
    dashboard: 'dashboard@http://localhost:3001/remoteEntry.js',
    checkout:  'checkout@http://localhost:3002/remoteEntry.js',
    profile:   'profile@http://localhost:3003/remoteEntry.js'
  },
  shared: {
    react: { singleton: true, eager: true }, // eager = loaded immediately (host must provide React)
    'react-dom': { singleton: true, eager: true }
  }
})

// Host: consuming a remote module (React)
import React, { Suspense, lazy } from 'react';

const DashboardApp = lazy(() => import('dashboard/DashboardApp'));
const CheckoutApp  = lazy(() => import('checkout/CheckoutApp'));

function Shell() {
  return (
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/dashboard/*" element={<DashboardApp />} />
        <Route path="/checkout/*"  element={<CheckoutApp />} />
      </Routes>
    </Suspense>
  );
}
The #1 Module Federation Mistake

Version mismatch on shared dependencies. If the host has React 18.2 and a remote has React 18.0, and singleton: true forces one copy, which version wins? Webpack negotiates based on requiredVersion. If versions are incompatible, you get runtime errors — "Invalid hook call" is the classic symptom of two React copies on the page. Always: (1) pin shared dependency versions across all federated apps, (2) use requiredVersion strictly, (3) monitor with shareScope debugging.

Is Module Federation Worth It?

For 95% of teams, the answer is no. Module Federation solves the "multiple teams deploying to the same page independently" problem — if you have 10 teams working on different parts of one SPA, each wanting independent CI/CD, it's a legitimate solution. But it adds significant complexity: runtime dependency negotiation, shared scope debugging, orchestration layer. For most teams, a well-structured monorepo with code splitting achieves the same result with far less complexity. The Shopify model: start with a modular monolith, split into MF only when team autonomy at the deploy level becomes the bottleneck.

Bundle Analysis — How to Audit and Reduce Bundle Size
Intermediate P2
Answer

Bundle analysis tools visualize what's inside your production JavaScript. webpack-bundle-analyzer and vite-bundle-visualizer (Rollup plugin) generate an interactive treemap where each rectangle represents a module — larger rectangles = bigger impact. You look for: (1) duplicate dependencies (two versions of lodash), (2) unexpectedly large modules (a 2MB locale file someone imported by accident), (3) un-minified code, (4) libraries that should be tree-shaken but aren't (moment.js, lodash without named imports). After identifying issues, fix them: replace moment with date-fns (tree-shakeable), use dynamic imports, enable compression in your CDN.

Bundle Analysis Commands
// Webpack: add to webpack.config.js plugins
const BundleAnalyzerPlugin = require('webpack-bundle-analyzer').BundleAnalyzerPlugin;
plugins: [new BundleAnalyzerPlugin({ analyzerMode: 'static' })]

// Vite: use rollup-plugin-visualizer
// npm run build -- --report   (if using vite-bundle-visualizer)

// Quick size check without visualization
npx vite build && du -sh dist/
# or on Windows:
npx vite build; if ($?) { Get-ChildItem -Path dist -Recurse -File | Measure-Object Length -Sum }
Quick Wins to Reduce Bundle
  • Replace moment.js (~72KB) with date-fns or dayjs (~2KB tree-shaken)
  • Use dynamic imports for heavy libraries (charting, rich text editors, maps)
  • Verify lodash is tree-shaken (import { debounce } from 'lodash-es' or use lodash/debounce)
  • Check for duplicate polyfills (core-js appearing in multiple chunks)
  • Ensure your CDN serves gzip/brotli compressed assets

Environment Variables — .env Files, CI Secrets, and the NEXT_PUBLIC_ Trap
Beginner P2
Answer

Environment variables configure your app differently across environments without code changes. .env files follow a priority chain: .env.local (highest, gitignored) → .env.development → .env (lowest, committed with defaults). CI secrets are injected into the build environment by the CI platform — they're never in the repo. The critical distinction for frontend: variables prefixed with VITE_ (Vite) or NEXT_PUBLIC_ (Next.js) are baked into the client bundle and visible to anyone who opens DevTools. Never put secrets (API keys, database URLs, tokens) in these — they must stay server-side. For runtime config that changes per deployment without rebuilding, use the /config.js pattern: a static JS file generated at startup that sets window.__APP_CONFIG__.

Environment Variable Patterns
# .env.local — developer-specific, gitignored
VITE_API_URL=http://localhost:4000
VITE_FEATURE_FLAGS=beta,new-dashboard

# .env.production — committed, default prod values
VITE_API_URL=https://api.myapp.com

# NEVER do this in Vite/Next.js client vars:
# VITE_SECRET_KEY=sk-abc123   ← EXPOSED in browser DevTools!

// Runtime config pattern (public/config.js — served by Nginx before app bundle)
window.__APP_CONFIG__ = {
  API_URL: 'https://api-{ENVIRONMENT}.myapp.com',
  ENVIRONMENT: '{ENVIRONMENT}',  // Replaced at container startup via sed/script
  SENTRY_DSN: '{SENTRY_DSN}'
};

// index.html — load config before app (SPA runtime injection)
<script src="/config.js"></script>
<script src="/assets/index.js"></script>
The NEXT_PUBLIC_/VITE_ Security Trap

I've seen teams commit Stripe secret keys with NEXT_PUBLIC_STRIPE_KEY — the prefix makes it available on window. If Next.js reads process.env.STRIPE_SECRET in getServerSideProps, it stays server-side. But NEXT_PUBLIC_STRIPE_SECRET is embedded in the client JS bundle — anyone can see it. Rule: only use NEXT_PUBLIC_/VITE_ prefixes for things you'd be comfortable printing on a billboard.

Lighthouse CI runs Lighthouse audits as part of your CI pipeline and asserts performance budgets. Turbopack — Rust-Based Next.js Bundler vs Vite and Webpack
Advanced P2
Answer

Turbopack is Vercel's Rust-based incremental bundler, built by the creator of Webpack (Tobias Koppers). It's the spiritual successor to Webpack, learning from the lessons of 12 years of bundler development. Unlike esbuild (which is fast but single-pass and limited in transform capabilities), Turbopack handles the full bundling pipeline — transforms, module resolution, chunking, optimization — all in Rust with incremental computation at its core. In Next.js 13+, Turbopack replaces Webpack for development; production builds still use Webpack (as of 2024) while Turbopack production mode is under development. Benchmarks show Turbopack cold starts 700x faster than Webpack on large projects (1000+ modules). The key architectural insight: function-level caching. If you change one line in a module, Turbopack only re-runs functions whose inputs actually changed — not the entire module.

Current Status (2025)

Turbopack is the default dev server in Next.js 15. It's stable for development. Production builds are coming. Vite remains the best choice outside the Next.js ecosystem. If you're starting a Next.js project today, you're already using Turbopack — and you'll never have to configure it.
