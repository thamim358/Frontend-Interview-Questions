What is Next.js? Explain the App Router vs Pages Router.
Beginner P1 — Critical
Short Interview Answer

Next.js is a React framework built by Vercel that provides file-based routing, server-side rendering, static site generation, and API routes out of the box. The Pages Router (pre-v13) uses a pages/ directory where each file becomes a route. The App Router (v13+) uses an app/ directory with nested layouts, React Server Components by default, streaming, and a more opinionated architecture. The App Router is the recommended approach for new projects, while the Pages Router continues to be supported.

Easy Explanation

Think of Next.js as React with training wheels that are actually rocket boosters. React alone gives you components — Next.js gives you pages, routing, data fetching patterns, and production optimizations all pre-configured. The Pages Router is like a well-organized filing cabinet (pages/about.js = /about). The App Router is a smart filing cabinet where each folder can have its own layout, loading state, and error boundary built-in.

Real-World Example

Netflix migrated parts of their dashboard to the App Router. Their authentication layout wraps all protected routes in a layout.tsx that checks sessions once (not on every navigation). Before, with the Pages Router, they had to duplicate auth logic in getServerSideProps on every single page. The App Router's nested layouts eliminated that duplication entirely.

Why Interviewers Ask This

This question tests whether you understand the evolution of Next.js and can articulate architectural decisions. Someone who can't explain why the App Router exists probably hasn't built anything serious with it. It also reveals whether you've been keeping up with the ecosystem or are stuck in 2021.

Explain Server Components vs Client Components. When do you use each?
Intermediate P1 — Critical
Short Interview Answer

In the App Router, all components are Server Components by default. They run on the server, have direct access to databases and filesystems, and send zero JavaScript to the client — reducing bundle size dramatically. Client Components are opt-in via the "use client" directive. They run in the browser, can use React hooks (useState, useEffect, useContext), event handlers (onClick), and browser APIs. The key insight: Server Components render on the server, Client Components hydrate on the client — and you can nest Client Components inside Server Components.

Easy Explanation

Imagine a restaurant. Server Components are the kitchen — they have access to the fridge (database), the stove (computation), and they prepare the meal (HTML). Client Components are the waiter bringing interactive elements (onClick, useState) to the table. The kitchen doesn't need to know about the customer's fork preferences (browser state), and the waiter doesn't need access to the raw ingredients (server-only APIs). Next.js orchestrates both, sending the prepared meal (server-rendered HTML) and the waiter's toolkit (JavaScript bundle) together.

Golden Rule

Push Client Components as far down the tree as possible. If only a button needs interactivity, make just the button a Client Component — not the entire page. Think "islands of interactivity" in a sea of server-rendered HTML.

Decision Matrix
NeedServer ComponentClient Component
Fetch data from DB/APIYes (direct)Yes (via fetch/useEffect)
useState / useReducerNoYes
useEffect / event handlersNoYes
Browser APIs (localStorage, etc.)NoYes
Access to filesystem / DB directlyYesNo
Keep sensitive keys secretYes (never sent to client)No (exposed in bundle)
Reduce client JS bundleYes (0 KB JS)No (adds to bundle)
Real-World Example

Vercel's own dashboard uses this pattern extensively. The project list page is a Server Component that fetches all projects from the database and renders the list. Each project card has a "Delete" button which is a Client Component ("use client") that handles the confirmation dialog and calls a Server Action. The heavy lifting (DB query, rendering 100+ cards) requires zero JavaScript sent to the browser.

Common Mistake

Marking the entire page with "use client" just because one button needs interactivity. This kills all the benefits of Server Components — your data fetching, rendering, and bundle size all suffer. Instead, extract the interactive part into its own file with "use client" at the top and import it into the Server Component.

  );
}

Senior Developer Insight

The real power isn't just smaller bundles — it's that Server Components never re-render. Once the server sends the HTML, that's it. No reconciliation, no virtual DOM diffing, no hooks to manage. This means you can put expensive computations (Markdown parsing, image processing) in Server Components and they run exactly once per request.

  2. What happens if you put "use client" in a file that's imported by another "use client" file?
  3. How does the interleaving (Server to Client to Server) boundary work?
Memory Trick: "Server = silent (no JS). Client = chatty (needs JS). Keep the chatty parts small and close to the user interaction."
  • Server Components: default, run on server, 0 KB JS, can use async/await
  • Client Components: opt-in via "use client", run in browser, can use hooks
  • Push "use client" as deep as possible — islands architecture
  • Server Components can import Client Components (not vice versa directly)
  • Bundle savings are massive — typically 30-50% reduction

Explain SSR vs SSG vs ISR. When should you use each?
Intermediate P1 — Critical
Short Interview Answer

SSR (Server-Side Rendering) generates HTML on each request — best for personalized, real-time data like dashboards. SSG (Static Site Generation) builds HTML at build time — ideal for content that rarely changes like blog posts or marketing pages. ISR (Incremental Static Regeneration) combines both: pages are statically generated but can be revalidated at specified intervals or on-demand, updating stale content without a full rebuild. In the App Router, all of these are controlled through fetch() cache options and the revalidate segment config, not separate functions like getStaticProps.

Easy Explanation

Think of a newspaper. SSG is like printing 10,000 copies at the factory — fast to distribute, but content is frozen until the next print run. SSR is like printing a custom copy per reader — always fresh, but slower. ISR is like printing a base copy but updating headlines every hour — best of both worlds. You get the speed of pre-printed pages with periodic freshness.

Comparison Table
FeatureSSRSSGISR
Rendering timePer requestBuild timeBuild time + revalidation
TTFBSlower (server work)Fastest (CDN)Fast (CDN, stale revalidate)
Data freshnessReal-timeStale until rebuildEventually fresh
Use casesDashboards, user profiles, cartsBlog posts, docs, landing pagesProduct listings, CMS pages, news
App Router configdynamic: 'force-dynamic'Default (no fetch)revalidate: 60
Scales toServer capacityInfinity (CDN)Infinity (CDN)
Real-World Example

Amazon product pages are the textbook ISR case. Product details (title, description, price) don't change every second, but inventory status does. Amazon could ISR at 60 seconds — 99% of requests hit the CDN cache (super fast), and every 60 seconds the page silently regenerates with updated stock counts. Twitter's home feed uses SSR — your feed is unique to you and changes constantly. Stripe's documentation uses SSG — docs change when engineers update them, which triggers a rebuild.

Common Mistake

Using ISR with revalidate: 1 thinking it equals real-time. Each revalidation still serves the stale page to the first visitor and regenerates in the background. For truly real-time data, use SSR with dynamic: 'force-dynamic' or stream updates via WebSockets.

Code Example
app/products/[id]/page.tsx — ISR Pattern
// Revalidate this page every 60 seconds
export const revalidate = 60;

export default async function ProductPage({ params }: { params: { id: string } }) {
  const product = await fetch(`https://api.example.com/products/${params.id}`, {
    next: { revalidate: 60 }
  }).then((res) => res.json());

  return <div>{product.name}: ${product.price}</div>;
}

export async function generateStaticParams() {
  const products = await fetch('https://api.example.com/products').then((r) => r.json());
  return products.map((p) => ({ id: p.id.toString() }));
}
app/dashboard/page.tsx — SSR (Dynamic) Pattern
// Always fetch fresh data — never cache this page
export const dynamic = 'force-dynamic';

export default async function DashboardPage() {
  const data = await fetch('https://api.example.com/live-stats', {
    cache: 'no-store'
  }).then((r) => r.json());

  return <div>Active users: {data.activeUsers}</div>;
}
Senior Developer Insight

The real art is composing these strategies within a single page. In the App Router, you can have a layout.tsx that's statically generated, a header that's SSR (dynamic user avatar), and content blocks that are ISR. This granularity didn't exist in the Pages Router — every page had a single strategy. Now you mix and match at the component boundary level.

Memory Trick: "SSG = bake once, serve forever. SSR = cook per order. ISR = bake once, reheat every N minutes."
  • SSR: HTML generated per request, best for dynamic/personalized content
  • SSG: HTML generated at build time, best for static content, infinite CDN scale
  • ISR: Static + periodic revalidation, best for mostly-static data with updates
  • App Router uses fetch() options + segment config (no more getX functions)
  • Can mix strategies: layouts can be static, pages dynamic, components ISR

How does Data Fetching work in the App Router?
Intermediate P1 — Critical
Short Interview Answer

In the App Router, Server Components can be async — you await fetch() directly in the component body. Next.js extends the native fetch API with caching options: force-cache (default, equivalent to SSG), no-store (SSR every request), and revalidate: N (ISR). There's no more getServerSideProps or getStaticProps. The data is fetched on the server, rendered to HTML, and sent to the client — the client never sees the raw API calls. You can also use Server Actions for mutations and React's cache() function for request-scoped deduplication.

Easy Explanation

Remember how in the Pages Router you had to jump through hoops — getServerSideProps for SSR, getStaticProps for SSG, and you couldn't fetch inside components? The App Router says "just write await fetch() where you need it." It's like going from a separate kitchen-prep room to an open kitchen — the data is fetched right where it's consumed, not in a separate function.

Fetch Cache Options
OptionBehaviorPages Router EquivalentUse Case
cache: 'force-cache'Cache indefinitely (default)getStaticPropsBlog posts, docs
cache: 'no-store'Fetch fresh every requestgetServerSidePropsDashboards, user data
next: { revalidate: 60 }Cache for 60s, then revalidategetStaticProps + revalidateProduct pages, CMS content
next: { tags: ['posts'] }On-demand revalidation via revalidateTagOn-Demand ISRAfter CMS content update
Real-World Example

Shopify's Hydrogen storefront (built on Next.js) fetches product data in Server Components using cache: 'no-cache' for inventory (must be real-time) and revalidate: 3600 for product descriptions (rarely change). They use React's cache() to deduplicate identical fetch calls across the component tree — if the header, sidebar, and product page all fetch the cart data, it only hits the API once per request.

Common Mistake

Accidentally leaving force-cache (the default) on user-specific data. Imagine fetching the current user's profile with the default cache — every visitor sees the first user who triggered the cache! Always use cache: 'no-store' for authenticated data or use cookies() to vary the cache key.

Code Example
app/blog/[slug]/page.tsx — Parallel Fetching
import { cache } from 'react';

// Deduplicate: if called multiple times, only fetches once per request
const getPost = cache((slug: string) =>
  fetch(`https://api.example.com/posts/${slug}`).then((r) => r.json())
);

export default async function BlogPost({ params }: { params: { slug: string } }) {
  const post = await getPost(params.slug);
  const comments = await fetch(`https://api.example.com/comments/${post.id}`, {
    next: { revalidate: 60 }
  }).then((r) => r.json());

  return (
    <article>
      <h1>{post.title}</h1>
      <CommentSection comments={comments} />
    </article>
  );
}
Parallel data fetching — both run simultaneously
export default async function DashboardPage() {
  const [user, orders, analytics] = await Promise.all([
    fetch('/api/user', { cache: 'no-store' }).then((r) => r.json()),
    fetch('/api/orders').then((r) => r.json()),
    fetch('/api/analytics').then((r) => r.json()),
  ]);

  return <Dashboard user={user} orders={orders} analytics={analytics} />;
}
Pro Tip

Use Promise.all() inside Server Components to fetch multiple independent data sources in parallel. Unlike the Pages Router where you had to manually coordinate getServerSideProps, the App Router makes parallel fetching natural — just await all promises simultaneously.

Memory Trick: "No more getX functions. Just async components + fetch(). The cache options ARE your rendering strategy."
  • Server Components are async — await fetch() directly in the component
  • Cache options: force-cache (SSG), no-store (SSR), revalidate: N (ISR)
  • react cache() deduplicates fetch calls within a single request
  • Promise.all() for parallel data fetching — avoid waterfalls
  • No more getStaticProps / getServerSideProps boilerplate

Explain Layouts, Templates, and Pages in the App Router.
Intermediate P1 — Critical
Short Interview Answer

Layouts (layout.tsx) wrap child routes and persist state across navigations — the nav bar, sidebar, and footer don't re-render when you navigate between pages. Templates (template.tsx) are like layouts but remount on every navigation — useful for animations, scroll position reset, or tracking page views. Pages (page.tsx) are the leaf nodes that render the actual content for a route. All three can be nested: each folder in the app/ directory can have its own layout, template, and page.

Easy Explanation

Layouts are like the frame of a painting — the ornate border stays the same as you flip through different artworks. Templates are like the stage curtain — it drops and rises between every act (animation opportunity). Pages are the artwork itself — each route has exactly one page. The beauty is that the frame (layout) persists, so the navigation bar doesn't flash or remount when you click a link.

Layout vs Template: When to Use Each
Behaviorlayout.tsxtemplate.tsx
State persistenceYes (keeps state)No (resets on navigation)
Re-renders on navigationNo (only children update)Yes (full remount)
useEffect runsOnly on initial mountOn every navigation
Best forNav bars, sidebars, footersAnimations, analytics, scroll reset
Suspense boundaryCan wrap childrenCan wrap children
Error boundaryCan wrap childrenCan wrap children
Real-World Example

Linear's dashboard (built with Next.js App Router) uses nested layouts: the root layout has the sidebar and command palette, the project layout adds a project header, and the issue page renders the actual content. Clicking between issues in the same project keeps the sidebar and project header intact — only the issue content area re-renders. This is why the app feels instant when navigating.

Common Mistake

Putting data fetching in a layout and expecting it to refresh on navigation. Layouts don't re-render or re-fetch when you navigate between sibling routes. If you need fresh data on each navigation, fetch it in the page component instead, or use a template.

Senior Developer Insight

Layout persistence is the single biggest UX improvement in the App Router. In the Pages Router, you'd use React's key prop hack or wrap the entire app in a custom Layout component that reimplements routing logic. Now it's built-in. The key interview point: layouts don't just avoid re-rendering — they preserve component state, scroll position, and even in-flight network requests across navigations.

Memory Trick: "Layouts are lazy (stay put), templates are eager (reset), pages are the destination."
  • layout.tsx: Wraps children, persists across navigations, keeps state
  • template.tsx: Wraps children, remounts every navigation, resets state
  • page.tsx: The actual route content, leaf of the tree
  • All three support nesting — each folder can have its own
  • loading.tsx, error.tsx, not-found.tsx are also per-segment special files

Explain Next.js Caching in depth — Data Cache, Full Route Cache, Router Cache.
Advanced P1 — Critical
Short Interview Answer

Next.js has 4 layers of caching that work together to serve pages as fast as possible. Data Cache stores raw fetch() responses on the server (cross-request, persistent). Full Route Cache stores the rendered HTML and RSC payload on the server (statically generated pages only). Router Cache stores RSC payloads in the browser's memory for 30s (soft navigation). Request Memoization deduplicates identical fetch calls within a single render pass (same request, React's cache() underneath). Understanding when to invalidate each cache is the key to building performant Next.js apps that don't serve stale data.

Easy Explanation

Think of it like a multi-level memory system in a CPU. Request Memoization = L1 cache (fastest, per-render). Router Cache = L2 cache (in browser memory, 30s). Full Route Cache = L3 cache (on server, rendered HTML). Data Cache = persistent storage (fetched data, survives deploys). Each layer trades freshness for speed, and you invalidate them with different APIs.

The Four Cache Layers
Cache LayerWhereWhats StoredDurationInvalidation
Request MemoizationServer (per-request)fetch() return valuesUntil render completesAutomatic per request
Data CacheServer (persistent)fetch() responsesPersistent (across deploys)revalidateTag, revalidatePath
Full Route CacheServer (persistent)Rendered HTML + RSC payloadPersistentRedeploy or revalidate
Router CacheClient (browser memory)RSC payload30s or sessionrouter.refresh(), cookies
Real-World Example

Netflix's browse page illustrates all four caches working together. The movie thumbnails (Data Cache) are fetched with revalidate: 3600. The browse page HTML (Full Route Cache) is regenerated when the data cache is stale. As you hover between rows, the Router Cache in your browser keeps recent titles instantly available. And within each render, Request Memoization ensures the "Continue Watching" row and the "Trending Now" row don't double-fetch the same user preferences API call.

Common Mistake

Calling revalidatePath('/') and expecting it to instantly update the client. The Router Cache still holds stale data for 30 seconds! You also need to call router.refresh() on the client to clear the Router Cache. Most "stale data" bugs in Next.js are actually Router Cache issues, not Data Cache issues.

Code Example
app/api/revalidate/route.ts — On-Demand Revalidation
import { revalidateTag, revalidatePath } from 'next/cache';
import { NextRequest } from 'next/server';

export async function POST(request: NextRequest) {
  const secret = request.nextUrl.searchParams.get('secret');

  if (secret !== process.env.REVALIDATION_SECRET) {
    return Response.json({ error: 'Invalid token' }, { status: 401 });
  }

  revalidateTag('posts');
  revalidatePath('/blog');

  return Response.json({ revalidated: true });
}
Tag-based fetch with on-demand revalidation
// In your page component:
const posts = await fetch('https://api.example.com/posts', {
  next: { tags: ['posts'] }
}).then((r) => r.json());

// In your CMS webhook handler:

FAANG Interview Twist

"A user reports seeing old data after updating their profile. The data cache is correctly purged. What's likely wrong?" — Answer: The Router Cache. Even after server-side revalidation, the client holds the RSC payload for 30 seconds. You need router.refresh() after the mutation completes.

Memory Trick: "Memoize per render, Data until you revalidate, Route until you redeploy, Router for 30 seconds. Four layers, four invalidation strategies."
  • 4 cache layers: Request Memoization, Data Cache, Full Route Cache, Router Cache
  • Data Cache: Persistent, cross-request, invalidated via revalidateTag/revalidatePath
  • Full Route Cache: Rendered HTML, only for static pages, cleared on redeploy
  • Router Cache: Client-side in-memory, 30s default, cleared with router.refresh()
  • Stale data bugs are often Router Cache issues, not Data Cache issues

What is Middleware in Next.js? How do you use it for auth, redirects, and more?
Intermediate P1 — Critical
Short Interview Answer

Middleware runs before every request completes, at the edge (or Node.js), giving you the ability to modify the request or response. Create a middleware.ts file in the project root (or src/). Use config.matcher to scope which routes it applies to. Common use cases: authentication checks (redirect unauthenticated users), geolocation-based redirects (serve different locales), A/B testing (rewrite to variant pages), and bot protection. Middleware has access to cookies, headers, and NextRequest/NextResponse — but runs in a limited Edge runtime, so no Node.js APIs (fs, net, etc.).

Easy Explanation

Middleware is a bouncer at the club entrance. Before anyone gets to the party (your pages), the bouncer checks their ID (cookies/tokens), verifies they're on the guest list (auth check), and either waves them through or redirects them to the line outside (login page). The bouncer is fast and runs close to the user (edge), but can't do heavy lifting like database queries — that's for the pages inside.

Real-World Example

Instagram could use Next.js middleware for regional content filtering. Users in the EU hit a different API endpoint due to GDPR requirements. Instead of duplicating this logic on every page, a single middleware checks request.geo?.country and rewrites the request to EU-specific data sources. Stripe uses middleware for bot detection — analyzing request patterns and blocking suspicious traffic before it hits expensive SSR pages.

Common Mistake

Running database queries inside middleware. Middleware runs on every request — if you have 10,000 RPM and each middleware makes a DB query, you've just created a massive bottleneck. Instead, only check lightweight tokens (JWTs, session cookies) in middleware, and do the heavy data fetching inside Server Components or Route Handlers.

Code Example
middleware.ts — Auth Guard and Redirect Pattern
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const token = request.cookies.get('auth-token')?.value;
  const isAuthPage = request.nextUrl.pathname.startsWith('/login');

  // If not authenticated and trying to access protected route
  if (!token && !isAuthPage) {
    const loginUrl = new URL('/login', request.url);
    loginUrl.searchParams.set('from', request.nextUrl.pathname);
    return NextResponse.redirect(loginUrl);
  }

  // If authenticated and trying to access login page
  if (token && isAuthPage) {
    return NextResponse.redirect(new URL('/dashboard', request.url));
  }

  // Clone and modify headers
  const response = NextResponse.next();
  response.headers.set('x-custom-header', 'middleware-was-here');

  return response;
}

export const config = {
  matcher: ['/dashboard/:path*', '/login', '/settings/:path*'],
};
middleware.ts — Geo-based Rewrite (A/B Testing)
export function middleware(request: NextRequest) {
  const country = request.geo?.country || 'US';

  if (['DE', 'FR', 'ES', 'IT'].includes(country)) {
    return NextResponse.rewrite(new URL(`/eu${request.nextUrl.pathname}`, request.url));
  }

  return NextResponse.next();
}
Pro Tip

Use config.matcher aggressively. If you only need middleware on /dashboard/* routes, don't run it on /public/* or static assets. Every millisecond counts when middleware runs on every matched request.

Memory Trick: "Middleware = the gate. Cookies/headers check at the gate, DB queries inside the castle (Server Components)."
  • middleware.ts at project root, runs before every matched request
  • Use config.matcher to scope routes (use string array, not regex)
  • Runs in Edge runtime — limited APIs, no Node.js modules
  • Perfect for auth checks, redirects, rewrites, header manipulation
  • Don't do heavy computation or DB calls in middleware

Explain Server Actions in Next.js. How do they work and when should you use them?
Advanced P1 — Critical
Short Interview Answer

Server Actions are async functions that run on the server but can be called from Client Components like regular functions. Defined with "use server", they enable form mutations, database writes, and API calls without creating a separate API route. They support progressive enhancement — forms work even before JavaScript loads. React provides useFormStatus (pending state) and useOptimistic (optimistic UI updates) hooks specifically for Server Actions. They're essentially RPC (Remote Procedure Call) — the client calls a function, Next.js serializes the arguments, sends them to the server, executes the function, and returns the result.

Easy Explanation

Remember how you used to write a form, create an API route /api/submit, add fetch() in the submit handler, handle errors, loading states, and validation — all manually? Server Actions collapse that into: write a function with "use server" at the top, pass it directly to <form action={myServerFn}>. That's it. The form submits, the function runs on the server, and React handles the rest. It's like having a direct hotline from the browser to your backend, no API routing layer needed.

Real-World Example

Vercel's commerce templates use Server Actions for the entire checkout flow. The "Add to Cart" button triggers a Server Action that updates the database, revalidates the cart cache, and streams back the updated cart total — all without a single /api/* route. Notion-style apps use Server Actions for real-time collaborative editing, combining useOptimistic for instant UI feedback with a Server Action that persists to the database.

Common Mistake

Calling Server Actions from event handlers thinking they're like regular functions. Server Actions make network requests — they're async and can fail. Always handle errors with try/catch and provide user feedback. Also, never pass class instances or non-serializable objects as arguments — only plain objects, FormData, strings, numbers, etc.

Code Example
app/actions.ts — Server Action Module
'use server';

import { revalidatePath } from 'next/cache';
import { z } from 'zod';

const schema = z.object({
  title: z.string().min(1),
  content: z.string().min(10),
});

export async function createPost(formData: FormData) {
  const parsed = schema.safeParse({
    title: formData.get('title'),
    content: formData.get('content'),
  });

  if (!parsed.success) {
    return { error: 'Validation failed' };
  }

  revalidatePath('/posts');

How do Image and Font Optimization work in Next.js?
Beginner P1 — Critical

Authentication Patterns — NextAuth/Auth.js, Middleware Auth, Server Sessions
Advanced P2 — High Value
Short Interview Answer

Authentication in Next.js typically follows three layers: Middleware checks session tokens and redirects unauthenticated users (fast, edge-level), Server Components read the session to fetch user-specific data (secure, no client exposure), and Client Components handle UI state (login buttons, user dropdowns). NextAuth.js (Auth.js v5) provides OAuth providers, database adapters, and JWT/session strategies out of the box. The key pattern: validate in middleware, personalize in Server Components, interact in Client Components.

Code Example — Middleware + Server Session
lib/auth.ts — Session helper (runs on server)
import { cookies } from 'next/headers';
import { jwtVerify } from 'jose';

export async function getSession() {
  const token = cookies().get('session')?.value;
  if (!token) return null;

  try {
    const { payload } = await jwtVerify(token, new TextEncoder().encode(process.env.JWT_SECRET!));
    return payload;
  } catch {
    return null;
  }
}
app/dashboard/page.tsx — Server Component reads session
import { getSession } from '@/lib/auth';
import { redirect } from 'next/navigation';

export default async function DashboardPage() {
  const session = await getSession();
  if (!session) redirect('/login');

  const user = await db.user.findUnique({ where: { id: session.sub } });
  return <div>Welcome back, {user.name}!</div>;
}
Common Mistake

Checking auth only in Client Components with useEffect. This causes a flash of unauthenticated content before the redirect fires. Always gate protected routes in middleware (fast, server-side, no flash) and Server Components.

Memory Trick: "Middleware = bouncer (redirects fast). Server Component = personal butler (fetches your data). Client Component = the furniture (interactive UI)."
  • Three layers: Middleware (gate), Server Components (data), Client Components (UI)
  • NextAuth.js v5: OAuth, database adapters, JWT sessions built-in
  • Never check auth in useEffect — use middleware for redirects
  • Server Components read sessions securely, never exposed to client

Route Handlers (API Routes) in the App Router
Intermediate P2 — High Value
Short Interview Answer

Route Handlers replace the Pages Router's API Routes. Create a route.ts file in the app/ directory with exported async functions named after HTTP methods: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS. They receive a standard Request and return a Response (Web API, not Express-style). They support streaming (return a ReadableStream), caching (same fetch options as pages), and CORS configuration. Route Handlers can live in the same folder as pages without conflicting — route.ts for API, page.tsx for UI.

Code Example
app/api/posts/route.ts — Full CRUD Route Handler
import { NextRequest } from 'next/server';

export async function GET(request: NextRequest) {
  const { searchParams } = request.nextUrl;
  const page = searchParams.get('page') || '1';

  const posts = await db.post.findMany({
    skip: (parseInt(page) - 1) * 10,
    take: 10,
  });

  return Response.json(posts);
}

export async function POST(request: Request) {
  const body = await request.json();
  const post = await db.post.create({ data: body });
  return Response.json(post, { status: 201 });
}
Streaming Route Handler
export async function GET() {
  const stream = new ReadableStream({
    async start(controller) {
      controller.enqueue('data: First chunk\n\n');
      await new Promise((r) => setTimeout(r, 1000));
      controller.enqueue('data: Second chunk\n\n');
      controller.close();
    },
  });

  return new Response(stream, {
    headers: { 'Content-Type': 'text/event-stream' },
  });
}
Pro Tip

Prefer Server Actions over Route Handlers for mutations. Route Handlers are best for external-facing APIs (webhooks, third-party integrations, public REST endpoints). For your own app's forms and mutations, Server Actions are simpler and more secure.

  • route.ts replaces pages/api/*.ts — Web API Request/Response
  • Export named functions: GET, POST, PUT, PATCH, DELETE
  • Supports streaming and standard fetch caching options
  • Can coexist with page.tsx in the same folder

Edge vs Node.js Runtime — Cold Starts, API Limitations, When to Use Each
Advanced P2 — High Value
Short Interview Answer

The Edge Runtime is a lightweight subset of Web APIs that runs on V8 isolates close to users (low latency, no cold starts in practice). It supports Web APIs like fetch, Request/Response, crypto, URL, TextEncoder, and streaming — but NO Node.js APIs (no fs, net, tls, child_process). The Node.js Runtime is the full Node.js environment with access to database drivers, filesystem, and npm packages. Edge is ideal for middleware, authentication checks, A/B testing, and geolocation redirects. Node.js is for data-heavy pages, database queries, image processing, and complex business logic. You set the runtime per route: export const runtime = 'edge' or 'nodejs'.

Senior Developer Insight

The edge runtime isn't universally faster — it's faster for simple, I/O-bound operations because it runs close to users. But for CPU-bound work (Markdown parsing, image resizing, complex database queries), Node.js can be faster because it has more compute power available and isn't limited by edge worker constraints. The real skill is knowing which runtime each route needs and not blindly choosing "edge" for everything.

Memory Trick: "Edge = fast bouncer at the door (lightweight checks). Node.js = heavy kitchen in the back (full processing power). Choose based on the task."
  • Edge: Web APIs only, no Node.js modules, global distribution, near-zero cold start
  • Node.js: Full Node.js, all NPM packages, native DB drivers
  • Set per route: export const runtime = 'edge' or 'nodejs'
  • Edge for middleware, auth, A/B tests. Node.js for DB operations, pages
  • Don't blindly use "edge" for everything — not always faster
