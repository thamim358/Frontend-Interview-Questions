01
What are the different types of state in a React application, and which tool should you use for each?
Intermediate P1
Short Answer

There are six categories of state in a modern React app: Local UI state (useState/useReducer), Global/Shared state (Context/Redux/Zustand), Server state (React Query/SWR), URL state (useSearchParams/router), Form state (React Hook Form/Formik), and Persisted state (localStorage/Zustand persist/redux-persist). Knowing which bucket each piece of state belongs in is the most important state management skill.

Easy Explanation

Think of state like clothes in your house. Some clothes you wear right now (local state — on your body), some are shared with your partner (global state — the closet), some come from Amazon deliveries (server state — fetched from outside), and some are permanently stored in the attic (persisted state). You wouldn't keep your socks in the attic or your winter coat on your body in summer. Same logic applies to React state.

The Six Categories

Local UITemporary, component-scopeduseState, useReducerModal open/close, toggle, input value
Global/SharedNeeded by many componentsContext, Redux, ZustandAuth user, theme, cart items
ServerFetched from API, cachedReact Query, SWRUser list, product catalog
URLIn the browser address baruseSearchParams, routerSearch query, page number, filter

Senior Insight

The #1 mistake I see in production React codebases is treating everything as global state. Developers shove server data into Redux, put form state in Context, and wonder why the app is slow and buggy. If the state doesn't survive a remount, useState is probably fine. If it comes from a server, use React Query. If you need it everywhere, only then reach for global state.

Common Mistakes

Putting server data in Redux and writing your own loading/error/caching logic (React Query does this 10x better). Storing ephemeral UI state (dropdown open, hover state) in a global store. Mixing form state with persisted state and accidentally overwriting user input on re-render.

Memory Trick: "Is it mine, ours, from outside, or forever?" — Local, Global, Server, or Persisted. Four buckets, always start local.
Follow-up Questions
  1. When would you not use React Query for server state?
  2. How do you decide between useState and useReducer for local state?
  3. What are the tradeoffs of putting state in the URL vs global store?
Summary
  • Six state categories: Local, Global, Server, URL, Form, Persisted
  • Match the tool to the state type — don't use one hammer for everything
  • Start local, lift only when needed, cache server data separately
  • React Query handles loading/error/caching/refetching for server state automatically
02
Redux Toolkit Deep Dive — createSlice, configureStore, createAsyncThunk, RTK Query, and how Immer works under the hood.
Advanced P1
Short Answer

Redux Toolkit (RTK) is the official, opinionated way to write Redux. It eliminates boilerplate by combining createSlice (actions + reducers together), configureStore (store setup with DevTools + middleware), createAsyncThunk (async actions with lifecycle), and RTK Query (data fetching and caching). Immer is baked in — you write "mutating" syntax inside reducers and Immer produces immutable updates.

The Old vs New Redux

Old Redux required: action type constants, action creators, switch-case reducers, combineReducers, applyMiddleware, and composing enhancers — all spread across separate files. Redux Toolkit collapses everything into a single createSlice call. A typical RTK slice is 20 lines versus 80+ in vanilla Redux.

TypeScript — Redux Toolkit slice with async thunk
import { createSlice, createAsyncThunk, configureStore } from '@reduxjs/toolkit';

// 1. Async thunk — fetch users from API
export const fetchUsers = createAsyncThunk<
  User[], void, { rejectValue: string }
>(
  'users/fetchUsers',
  async (_, { rejectWithValue }) => {
    try {
      const res = await fetch('/api/users');
      if (!res.ok) throw new Error('Failed');
      return await res.json();
    } catch (err) {
      return rejectWithValue((err as Error).message);
    }
  }
);

// 2. Slice — mutating syntax thanks to Immer
const usersSlice = createSlice({
  name: 'users',
  initialState: {
    items: [] as User[],
    status: 'idle' as 'idle' | 'loading' | 'succeeded' | 'failed',
    error: null as string | null,
  },
  reducers: {
    addUser(state, action: PayloadAction<User>) {
      state.items.push(action.payload); // Immer — looks mutable, is immutable
    },
    removeUser(state, action: PayloadAction<string>) {
      state.items = state.items.filter(u => u.id !== action.payload);
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending, (state) => {
        state.status = 'loading';
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.status = 'succeeded';
        state.items = action.payload;
      })
      .addCase(fetchUsers.rejected, (state, action) => {
        state.status = 'failed';
        state.error = action.payload ?? 'Unknown error';
      });
  },
});

// 3. Store — one-liner setup
export const store = configureStore({
  reducer: { users: usersSlice.reducer },
  // Thunk middleware + DevTools auto-enabled in dev
});

export const { addUser, removeUser } = usersSlice.actions;
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
Pro Tip — RTK Query

RTK Query is built into Redux Toolkit. It eliminates the need for createAsyncThunk for data fetching. You define an API slice with endpoints, and RTK Query auto-generates hooks, manages caching, and handles loading/error states. If you're fetching data with Redux, you should be using RTK Query, not hand-rolled async thunks.

TypeScript — RTK Query vs manual async thunks
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

// RTK Query: Define API once, get hooks + caching for free
export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User', 'Post'],
  endpoints: (builder) => ({
    getUsers: builder.query<User[], void>({
      query: () => 'users',
      providesTags: ['User'],
    }),
    addUser: builder.mutation<User, Partial<User>>({
      query: (body) => ({ url: 'users', method: 'POST', body }),
      invalidatesTags: ['User'], // Auto refetch getUsers
    }),
  }),
});

// Auto-generated hooks:
export const { useGetUsersQuery, useAddUserMutation } = api;
FAANG Insight

At scale, Redux's single global store becomes a bottleneck — every action goes through every reducer. Large apps often split into domain-specific stores or migrate to Zustand (simpler API, no Provider, same performance). Meta uses a custom Redux-like store internally. Airbnb uses Zustand. Netflix and Twitch use React Query + Context. The pattern matters more than the library.

Memory Trick: "Slice defines state + changes, Thunk handles async, RTK Query handles API, Immer makes mutations safe." — Four pillars of Redux Toolkit.
Summary
  • createSlice merges actions + reducers, configureStore replaces createStore
  • createAsyncThunk provides pending/fulfilled/rejected lifecycle for async ops
  • RTK Query is the modern replacement for hand-rolled data fetching in Redux
  • Immer lets you write mutable-looking code; Redux Toolkit Immer is enabled by default
  • Consider whether you even need Redux — Zustand or Context + React Query often suffice
03
Zustand Deep Dive — how does it work, and why do developers love the "no Provider" pattern?
Advanced P1
Short Answer

Zustand is a tiny (1.1 KB), unopinionated state management library. Unlike Redux and Context, it doesn't require a Provider to wrap your component tree. You create a store with create(), which returns a hook — call that hook in any component to read/write state. Zustand uses React 18's useSyncExternalStore under the hood for rendering, has excellent selector support, and supports middleware (persist, immer, devtools) as simple wrapper functions.

Why "No Provider" Matters

Provider-based stores (Context, Redux) wrap your entire app, causing every consumer to potentially re-render. Zustand stores are external to React — they're plain JavaScript objects. React components subscribe via hooks, and Zustand compares values itself. This means zero extra wrapper components, no provider drilling, and fine-grained re-renders controlled by selectors.

TypeScript — Zustand store with multiple middlewares
import { create } from 'zustand';
import { persist, devtools } from 'zustand/middleware';
import { immer } from 'zustand/middleware/immer';

interface CartStore {
  items: CartItem[];
  total: number;
  addItem: (item: CartItem) => void;
  removeItem: (id: string) => void;
  clearCart: () => void;
}

export const useCartStore = create<CartStore>()(
  devtools(
    persist(
      immer((set) => ({
        items: [],
        total: 0,
        addItem: (item) =>
          set((state) => {
            state.items.push(item);
            state.total += item.price;
          }),
        removeItem: (id) =>
          set((state) => {
            const idx = state.items.findIndex(i => i.id === id);
            if (idx !== -1) {
              state.total -= state.items[idx].price;
              state.items.splice(idx, 1);
            }
          }),
        clearCart: () => set({ items: [], total: 0 }),
      })),
      { name: 'cart-storage' } // Auto-persist to localStorage
    ),
    { name: 'CartStore' } // Redux DevTools label
  )
);

// Usage — no Provider needed!
function CartButton() {
  // Fine-grained selector: only re-renders when count changes
  const itemCount = useCartStore(s => s.items.length);
  return <button>Cart ({itemCount})</button>;
}

function CartTotal() {
  // Only re-renders when total changes — not when items change
  const total = useCartStore(s => s.total);
  return <span>${total.toFixed(2)}</span>;
}
Selector Performance

Zustand uses Object.is for shallow comparison by default. If your selector returns a new object/reference every time, it'll cause unnecessary re-renders. Use useShallow() when selecting multiple values: useCartStore(useShallow(s => ({ count: s.items.length, total: s.total }))).

Senior Insight — Zustand's Secret Sauce

Zustand leverages React 18's useSyncExternalStore — the same API used by Redux and React Query. This ensures correct behavior with concurrent rendering. But the real magic is how simple it is: the store is literally a module-level variable. You can read/write from outside React (e.g., WebSocket handlers, service workers, tests). This makes Zustand far more flexible than Context or even Redux.

Memory Trick: "Zustand = global variable + React hook subscription." No Provider, no boilerplate, just a hook you call anywhere.
Summary
  • Zustand stores live outside React — no Provider needed
  • Uses useSyncExternalStore for concurrent safety
  • Selectors give fine-grained re-render control
  • Middleware (persist, immer, devtools) compose as wrapper functions
  • Can be accessed outside React — perfect for non-React code paths
04
React Query (TanStack Query) — useQuery, useMutation, staleTime vs gcTime, and cache invalidation.
Advanced P1
Short Answer

TanStack Query (previously React Query) is a server-state management library. It handles fetching, caching, synchronizing, and updating server state in React apps. The core primitives are useQuery (fetch and cache data), useMutation (create/update/delete and invalidate), staleTime (how long data is "fresh" before background refetch), gcTime (how long inactive cache data lives before garbage collection), and invalidateQueries (mark queries as stale for refetch).

staleTime vs gcTime — The Most Confused Concepts

staleTime (default 0ms): Duration after which data is considered "stale" and eligible for background refetch. While fresh, React Query returns cache data without refetching. Think of it as the "freshness guarantee."
gcTime (default 5min): How long React Query keeps inactive/unused cache data before removing it from memory (garbage collection). Think of it as the "retention period." If a component re-mounts within gcTime, cached data is served instantly.

TypeScript — React Query comprehensive example
import {
  useQuery,
  useMutation,
  useQueryClient,
} from '@tanstack/react-query';
import { fetchPosts, deletePost, createPost } from './api';

function PostList() {
  const queryClient = useQueryClient();

  // staleTime: 30s — data is "fresh" and won't refetch
  // gcTime: 10min — cache survives unmount for 10min
  const { data, isLoading, error, refetch } = useQuery({
    queryKey: ['posts'],
    queryFn: fetchPosts,
    staleTime: 30 * 1000,
    gcTime: 10 * 60 * 1000,
    retry: 3, // Retry 3 times on failure
    enabled: true, // Conditional fetching
  });

  // Mutation: create a post, then invalidate the list
  const createMutation = useMutation({
    mutationFn: createPost,
    onSuccess: () => {
      // Invalidate = mark stale = trigger refetch
      queryClient.invalidateQueries({ queryKey: ['posts'] });
    },
    onSettled: () => {
      // Always runs after success or error — cleanup, analytics, etc.
    },
  });

  const deleteMutation = useMutation({
    mutationFn: deletePost,
    onMutate: async (id) => {
      // Cancel outgoing refetches to avoid overwriting optimistic update
      await queryClient.cancelQueries({ queryKey: ['posts'] });
      // Snapshot previous value for rollback
      const previous = queryClient.getQueryData(['posts']);
      // Optimistically remove the post
      queryClient.setQueryData(['posts'], (old) =>
        old?.filter(p => p.id !== id)
      );
      return { previous }; // Context for onError rollback
    },
    onError: (err, id, context) => {
      // Rollback on failure
      if (context?.previous) {
        queryClient.setQueryData(['posts'], context.previous);
      }
    },
  });

  if (isLoading) return <Skeleton />;
  if (error) return <Error message={error.message} />;

  return (
    <div>
      {data?.map(post => (
        <PostItem
          key={post.id}
          post={post}
          onDelete={() => deleteMutation.mutate(post.id)}
        />
      ))}
    </div>
  );
}
Remember This

React Query manages server state — it is NOT a replacement for global state (Zustand/Redux). It's a cache, not a store. Don't put local UI state in React Query. If you find yourself calling setQueryData for non-server data, you're abusing it.

Memory Trick: "staleTime = freshness guarantee. gcTime = memory retention." stale controls when to refetch, gcTime controls when to delete from memory.
Summary
  • useQuery for reads, useMutation for writes, invalidateQueries to refresh
  • staleTime: data stays "fresh" and skips refetch; gcTime: keeps cache in memory
  • React Query is a server cache, not a general-purpose state manager
  • Optimistic updates via onMutate/onError/onSettled for instant-feel UI
  • Default staleTime is 0 — every mount triggers a refetch unless you set it
05
Context API — When is it enough and when is it NOT? What's the performance problem?
Intermediate P1
Short Answer

Context API is ideal for low-frequency, static-ish global data — themes, locale, auth user, feature flags. It fails for high-frequency, frequently-updating state (form values, animation frames, real-time feeds) because every consumer of a Context re-renders when its value changes, even if it only uses a subset of that value. There's no built-in way to subscribe to a slice of context — you get all-or-nothing re-renders.

The Performance Problem Explained

When you do <MyContext.Provider value={{ counter, user, theme }}>, that object is recreated every render of the parent. Every child that calls useContext(MyContext) re-renders when the parent renders — even if it only reads theme and counter/user haven't changed. The fix is to split into multiple contexts (one for theme, one for user, one for counter) so components only subscribe to the data they actually use.

TypeScript — Splitting context to avoid unnecessary re-renders
// BAD: One big context — EVERYTHING re-renders when ANYTHING changes
const AppContext = createContext<AppState>(null!);
// Header only uses theme, but re-renders when user/cart change
// Sidebar only uses user, but re-renders when theme/cart change

// GOOD: Split by update frequency
const ThemeContext = createContext<Theme>('light');     // Changes rarely
const AuthContext = createContext<Auth>(null!);       // Changes on login/logout
const CartContext = createContext<CartControls>(null!); // Changes frequently

function AppProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  const [user, setUser] = useState<User | null>(null);
  const [cart, setCart] = useState<Item[]>([]);

  const themeValue = useMemo(() => ({ theme, setTheme }), [theme]);
  const authValue = useMemo(() => ({ user, setUser }), [user]);
  const cartValue = useMemo(() => ({ cart, setCart }), [cart]);

  return (
    <ThemeContext.Provider value={themeValue}>
      <AuthContext.Provider value={authValue}>
        <CartContext.Provider value={cartValue}>
          {children}
        </CartContext.Provider>
      </AuthContext.Provider>
    </ThemeContext.Provider>
  );
}
Common Mistakes

Using Context for everything just to avoid prop drilling. Context IS NOT a state management tool — it's a dependency injection mechanism. It has no selectors, no memoization, no middleware. If you need any of those, reach for Zustand. Also: forgetting useMemo on context values — without it, you're creating a new object every render and defeating the purpose.

What Big Companies Do

Airbnb uses a combination of Context + Zustand. Vercel uses Context for theme + React Query for server state. Spotify uses Redux but keeps slices small. The pattern at scale: Context for static globals (theme, locale), specialized libraries for high-frequency or server state.

Memory Trick: "Context is a pipe, not a tank." It transports data down the tree. If you need a tool that manages, selects, and optimizes that data, use a state library.
Summary
  • Context is perfect for theme, auth, locale — infrequently changing data
  • Every consumer re-renders when context value changes — no selective subscription
  • Split contexts by update frequency to avoid unnecessary re-renders
  • For high-frequency state, use Zustand/Redux with selectors instead
06
Server State vs Client State — Why server data doesn't belong in Redux, and the right caching patterns.
Advanced P1
Short Answer

Client state is data you own and control locally (UI toggles, form inputs, current user selection). Server state is data you fetched from an API — it's a snapshot of truth owned by the server, not by your app. Putting server state in Redux is problematic because: (1) it goes stale the moment you fetch it, (2) you end up writing boilerplate for loading/error/caching/refetching/retry/optimistic updates, and (3) you're duplicating data that the backend owns. React Query handles all of this out of the box.

The Architecture Shift

In 2020, Redux was the default for everything. In 2025, the pattern is: React Query (or SWR) for ALL server data, Zustand (or Context) for the little remaining client state. Your global store shrinks from hundreds of kilobytes to maybe 5-10 fields. This is called the "thin store" pattern.

TypeScript — Before vs After: Removing server state from Redux
// BEFORE: Redux holds everything (bad)
interface OldStore {
  // Server state — gets stale
  posts: { data: Post[]; loading: boolean; error: string | null };
  users: { data: User[]; loading: boolean; error: string | null };
  comments: Record<string, Comment[]>;
  // Client state — tiny
  theme: Theme;
  sidebarOpen: boolean;
  currentView: View;
}

// AFTER: Redux/Zustand holds ONLY client state
interface NewStore {
  // Client state only — no server data
  theme: Theme;
  sidebarOpen: boolean;
  currentView: View;
}
// Server state lives in React Query cache — auto-managed
When CAN server state go in Redux?

Rarely: when your app is fully offline-first and you need a local source of truth that syncs to the server. Even then, consider using RTK Query (which IS Redux) or pairing Redux with a persistence layer. But for 95% of apps, the thin store pattern is correct.

Memory Trick: "If it lives on a server, it lives in React Query. If you made it up, it lives in Redux/Zustand." Server = React Query. Client = your choice of store.
Summary
  • Server state is a cache, not a database — it's stale by definition
  • React Query handles loading/error/caching/refetching/mutations — you don't write this code
  • Thin store pattern: global store shrinks to 5-10 fields of pure client state
  • RTK Query bridges the gap if you're committed to Redux

Optimistic Updates — How to implement them with React Query and why they matter for UX.
Advanced P1
Short Answer

An optimistic update updates the UI immediately before the server confirms the change, then rolls back if the server returns an error. React Query supports this through the onMutate (update cache immediately), onError (rollback from snapshot), and onSettled (invalidate to sync with server) callbacks in useMutation. The UX difference is dramatic — Amazon's "add to cart," WhatsApp's "message sent" checkmarks, and Twitter's "like" are all optimistic.

The Pattern

1. onMutate: Cancel outgoing queries (avoid race conditions), snapshot the current cache, optimistically update the cache.
2. onError: Roll back to the snapshot.
3. onSettled: Invalidate queries so the server is the final source of truth.

TypeScript — Optimistic update for a todo app
const toggleTodo = useMutation({
  mutationFn: async (todoId: string) => {
    const res = await fetch(`/api/todos/${todoId}/toggle`, { method: 'PATCH' });
    if (!res.ok) throw new Error('Network error');
    return res.json();
  },

  onMutate: async (todoId) => {
    // 1. Cancel in-flight refetches (race condition guard)
    await queryClient.cancelQueries({ queryKey: ['todos'] });

    // 2. Snapshot previous todos for rollback
    const previousTodos = queryClient.getQueryData(['todos']);

    // 3. Optimistically toggle the todo
    queryClient.setQueryData(['todos'], (old: Todo[] | undefined) =>
      old?.map(t =>
        t.id === todoId ? { ...t, completed: !t.completed } : t
      ) ?? []
    );

    // 4. Return snapshot — received as `context` in onError / onSettled
    return { previousTodos };
  },

  onError: (err, todoId, context) => {
    // Rollback: restore the snapshot
    if (context?.previousTodos) {
      queryClient.setQueryData(['todos'], context.previousTodos);
    }
    toast('Failed to update todo');
  },

  onSettled: () => {
    // Always refetch to sync with server truth
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});
Real-World Example

WhatsApp messages: The message appears instantly in the chat. The single checkmark means "sent to server." Double checkmark means "delivered to recipient." If sending fails, the message gets a red warning icon. This is optimistic update + status indicators. Same logic with Twitter likes — the heart turns red instantly, and if the API call fails, it toggles back.

Common Mistakes

Forgetting to cancel outgoing queries — if you don't, a stale query refetch might overwrite your optimistic update before the mutation completes. Also: not returning the snapshot from onMutate — without it, onError has nothing to roll back to.

Memory Trick: "Show first, ask later. If it fails, take it back." Optimistic = instant UI + rollback safety net.
Summary
  • Optimistic updates make apps feel instant by updating UI before server response
  • onMutate: cancel queries, snapshot, update cache — return snapshot as context
  • onError: rollback to snapshot
  • onSettled: invalidate to resync with server
  • Used by WhatsApp, Twitter, Amazon, GitHub — every great app does this

useReducer Pattern — When to use it over useState, and how it gives you Redux-like power without Redux.
Intermediate P1
Short Answer

useReducer is React's built-in state management for complex state logic. Instead of setting values directly (like useState), you dispatch actions that a reducer function processes to produce the next state: (state, action) => newState. Use it when: (1) the next state depends on the previous state in a non-trivial way, (2) multiple state values change together, or (3) you want to colocate update logic. It's Redux without the library — same mental model, no dependencies.

useState vs useReducer — Decision Framework
useStateuseReducer
Simple value: string, number, booleanComplex object/array that changes atomically
Independent state valuesValues that change together (e.g., form)
Update logic is trivialUpdate logic has multiple branches (if/switch)
Single setter call covers the logicMultiple actions modify the same state
Toggle, input value, modal openMulti-step form, undo/redo, game state
TypeScript — useReducer for a multi-step checkout form
type CheckoutState = {
  step: 'shipping' | 'payment' | 'review' | 'confirmed';
  shipping: Address | null;
  payment: CardInfo | null;
  coupon: string;
  discount: number;
  errors: Record<string, string>;
};

type CheckoutAction =
  | { type: 'SET_SHIPPING'; address: Address }
  | { type: 'SET_PAYMENT'; card: CardInfo }
  | { type: 'NEXT_STEP' }
  | { type: 'PREV_STEP' }
  | { type: 'APPLY_COUPON'; code: string; discount: number }
  | { type: 'SET_ERROR'; field: string; message: string }
  | { type: 'RESET' };

const steps: CheckoutState['step'][] = ['shipping', 'payment', 'review', 'confirmed'];

function checkoutReducer(state: CheckoutState, action: CheckoutAction): CheckoutState {
  switch (action.type) {
    case 'SET_SHIPPING':
      return { ...state, shipping: action.address, errors: {} };
    case 'SET_PAYMENT':
      return { ...state, payment: action.card, errors: {} };
    case 'NEXT_STEP': {
      const idx = steps.indexOf(state.step);
      return { ...state, step: steps[idx + 1], errors: {} };
    }
    case 'PREV_STEP': {
      const idx = steps.indexOf(state.step);
      return { ...state, step: steps[idx - 1], errors: {} };
    }
    case 'APPLY_COUPON':
      return { ...state, coupon: action.code, discount: action.discount };
    case 'SET_ERROR':
      return { ...state, errors: { ...state.errors, [action.field]: action.message } };
    case 'RESET':
      return initialCheckoutState();
    default:
      return state;
  }
}

function CheckoutFlow() {
  const [state, dispatch] = useReducer(checkoutReducer, null, initialCheckoutState);

  // Easy testing: dispatch actions, assert state
  // Clean separation: UI components only dispatch — never compute state
  // Predictable: given same state + action, always same result

  if (state.step === 'confirmed') return <Confirmation state={state} />;
  return (
    <div>
      {state.step === 'shipping' &&
        <ShippingForm onSubmit={a => dispatch({ type: 'SET_SHIPPING', address: a })} />}
      {state.step === 'payment' &&
        <PaymentForm onSubmit={c => dispatch({ type: 'SET_PAYMENT', card: c })} />}
    </div>
  );
}
useReducer + Context = Redux Lite

Combine useReducer with Context to share state across components without Redux: put the [state, dispatch] in a context, and any child can read state and dispatch actions. This is a valid pattern for medium-complexity apps. Just remember: as your app grows, you'll eventually want selectors (less re-rendering) and middleware — that's when you graduate to Zustand.

Memory Trick: "useState for simple. useReducer when next state depends on previous in a branching way." If your state update has an if/switch, use useReducer.
Summary
  • useReducer = dispatch actions → reducer produces new state (Redux pattern, no library)
  • Best for: multi-step flows, form wizards, game logic, undo/redo
  • Pair with Context for shared state (Redux-lite pattern)
  • Testable: reducer is a pure function — easy to unit test

State Normalization — Flat entities, entity adapters, and why nested data structures are a performance trap.
Advanced P1
Short Answer

State normalization means storing data as flat key-value maps instead of nested trees, similar to database tables. Each entity type gets its own "table" with an ids array and an entities map. This avoids: (1) deeply nested state that's hard to update immutably, (2) duplicate data across different parts of the tree, and (3) re-rendering entire subtrees when one item changes. Redux Toolkit provides createEntityAdapter to manage this pattern automatically.

Nested vs Normalized
Before vs After: Normalized state shape
// BAD: Nested — updating a comment requires deep path traversal
{
  posts: [
    {
      id: 1,
      title: 'Hello',
      comments: [
        { id: 100, text: 'Nice!', author: { id: 5, name: 'Alice' } },
        { id: 101, text: 'Great!', author: { id: 5, name: 'Alice' } }, // Duplicate author!
      ],
    }
  ]
}

// GOOD: Normalized — flat, no duplication, O(1) access
{
  posts: {
    ids: [1],
    entities: { '1': { id: 1, title: 'Hello', comments: [100, 101] } }
  },
  comments: {
    ids: [100, 101],
    entities: {
      '100': { id: 100, text: 'Nice!', authorId: 5 },
      '101': { id: 101, text: 'Great!', authorId: 5 }
    }
  },
  users: {
    ids: [5],
    entities: { '5': { id: 5, name: 'Alice' } } // Single source of truth
  }
}
TypeScript — createEntityAdapter
import { createEntityAdapter, createSlice } from '@reduxjs/toolkit';

interface Book { id: string; title: string; author: string; rating: number; }

  // Use 'isbn' as the ID instead of 'id'
  selectId: b => b.id,
  // Sort by rating descending
  sortComparer: (a, b) => b.rating - a.rating,
});

const booksSlice = createSlice({
  name: 'books',
  initialState: booksAdapter.getInitialState({
    loading: 'idle', // Extra non-entity state
  }),
  reducers: {
    bookAdded: booksAdapter.addOne,
    booksAdded: booksAdapter.addMany,
    bookUpdated: booksAdapter.updateOne,   // Partial update
    bookRemoved: booksAdapter.removeOne,
  },
});

// Auto-generated selectors — zero boilerplate
export const {
  selectAll: selectAllBooks,     // Array, sorted
  selectById: selectBookById,   // O(1) lookup
  selectIds: selectBookIds,     // ID array only
  selectTotal: selectBookTotal, // Count
} = booksAdapter.getSelectors<RootState>(s => s.books);
Why This Matters at Scale

Imagine Reddit with 50,000 comments nested under each other. Updating one deeply nested comment requires deep-cloning the entire tree up to the root — an O(n) operation. With normalized state, it's an O(1) update on a single entity. Same logic applies to React Query's cache when you structure query data as flat references.

Memory Trick: "Entities as maps, IDs as arrays. No nesting, no duplicates, no deep updates." Your state is a database, not a tree.
Summary
  • Normalization = flat key-value maps like database tables
  • Benefits: no duplicates, O(1) lookups, simple immutable updates
  • createEntityAdapter handles CRUD + sorting + selectors automatically
  • Apply to React Query caches too — structure data as flat references

Immer — How does "mutable syntax, immutable results" actually work?
Advanced P1
Short Answer

Immer is a library that lets you write mutable-looking code that produces immutable results. It works using JavaScript Proxy objects: when you call produce(baseState, recipe), Immer creates a Proxy that intercepts all mutations (assignments, pushes, deletes), records them in a "draft," and then constructs the new immutable state tree by applying only the changes to the original base. The original is never modified. Redux Toolkit bundles Immer so all createSlice reducers use it automatically.

How Immer Works Under the Hood

1. Immer creates a Proxy wrapping your base object (e.g., { name: 'John', age: 30 }).
2. When you do draft.age = 31, the Proxy's set trap records "age changed from 30 to 31" and marks that node as modified.
3. When the recipe finishes, Immer walks the object tree: if a node was modified, it creates a shallow copy with the changes applied. If a node was NOT modified, it reuses the original reference (structural sharing).
4. The result is an entirely new top-level object, but unmodified subtrees are shared with the original — minimizing memory.

JavaScript — Immer produce() examples
import produce from 'immer';

const base = {
  user: { name: 'Alice', address: { city: 'NYC' } },
  tags: ['react', 'typescript'],
};

const next = produce(base, (draft) => {
  draft.user.address.city = 'SF';       // Deep update, looks mutable
  draft.tags.push('javascript');            // Array push without spread!
  draft.user.lastLogin = new Date();      // Add new property
});

// base is untouched — Immer returned a new object
console.log(base.user.address.city);   // 'NYC'
console.log(next.user.address.city);   // 'SF'
console.log(base.tags.length);          // 2
console.log(next.tags.length);          // 3

// Structural sharing: unmodified subtrees are the same reference
console.log(base.user === next.user);           // false (parent changed)
console.log(base.user.name === next.user.name); // true  (string didn't change)

// Curried produce: returns a function
const addTag = produce(draft, tag => {
  draft.tags.push(tag);
});
const next2 = addTag(base, 'css');
Immer in Redux Toolkit

Every reducer in a createSlice is wrapped in Immer's produce(). You can write state.items.push(action.payload) and Redux Toolkit handles the immutability. But there's a catch: you must either mutate the draft OR return a new value, never both. If you return a value, Immer ignores any mutations you made to the draft.

Memory Trick: "Immer = Proxy that tracks what you change, then builds a new object using only the changes." Write like JavaScript, get immutability for free.
Summary
  • Immer uses Proxies to record mutations, then produces an immutable result
  • Structural sharing: unmodified parts of the tree are re-used by reference
  • Built into Redux Toolkit — all createSlice reducers auto-wrapped
  • Mutate the draft XOR return a new value — never both in the same reducer
  • Independent of React — works with any JavaScript codebase

Core Difference

Zustand uses a single store (like Redux but simpler). Jotai and Recoil use atomic state — each piece of state is its own independent "atom." Jotai is essentially the open-source spiritual successor to Recoil (Meta abandoned Recoil in 2024).

Decision Rule

Use Zustand for most apps — simplest API, smallest bundle, most battle-tested. Use Jotai when you need fine-grained derived state or when your state naturally decomposes into independent atoms (like a design tool with many independent properties). Never choose Recoil for new projects — it's abandoned.

Memory Trick: "Zustand for stores. Jotai for atoms. Recoil for legacy." — Choose based on whether you want a store or independent atoms.

Redux Middleware — Thunk, Logger, persist, and how to write custom middleware.
Advanced P2
What Is Middleware?

Middleware is a pipeline that sits between dispatch(action) and the reducer. Every action passes through the middleware chain before reaching the reducer. This lets you intercept, log, modify, delay, or cancel actions. Middleware is a functional composition pattern: middleware = store => next => action => { ... next(action) ... }.

TypeScript — Custom crash reporter middleware
import { Middleware } from '@reduxjs/toolkit';

const crashReporter: Middleware = (storeApi) => (next) => (action) => {
  try {
    console.group(action.type);
    console.log('Before:', storeApi.getState());
    console.log('Action:', action);
    const result = next(action); // Pass to next middleware or reducer
    console.log('After:', storeApi.getState());
    console.groupEnd();
    return result;
  } catch (err) {
    console.error('Redux crash:', err);
    Sentry.captureException(err, { extra: { action, state: storeApi.getState() } });
    throw err;
  }
};

// Usage with configureStore:
configureStore({
  reducer: rootReducer,
  middleware: getDefaultMiddleware() =>
    getDefaultMiddleware().concat(crashReporter, logger),
});

Form State Management — React Hook Form + Zod, controlled vs uncontrolled patterns.
Intermediate P2
Controlled vs Uncontrolled

Controlled: React state is the single source of truth. Every keystroke triggers a state update and re-render. Good for real-time validation, bad for large forms.
Uncontrolled: The DOM manages the value. React hooks in to get values on submit. Faster, fewer re-renders. React Hook Form uses uncontrolled by default.

TypeScript — React Hook Form + Zod validation
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const schema = z.object({
  email: z.string().email('Invalid email'),
  password: z.string().min(8, 'Minimum 8 characters'),
  age: z.number({ invalid_type_error: 'Required' }).min(18),
});

type FormData = z.infer<typeof schema>;

function SignupForm() {
  const { register, handleSubmit, formState: { errors } } =
    useForm<FormData>({ resolver: zodResolver(schema) });

  const onSubmit = async (data: FormData) => {
    // data is fully typed and validated
    await api.signup(data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('email')} />
      {errors.email && <span>{errors.email.message}</span>}

      <input type="password" {...register('password')} />
      {errors.password && <span>{errors.password.message}</span>}

      <input type="number" {...register('age', { valueAsNumber: true })} />
      {errors.age && <span>{errors.age.message}</span>}

      <button type="submit">Sign Up</button>
    </form>
  );
}
Why React Hook Form + Zod?

RHF is uncontrolled by default (fast), has tiny bundle (10KB), handles validation with any library (Zod, Yup, Joi), and exposes field-level errors. Zod gives you type-safe validation that infers TypeScript types from schemas — no need to define types twice. Together they reduce form code by 60-70% compared to raw controlled inputs.

URL State — useSearchParams, shareable/bookmarkable state, and why the URL is the best state manager.
Intermediate P2
Why URL State Matters

The URL is the original global state manager. It persists across refreshes, is shareable via copy-paste, bookmarks work naturally, and the browser's back/forward buttons handle undo/redo for free. For anything that should be shareable — search queries, filter selections, current page, selected tab — the URL is the right answer, not Redux or Context.

TypeScript — useSearchParams for filters + pagination
import { useSearchParams } from 'react-router-dom';

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();

  const page = Number(searchParams.get('page')) || 1;
  const query = searchParams.get('q') || '';
  const sort = searchParams.get('sort') || 'newest';
  const category = searchParams.get('category') || 'all';

  const updateFilter = (key: string, value: string) => {
    const next = new URLSearchParams(searchParams);
    if (value) {
      next.set(key, value);
    } else {
      next.delete(key);
    }
    next.set('page', '1'); // Reset page on filter change
    setSearchParams(next);
  };

  // URL is now: /products?q=shoe&sort=price-asc&page=1&category=men
  // Share this URL — recipient sees the exact same results

  // Fetch products based on URL params (React Query)
  const { data } = useQuery({
    queryKey: ['products', { page, query, sort, category }],
    queryFn: () => fetchProducts({ page, query, sort, category }),
  });
}
Senior Insight

Amazon product search URLs are the perfect example: the URL encodes every filter, sort order, and page number. Copy the URL to another tab and everything is restored. This is superior to storing filters in Redux because it's trivially shareable. As a rule: if you'd email the state to a colleague, put it in the URL.

Undo/Redo Pattern — History stack and state snapshots.
Advanced P2
The Pattern

Maintain three arrays: past (previous states), present (current state), future (states after undo). Each state change pushes the current present onto past, and sets present to the new state. Undo: move present to future, shift past to present. Redo: move present to past, shift future to present. Clear future when a new action occurs (any redo-only branch dies).

TypeScript — Undo/Redo hook
interface UndoState<T> { past: T[]; present: T; future: T[]; }

function useUndo<T>(initial: T) {
  const [state, dispatch] = useReducer(
    undoReducer<T>,
    { past: [], present: initial, future: [] }
  );

  const undo = useCallback(() => {
    if (state.past.length === 0) return;
    const previous = state.past[state.past.length - 1];
    dispatch({
      past: state.past.slice(0, -1),
      present: previous,
      future: [state.present, ...state.future],
    });
  }, [state]);

  const redo = useCallback(() => {
    if (state.future.length === 0) return;
    dispatch({
      past: [...state.past, state.present],
      present: state.future[0],
      future: state.future.slice(1),
    });
  }, [state]);

  const update = useCallback((next: T) => {
    dispatch({
      past: [...state.past, state.present],
      present: next,
      future: [], // Clear redo stack on new change
    });
  }, [state]);

  return { present: state.present, undo, redo, update,
    canUndo: state.past.length > 0,
    canRedo: state.future.length > 0 };
}
When to mention this in an interview

If you're asked "how would you build a drawing app?" or "how would you implement undo?" — this is the answer. Figma, Canva, Excalidraw all use variations of this pattern. Bonus points if you mention command pattern: store actions instead of state snapshots for memory efficiency (undo = reverse-apply command, not restore entire state).

Cross-tab State Sync — BroadcastChannel and storage events.
Advanced P2
Two Approaches

BroadcastChannel: Dedicated API for cross-tab messaging. Send structured data between same-origin tabs. Works in all modern browsers. Perfect when you control both the sender and receiver.
storage event: The window.addEventListener('storage') fires when localStorage changes in another tab (not the current one). Good as a fallback or for libraries that already persist to localStorage.

TypeScript — Zustand cross-tab sync
const useStore = create(
  persist(
    (set) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) }),
    { name: 'counter' }
  )
);

// Listen for changes from OTHER tabs
window.addEventListener('storage', (e) => {
  if (e.key === 'counter' && e.newValue) {
    const parsed = JSON.parse(e.newValue);
    useStore.setState(parsed.state); // Directly set zustand state
  }
});

// Alternative: BroadcastChannel (cleaner API)
const channel = new BroadcastChannel('app-state');
channel.onmessage = (event) => {
  useStore.setState(event.data);
};

// When state changes locally, broadcast to other tabs
useStore.subscribe(state => channel.postMessage(state));
Real Usage

Notion syncs notes across tabs. Google Docs shows live cursors from other users (cross-tab + WebSocket). Spotify Web syncs the currently playing track between tabs. The combination of localStorage for persistence + BroadcastChannel/storage events for sync covers 90% of cross-tab use cases.

Real-time State — WebSocket + React Query cache updates for live data.
Expert P2
The Pattern

WebSocket pushes data to your app; React Query's cache acts as the single source of truth for that data in the UI. The WebSocket listener calls queryClient.setQueryData() to update the cache directly — no refetch needed. React Query then notifies all subscribed components of the change. This avoids: loading spinners on live data, duplicate network requests, and stale UI.

TypeScript — WebSocket + React Query integration
function useRealtimePosts() {
  const queryClient = useQueryClient();

  useEffect(() => {
    const ws = new WebSocket('wss://api.example.com/live');

    ws.onmessage = (event) => {
      const update: PostUpdate = JSON.parse(event.data);

      switch (update.type) {
        case 'POST_CREATED':
          // Prepend to cached posts list
          queryClient.setQueryData(['posts'], (old: Post[] = []) =>
            [update.post, ...old]
          );
          break;

        case 'POST_LIKED':
          // Update single post in-place
          queryClient.setQueryData(['posts'], (old: Post[] = []) =>
            old.map(p =>
              p.id === update.postId
                ? { ...p, likes: p.likes + 1 }
                : p
            )
          );
          break;

        case 'POST_DELETED':
          queryClient.setQueryData(['posts'], (old: Post[] = []) =>
            old.filter(p => p.id !== update.postId)
          );
          break;
      }
    };

    return () => ws.close();
  }, [queryClient]);

  // Also fetch initial data via REST/GraphQL
  return useQuery({ queryKey: ['posts'], queryFn: fetchPosts });
}
Senior Insight

The WebSocket is just a transport — don't use it as your state manager. React Query's cache should always be the final source of truth in the UI. The WebSocket only writes to the cache; components only read from the cache. This separation makes debugging, testing, and offline handling (websocket disconnected = stale cache shown = still usable) much easier.
