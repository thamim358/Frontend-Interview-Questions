Design a Large-Scale React App for 10M+ Users
Expert P1
The Question

"Design the frontend architecture for a social media platform with 10 million daily active users. The app has a news feed, real-time notifications, user profiles, direct messaging, and a media uploader. Walk me through your folder structure, state architecture, performance strategy, monitoring, and CI/CD pipeline."

Why feature-first: Each feature team (Feed Team, Messaging Team) owns their directory. They can ship independently. A feature's index.ts acts as a public API contract — no importing internal components directly. This enforces boundaries without micro-frontend complexity. Facebook's internal React codebase follows a similar structure with tens of thousands of components.

2. State Architecture — Layered by Concern
LayerToolPurposeExample
Server StateReact Query v5All data from the API — caching, refetching, optimistic updatesFeed posts, user data, messages
Client StateZustandUI state that lives only in the browserActive tab, sidebar open, draft message

The rule: Start with the URL for shareable state. Use React Query for all server data — never put server data in Zustand/Redux (that's double-caching and a source of staleness bugs). Zustand only for client-only UI state. React Query's staleTime and gcTime (formerly cacheTime) are the most important knobs: set staleTime: 30000 (30s) for feed data, staleTime: Infinity for rarely-changing data like user profiles. Facebook learned the hard way — their News Feed used to be in Redux/Flux and had constant staleness bugs until they moved to a normalized cache with server-driven invalidation.

3. Performance Strategy — Render Less, Load Less, Ship Less

a) Virtualization everywhere: Feeds with 1000+ items MUST use windowing. react-virtuoso for lists, react-virtuoso for grids. Without virtualization, rendering 500 DOM nodes per scroll position burns the main thread — INP (Interaction to Next Paint) metrics will fail.

b) Code splitting at three levels: (1) Route-level: every page is React.lazy() loaded. (2) Component-level: heavy components (rich text editor, emoji picker, video player) load only when visible via IntersectionObserver. (3) Conditional-level: locale files, admin tools, debug panels load only for specific users.

c) Image optimization pipeline: Use next/image or a custom image CDN (Imgix, Cloudinary). Serve WebP/AVIF with <picture> fallbacks. Lazy-load all images below the fold. Generate blur placeholders server-side. Reserve space with aspect-ratio CSS to prevent CLS.

d) SSR + Streaming: Use Next.js App Router with React Server Components. Critical path (header, sidebar, initial post skeleton) renders on the server and streams HTML. Client-side hydration is selective (progressive hydration). Non-critical components (comments, related posts) hydrate when idle or on interaction.

e) Prefetching: Prefetch links on hover/touchstart (<Link prefetch>). Prefetch data when a user is likely to navigate (React Query's queryClient.prefetchQuery in route loaders). The goal: navigation feels like a SPA but has SSR-quality first paint.

4. Monitoring & Observability

Error tracking: Sentry with React Error Boundary integration. Every caught error provides a stack trace, user context, and breadcrumbs (last 30 user actions). Source maps uploaded during CI — never serve source maps to clients.

Performance monitoring: Datadog RUM or New Relic Browser. Track Core Web Vitals (LCP, CLS, INP) per route, per device type, per geography. Set up alerts: if P75 LCP exceeds 2.5s on the feed page for Android devices in India, the on-call engineer gets paged.

Business metrics: Custom events via Amplitude/Mixpanel — "time to first post render", "message send success rate", "feed scroll depth". These tell you if performance problems are actually hurting users.

The Scaling Mindset

At 10M users, you stop optimizing for the average user and start optimizing for the P95 user. The median user on WiFi + iPhone 15 is fine. The P95 user on a throttled 3G connection in a rural area with a $50 Android phone is who defines your performance budget. Every architecture decision should answer: "Does this make the P95 experience better or worse?" Server-side rendering helps the P95. Large client-side JS hurts the P95. Edge computing helps the P95. Heavy third-party scripts in the critical path hurt the P95. This is why Google, Facebook, and Amazon test on low-end devices and slow networks — the average case takes care of itself.

How FAANG Actually Does It

Facebook: News Feed uses a custom framework (React + Relay + GraphQL). The feed is rendered server-side with selective hydration. Each post component is lazily hydrated when it enters the viewport. They use a custom virtual list that recycles DOM nodes — only ~15 DOM nodes exist at any time regardless of how many posts are loaded. Netflix: The landing page ships only ~100KB of JS. Each row of content is fetched and rendered independently — if one row fails, the rest still work. They use a custom IntersectionObserver-based lazy loader for every heavy component.

Core Web Vitals Optimization — LCP, CLS, INP
Advanced P1
Short Answer

Core Web Vitals are Google's three metrics for measuring real-world user experience: LCP (Largest Contentful Paint — loading performance, target under 2.5s), CLS (Cumulative Layout Shift — visual stability, target under 0.1), and INP (Interaction to Next Paint — responsiveness, target under 200ms, replacing FID in March 2024). These directly affect your Google Search ranking and user conversion rates. Amazon found every 100ms of latency cost them 1% in sales.

LCP — Largest Contentful Paint (Target: under 2.5s)

What it measures: The time until the largest content element (hero image, heading, video poster) is rendered. This is when the user perceives the page as "loaded."

Top optimization strategies:

StrategyImpactImplementation
Server-side render critical contentHighNext.js SSR/SSG, pre-render the hero section. Client-only SPAs have terrible LCP.
Preload hero imagesHigh<link rel="preload" as="image" href="hero.webp" /> — the browser fetches it immediately, not after parsing CSS.
Optimize LCP imageHighServe WebP/AVIF, responsive sizes via srcset, remove from initial JS bundle, use CDN edge caching.
Eliminate render-blocking resourcesMediumInline critical CSS, defer non-critical CSS/JS. Audit with Coverage tab in DevTools.
Use a CDNHighServe static assets from edge locations close to users. CloudFront, Cloudflare, Fastly.
CLS — Cumulative Layout Shift (Target: under 0.1)

What it measures: How much the page layout unexpectedly shifts during loading. The infuriating experience where you're about to tap a button and an ad loads above it, making you tap the ad instead.

Top causes and fixes:

CSS — Preventing Layout Shift
/* RULE 1: Always reserve space for images */
img, video {
  width: 100%;
  height: auto;
  aspect-ratio: 16 / 9;      /* Browser reserves space BEFORE image loads */
  object-fit: cover;
}

/* RULE 2: Use font-display to prevent FOIT/FOUT */
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2');
  font-display: optional;          /* Best for perf: use if cached, fallback if not */
  /* or: font-display: swap; — always swap, but causes FOUT (layout shift) */
}

/* RULE 3: Reserve space for dynamic content */
.ad-banner-container {
  min-height: 90px;               /* Ads inject later — reserve their space */
}

/* RULE 4: Animate with transform, not height/width */
/* BAD — triggers layout recalculation */
.element { transition: height 0.3s; }
/* GOOD — compositor-only, no layout shift */
.element { transition: transform 0.3s; }

Dynamically injected content: Banners, cookie notices, and chat widgets are the #1 CLS offenders at scale. They inject late and push content down. Fix: measure their height in advance or position them as overlays that don't affect document flow (position: fixed or position: absolute).

INP — Interaction to Next Paint (Target: under 200ms)

What it measures: The time from a user interaction (click, tap, keypress) to the next visual frame. It captures the responsiveness of the page throughout the entire lifecycle — not just the first interaction like FID did.

The core problem: Long JavaScript tasks block the main thread. If a task takes 300ms, any interaction during that time is delayed by up to 300ms before the browser can even start processing it.

Top optimization strategies:

  • Break long tasks: Use scheduler.yield() (Chrome 115+) or setTimeout(fn, 0) to yield to the browser after 50ms chunks. React's useTransition marks updates as low-priority so the browser can interrupt them for user interactions.
  • Debounce/throttle input handlers: Search-as-you-type that fires on every keystroke blocks the main thread. Debounce by 300ms. The user doesn't need results after 'h' and 'he' and 'hel'.
  • Use Web Workers for heavy computation: Move data processing, CSV parsing, image manipulation off the main thread entirely. The main thread should only do rendering and event handling.
  • content-visibility: auto: Tells the browser to skip rendering off-screen content entirely — not just lazy load, but skip layout and paint calculations. Massive improvement for long pages.
React — useTransition for INP Optimization
function SearchPage() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

}

Micro-Frontends — Architecture, Trade-offs, and When to Use
Expert P1
Short Answer

Micro-frontends extend the microservices pattern to the browser: a single page is composed of independently developed, tested, and deployed frontend applications owned by separate teams. Unlike a monolith where 50 engineers share one deploy pipeline, micro-frontends let each team deploy their slice of the UI independently — on their own schedule, with their own tech stack. The architecture solves organizational scaling, not technical scaling. If you have 3 teams, you don't need micro-frontends.

Three Implementation Approaches

IframesEach micro-frontend runs in its own <iframe>.True isolation (CSS, JS, security), simplest to implementNo shared state, double scroll bars, terrible performance (each iframe is a full document), URL not shared
Single-SPA / qiankunFramework orchestrator mounts/unmounts apps into DOM.Framework-agnostic, simpler than Module FederationNo shared React instance possible without hacks, CSS leaking
Edge-side includesCDN stitches HTML fragments at edge before serving.Best performance (composed at edge, no client overhead)Only works for static content, limited interactivity sharing
The Decision Framework: Should You Use Micro-Frontends?

Yes, if: (1) You have 5+ independent teams that need to deploy to production on their own schedule without coordinating releases. (2) Teams have different tech stacks or want to experiment independently. (3) Different parts of the page have different release cadences (e.g., the checkout team ships weekly, the profile team ships daily).

No, if: (1) You have fewer than 4 teams — a monorepo with feature folders achieves the same goals with less complexity. (2) Your teams share the same tech stack (React + TypeScript) — there's no tech diversity to justify the cost. (3) You don't have strong DevOps practices — micro-frontends multiply deployment complexity. Every team needs its own CI/CD pipeline, preview environment, and monitoring.

The Modular Monolith First Approach

Start with a well-structured monorepo where each team's code lives in a features/team-name/ directory with a strict public API boundary (index.ts). Use code owners in GitHub to enforce that Team A can't modify Team B's directory. Run independent CI checks per feature via Turborepo's --filter. Only when this approach breaks down — typically when teams can't deploy independently because one team's PR blocks another's release — do you extract to micro-frontends. Shopify operates this way: modular monolith with thousands of components, extracted to micro-frontends only for the 3-4 areas where deployment autonomy was the bottleneck.

The Most Common Micro-Frontend Failures

1. Inconsistent UX: Team A uses a blue button with 8px border-radius. Team B uses a green button with 4px border-radius. The page looks like a patchwork quilt. Fix: a shared design system (design tokens + component library) that ALL micro-frontends must consume from a single source of truth. 2. Duplicate dependencies: Each micro-frontend ships its own copy of React. The page loads 3 React instances = 3x the JS + broken hooks (multiple React trees). Fix: Module Federation's shared: { react: { singleton: true } }. 3. Routing conflicts: Both Team A and Team B claim /settings. Fix: a centralized route registry or an orchestration layer that resolves route ownership.

  2. What's the performance cost of micro-frontends vs a monolith? (Hint: more JS, more HTTP requests)
  3. How does Webpack Module Federation handle CSS isolation?
  4. How would you test a page composed of 5 different micro-frontends in CI?
Memory Trick: "Micro-frontends solve organizational scale, not technical scale. If you have 3 teams, use a monorepo. If you have 10+ teams that deploy independently, consider Module Federation. The sweet spot: start modular monolith, extract only when deployment autonomy becomes the bottleneck."
Summary
  • Micro-frontends = independent deploy for UI slices owned by different teams
  • Module Federation (Webpack), Single-SPA, iframes, edge-side includes — increasing complexity left to right
  • Start with modular monolith (feature folders + code owners + independent CI per feature)
  • Extract to micro-frontends only when deployment autonomy becomes the bottleneck
  • Critical: shared design system, singleton dependencies, centralized routing — without these, the UX falls apart

Frontend Security — XSS, CSRF, Secure Auth, and CSP
Advanced P1
Short Answer

Frontend security is about preventing attackers from executing code in other users' browsers or making unauthorized requests on their behalf. The big three: XSS (Cross-Site Scripting — injecting malicious scripts), CSRF (Cross-Site Request Forgery — tricking users into making requests), and insecure authentication (token storage, session management). A breach in any of these means attackers can steal user data, impersonate users, or deface your application.

XSS — Cross-Site Scripting

What it is: An attacker injects malicious JavaScript into your page, which then executes in other users' browsers. Three types:

Stored XSS: Attacker submits a comment containing <script>stealCookies()</script>. Your server stores it. Every user who views the comment gets their cookies sent to attacker.com. This is the most dangerous — one injection, many victims.

Reflected XSS: Attacker sends a URL like yoursite.com/search?q=<script>...</script>. If your page renders the query param without escaping, the script executes. Requires the victim to click a crafted link.

DOM-based XSS: Attacker manipulates client-side JavaScript to execute malicious code via innerHTML, eval(), or document.write() with unsanitized input. This never touches the server.

XSS Defense Strategy

1. Output encoding: React auto-escapes JSX by default — {userInput} is safe because React converts < to &lt;. This alone prevents 90% of XSS.

2. DOMPurify for rich text: When you MUST render user HTML (comments with formatting, blog posts), sanitize it: DOMPurify.sanitize(dirtyHTML, { ALLOWED_TAGS: ['b', 'i', 'p', 'a'] }). This strips all scripts, event handlers, and dangerous attributes.

3. Content Security Policy (CSP): An HTTP header that tells the browser "only execute scripts from these sources." The ultimate defense-in-depth: even if an attacker injects a script tag, the browser refuses to execute it because the source isn't whitelisted.

4. Never use dangerous APIs: Avoid dangerouslySetInnerHTML without sanitization. Avoid eval(), new Function(), document.write() entirely. Use textContent instead of innerHTML when inserting text.

CSRF — Cross-Site Request Forgery

What it is: An attacker tricks a logged-in user into making an unwanted request. If you're logged into your bank at bank.com, and you visit a malicious site that has <img src="bank.com/transfer?to=attacker&amount=10000" />, the browser sends your session cookie with the request — and your bank processes it.

Defense:

  • SameSite cookies: Set-Cookie: session=...; SameSite=Lax. This tells the browser "only send this cookie for same-site requests." A cross-site <img> won't include the cookie. This single setting prevents most CSRF.
  • CSRF tokens: Server generates a random token, sends it to the client, client includes it in every state-changing request (header or body). The attacker can't guess the token. Modern frameworks do this automatically.
  • Custom request headers: Browsers enforce CORS preflight for requests with custom headers. An X-CSRF-Token header triggers preflight, which the attacker's site can't satisfy.
Secure Authentication Storage

The golden rule: NEVER store access tokens in localStorage. Any JavaScript on the page can read localStorage — including injected scripts from XSS. Instead:

HTTP-only cookies: Set-Cookie: token=...; HttpOnly; Secure; SameSite=Strict. The HttpOnly flag means JavaScript CANNOT read this cookie — XSS can't steal it. The browser automatically attaches it to requests.

Token rotation: Access tokens expire in 15 minutes. Refresh tokens (also HTTP-only) last 7 days but are single-use — using a refresh token invalidates it and issues a new one. If an attacker steals a refresh token, the legitimate user's next refresh invalidates the attacker's copy, and the server can detect the reuse and revoke all tokens.

BFF pattern (Backend For Frontend): A thin backend layer between your SPA and the API. The SPA authenticates with the BFF (same domain = first-party cookies work). The BFF holds the real API tokens and forwards requests. The browser never sees the real API tokens — they're server-to-server only.

The Most Common Security Mistakes I See in Interviews

1. "I store JWT in localStorage" — immediate red flag. Every interviewer will ask: "What happens if there's an XSS vulnerability?" The answer: all tokens stolen. 2. "React is safe by default" — yes for JSX, no for dangerouslySetInnerHTML, href attributes (javascript:alert(1)), and a tag target="_blank" without rel="noopener noreferrer". 3. "We don't need CSP because React escapes JSX" — CSP is defense in depth. XSS can come from third-party scripts, CDN compromises, or supply chain attacks. CSP catches what React misses.

Caching Strategy — CDN, Service Worker, React Query, and Next.js Cache Layers
Advanced P1
Short Answer

A caching strategy is a layered defense against latency. Each layer serves a different purpose and has a different lifespan. From the user outward: (1) React Query in-memory cache (milliseconds, single session) — deduplicates requests, provides instant UI on navigation back. (2) Service Worker cache (offline, cross-session) — serves cached pages when offline, enables instant loading on repeat visits. (3) Browser HTTP cache (automatic, based on headers) — Cache-Control: max-age=31536000, immutable for hashed assets. (4) CDN cache (geographic edge, minutes to hours) — serves static assets and SSR HTML from the closest edge node. (5) Next.js data cache (server-side, configurable) — fetches data once and reuses across requests for a configurable time.

stale-while-revalidate — The Pattern That Makes Everything Feel Instant

The pattern: (1) User navigates to Dashboard. (2) React Query checks its cache — has data from 30 seconds ago. Serve that immediately. User sees content in 0ms. (3) In the background, React Query refetches from the API. (4) When the fresh data arrives, React Query reconciles it into the UI. If nothing changed, no re-render. If something changed, smooth transition.

This pattern exists at every caching layer. The HTTP Cache-Control: stale-while-revalidate=60 tells the browser: serve from cache even if stale, fetch fresh in the background. CDNs implement the same pattern. The user NEVER waits for data — they always see the last known good state while fresh data loads behind the scenes.

React Query — stale-while-revalidate Configuration
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30 * 1000,          // Data considered fresh for 30s — no refetch if fresh
      gcTime: 5 * 60 * 1000,          // Keep in cache for 5min after last use (was cacheTime)
      refetchOnWindowFocus: true,    // Refetch when user returns to tab — good for collaborative apps
      retry: 3,                       // Auto-retry failed queries 3 times
      refetchOnMount: true           // Refetch when component mounts if data is stale

Infinite Scroll at Scale — 100k+ Items, Virtualization, and Pagination
Advanced P1
Short Answer

Infinite scroll at scale requires solving three problems simultaneously: data fetching (what backend pagination strategy), rendering (how to keep the DOM light even with 100k items), and memory management (how to avoid crashing the browser tab when JavaScript holds references to thousands of data objects). The solution: cursor-based pagination for the API, windowing/virtualization for rendering, and a sliding window cache for memory.

1. Cursor Pagination — Why Offset Fails at Scale

Offset pagination (?page=3&limit=20) breaks when data mutates between page loads. If a new item is inserted at the top while the user is scrolling, offset 40 shifts — the user sees duplicate items or misses items entirely. For a social media feed, this is unacceptable.

Cursor pagination: The server returns a cursor (an opaque string like "cursor:abc123") that represents a position in the sorted list. The next request includes ?cursor=abc123&limit=20. The cursor is usually the ID or timestamp of the last item. Even if new items are inserted above, the cursor points to a stable position — no duplication, no missing items. This is how Twitter, Reddit, and every major feed API works.

2. Virtualization — DOM Recycling

Without virtualization, 100k items = 100k DOM nodes. The browser will crash or become unusably slow. react-virtuoso is the current best library for this — it renders only the items visible in the viewport (plus a small buffer above and below). For a viewport showing ~10 items, only ~15 DOM nodes exist. When the user scrolls, Virtuoso calculates which items should be visible now, reuses existing DOM nodes, and updates their content. This is O(1) DOM rendering regardless of list size.

Why not react-window or react-virtualized? react-virtuoso handles dynamic row heights (tweets with variable text + images), bi-directional scrolling (chat: scroll up for history AND new messages), and header/footer components without configuration hacks. It also has a GroupedVirtuoso for grouped lists with sticky headers.

3. Memory Management — The Sliding Window

Even with virtualized DOM, React Query cache holds ALL fetched items in JavaScript memory. 100k items × 2KB average = 200MB of memory. On mobile, the browser will crash at ~300-500MB.

Sliding window cache: Keep only the last N pages in memory (e.g., last 10 pages × 20 items = 200 items = ~400KB). When the user scrolls far enough, evict older pages from the cache. If they scroll back up, re-fetch from the API. React Query doesn't do this natively — you implement it by manually managing queryClient.setQueryData and removing old data. For most apps, however, the simpler approach is to keep all data and add a "scroll to top" / "back to top" button — users rarely scroll through more than their last 500 posts.

Component Library Architecture — Design Tokens, Storybook, and Versioning
Advanced P1
Short Answer

A component library is a design system's technical implementation — reusable UI components with enforced design tokens, documented in Storybook, tested with visual regression tools (Chromatic), versioned with semantic versioning, and distributed as an npm package. The goal: any developer can build a new page using only library components and it automatically looks like it belongs in your app — consistent spacing, colors, typography, and accessibility — without a designer reviewing every PR.

Architecture Layers

Layer 1: Design Tokens — The atomic values: --color-primary-500: #3B82F6, --spacing-4: 1rem, --font-size-lg: 1.125rem. Stored as CSS custom properties (or a JSON file that generates CSS + JS). Changes to tokens cascade through every component. Using Tailwind? Your tokens ARE your Tailwind config. Single source of truth.

Layer 2: Primitives — The smallest reusable building blocks: Button, Input, Badge, Avatar, Spinner. These have no business logic. They accept props for variants (primary/secondary/danger), sizes (sm/md/lg), and states (loading/disabled/error).

Layer 3: Composites — Compositions of primitives: Modal (uses Button + overlay + trap-focus), DataTable (uses Input + Badge + Pagination), Autocomplete (uses Input + List + Spinner). These encapsulate interaction patterns.

Layer 4: Recipes — Page-level patterns: SettingsForm, DashboardLayout. These are often in the app itself, not the library, because they're too specific.

Storybook + Chromatic — Document, Test, Review

Storybook: Every component has stories covering all variants, states, and edge cases. A Button with 3 variants × 4 sizes × 5 states = 60 stories, generated programmatically. Stories serve as documentation (designers can see every state), development environment (build components in isolation), and test harness (visual regression + interaction tests run against stories).

Chromatic: Runs visual regression tests on every PR — takes screenshots of every story and compares pixel-by-pixel with the main branch. If your Button's border-radius changed from 6px to 4px, Chromatic highlights the diff. Humans approve or reject. This catches the "I changed a CSS variable and accidentally broke 40 components" bug before it reaches production.

Versioning Strategy

Semantic versioning applied to components: MAJOR — breaking changes to component API (changing a prop name, removing a variant). MINOR — new components, new features (adding a new variant, new prop that doesn't break existing usage). PATCH — visual tweaks, accessibility fixes, bug fixes that don't change the API. Package the entire library as a single version (not per-component versioning — that's a coordination nightmare). For monorepos, the library lives in packages/ui and consumer apps pin the version.

Authentication & Authorization Flow — JWT, OAuth2, RBAC, and Middleware
Advanced P1
Short Answer

Authentication proves who you are ("I am user #42"). Authorization determines what you can do ("user #42 can edit posts but not delete users"). The modern auth stack for frontend: JWT access tokens (short-lived, 15min) + refresh tokens (long-lived, stored in HTTP-only cookies, single-use) + OAuth2/OIDC for social login and enterprise SSO + RBAC (Role-Based Access Control) for coarse-grained permissions + middleware at the server/routing layer to gate access before any component renders.

JWT + Refresh Token Flow

1. Login: User submits credentials → server validates → server issues: (a) Access token (JWT, 15min expiry, stored in memory/JS closure in the SPA) + (b) Refresh token (opaque or JWT, 7 days, stored in HTTP-only Secure SameSite cookie).

2. API calls: SPA attaches access token in Authorization: Bearer <token> header. If 401 (expired), the SPA calls /api/auth/refresh — the browser automatically sends the refresh cookie. Server validates refresh token, issues new access token + new refresh token (invalidates old refresh token — single-use rotation).

3. Token rotation detection: If an attacker steals a refresh token and uses it before the legitimate user, the server sees the legitimate user's refresh attempt as a "reuse" because the token was already consumed. The server revokes ALL refresh tokens for that user — the attacker and the user are both logged out. The user re-authenticates; the attacker loses access. This is called "refresh token rotation with reuse detection."

OAuth2 / OIDC — Social Login & Enterprise SSO

The flow: User clicks "Sign in with Google" → your app redirects to Google's authorization server → user approves → Google redirects back to your app with an authorization code → your server exchanges the code for tokens (access + refresh + ID token) → server creates a session/JWT for your app → redirects user to the dashboard. The user never sees a password form on your site. Your server never sees the user's Google password.

Key decisions: (1) PKCE flow for SPAs — no client secret needed, uses a code challenge. (2) Backend For Frontend — the token exchange happens on your server, not the browser. The browser only gets your app's session cookie, never sees the third-party tokens. (3) Account linking — what happens when a user signs in with Google AND GitHub? Same email = same account or separate accounts? This is a product decision with security implications.

RBAC — Role-Based Access Control

Frontend responsibilities: (1) UI-level: hide/show UI elements based on user role (admin sees "Delete User" button, regular user doesn't). This is a UX convenience, NOT security — the API must also enforce authorization. (2) Route-level: redirect unauthorized users away from routes they shouldn't access (middleware or route guards). (3) Component-level: <Can permission="delete:posts"><DeleteButton /></Can> — declarative permission gating.

Backend responsibilities (the real security): Every API endpoint checks the user's permissions from the JWT claims or a database lookup. The frontend's role is purely UX — never trust client-side authorization for security.

        .finally(() => { refreshPromiseRef.current = null; });

          error.config.headers.Authorization = `Bearer ${token}`;
          return apiClient(error.config);
        }
        return Promise.reject(error);
      }
    );
    return () => apiClient.interceptors.response.eject(interceptor);

Real-Time Collaboration — CRDT, WebSocket Architecture, and Optimistic Updates
Expert P2
Answer

Real-time collaboration (Google Docs, Figma, Notion) requires solving the conflict resolution problem: two users edit the same data simultaneously — whose change wins? OT (Operational Transformation) was Google Docs' original approach. CRDT (Conflict-free Replicated Data Types, specifically Yjs) is the modern standard used by Notion, Linear, and Room.sh. CRDTs are data structures that guarantee eventual consistency without a central server resolving conflicts — every user's document converges to the same state automatically.

Architecture: WebSocket connection per document → changes sent as binary CRDT updates (Yjs documents) → server relays updates to all collaborators (can be dumb relay or aware of document state) → each client applies updates locally → optimistic updates mean the local user sees their change INSTANTLY (before server confirms) → if the server rejects, the CRDT library handles the rollback seamlessly. The key insight: CRDTs make the server a relay, not an authority. The document truth is the union of all edits.

PWA Implementation — Service Workers, Workbox, Manifest, and Offline-First
Intermediate P2
Answer

A Progressive Web App is a web app that uses modern browser APIs to deliver an app-like experience: installable (manifest), offline-capable (service worker), and engaging (push notifications). The three pillars:

1. Web App Manifest: A manifest.json file that tells the browser your app's name, icons, theme color, and display mode ("display": "standalone" removes the browser chrome). This is what makes the "Add to Home Screen" prompt appear.

2. Service Worker: A JavaScript file that runs in the background, separate from the page. It intercepts all network requests and can serve cached responses when offline. Workbox (Google's library) simplifies this — pre-cache your app shell (HTML, CSS, JS) during install, cache API responses at runtime with strategies (Cache First for static assets, Network First for API calls, Stale-While-Revalidate for images). The hardest part: cache invalidation. When you deploy a new version, the old service worker must be replaced — Workbox handles this with a skipWaiting() + clientsClaim() pattern, but you must notify the user when an update is available ("A new version is available. Refresh?").

3. Offline-first: The app must work without internet. Not just a "You're offline" page, but full functionality: read cached content, queue writes to sync when online (Background Sync API), show cached data with an "offline" indicator. Twitter Lite does this beautifully — you can scroll your timeline offline because the service worker cached it.

SPAs render content with JavaScript.   • Meta tags: <title>, <meta name="description">, <meta property="og:title">, <meta name="twitter:card">. Use Next.js generateMetadata API to set these per route.

  • Dynamic OG images: @vercel/og or satori generates social preview images dynamically — each blog post gets a unique preview card. This is table stakes for content marketing.
  • Sitemap + robots.txt: Auto-generated XML sitemap listing all pages with <lastmod> dates. robots.txt directing crawlers what to index.

"Google can render JavaScript, so my React SPA is fine for SEO." This is dangerously wrong. Answer

A CDN (Content Delivery Network) is a globally distributed network of servers that cache and serve your content from the location closest to the user. The difference between "fetching from a server in Virginia from Tokyo" (200ms latency) and "fetching from an edge node in Tokyo" (5ms latency) is the difference between a sluggish app and an instant one.

Design a Real-Time Chat Application Frontend — WebSockets, message sync, offline support, and optimistic UI
Advanced P1
Answer

Designing a real-time chat frontend is one of the most common system design questions in senior frontend interviews — asked at Meta (Messenger), Google (Chat), Amazon, Swiggy, and MakeMyTrip (2025-2026). The architecture spans:

1. Connection Layer: WebSocket for bidirectional real-time messaging. On mount, the client opens a WS connection to wss://chat.example.com/ws?token=JWT. Connection lifecycle: open → send heartbeat (ping/pong every 30s) → receive messages → reconnect on disconnect (exponential backoff: 1s, 2s, 4s, 8s... max 30s). Fallback to SSE (Server-Sent Events) if WebSocket is unavailable (corporate firewalls, restricted networks).

2. Message Sync & Storage: Messages stored in IndexedDB (via Dexie.js or idb) for offline access. On reconnect, request messages since the last known message ID (GET /api/messages?since=12345). This "catch-up" strategy handles missed messages during disconnection. Keep the last N messages in React Query cache for instant UI on conversation switch.

3. Optimistic UI + State Management: When a user sends a message, immediately show it in the UI (optimistic update) with a "sending" indicator. On server confirmation, update the message status to "sent." On failure, mark as "failed — tap to retry." Use React Query's optimistic update or Zustand with an optimisticMessages array merged with server messages. Use useSyncExternalStore for the WebSocket connection state to prevent tearing during concurrent rendering.

4. Virtualized Message List: Chat histories are long (10k+ messages). Use react-virtuoso (purpose-built for chat — handles dynamic heights, reverse scrolling, sticky timestamps, keyboard navigation). When the user scrolls up, load older messages via pagination (GET /api/messages?before=messageId&limit=50) and prepend them to the virtualized list. Preserve scroll position after prepending.

5. Typing Indicators & Presence: Debounced typing events sent via WebSocket (emit every 3s while typing). The server broadcasts to the conversation. The client shows "{name} is typing..." with a 5s timeout (if no new typing event within 5s, hide indicator). Presence: online/offline/away status via WebSocket connection state + idle detection (requestIdleCallback + mousemove listener).

Senior Insight — The Hard Parts

Hardest challenges in chat: (1) Scroll position preservation when new messages arrive while the user is reading history — solution: react-virtuoso's followOutput prop that auto-follows only when already at the bottom. (2) Out-of-order messages from multiple servers — solution: server-assigned monotonic message IDs; client sorts by ID not by arrival time. (3) Attachment handling — upload to S3 pre-signed URL first, then send message with attachment URL; show local preview immediately with upload progress. (4) End-to-end encryption (WhatsApp-style) — messages encrypted client-side before sending; key management is the hardest distributed systems problem; use libraries like libsignal (Signal protocol) but expect 10x engineering complexity.

React — useWebSocket Hook with Auto-Reconnect
function useWebSocket(url) {
  const [readyState, setReadyState] = useState('connecting');
  const [lastMessage, setLastMessage] = useState(null);
  const wsRef = useRef(null);
  const reconnectAttempt = useRef(0);
  const maxDelay = 30000;

  const connect = useCallback(() => {
    const ws = new WebSocket(url);
    ws.onopen = () => { setReadyState('open'); reconnectAttempt.current = 0; };
    ws.onclose = () => {
      setReadyState('reconnecting');
      const delay = Math.min(1000 * Math.pow(2, reconnectAttempt.current), maxDelay);
      reconnectAttempt.current++;
      setTimeout(connect, delay);
    };
    ws.onmessage = (e) => setLastMessage(JSON.parse(e.data));
    wsRef.current = ws;
  }, [url]);

  useEffect(() => { connect(); return () => wsRef.current?.close(); }, [connect]);

  const send = useCallback(data => {
    if (wsRef.current?.readyState === WebSocket.OPEN) {
      wsRef.current.send(JSON.stringify(data));
    }
  }, []);

  return { readyState, lastMessage, send };
}

function useAutocomplete({ fetchFn, debounceMs = 300, minChars = 2 }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [status, setStatus] = useState('idle'); // idle | loading | success | error
  const cacheRef = useRef(new Map());
  const abortRef = useRef(null);

  const search = useCallback(async (q) => {
    if (q.length < minChars) { setResults([]); setStatus('idle'); return; }

    const normalized = q.toLowerCase().trim();
    const cached = cacheRef.current.get(normalized);
    if (cached) { setResults(cached); setStatus('success'); return; }

    abortRef.current?.abort();
    const controller = new AbortController();
    abortRef.current = controller;

    setStatus('loading');
    try {
      const data = await fetchFn(normalized, { signal: controller.signal });
      cacheRef.current.set(normalized, data);
      setResults(data); setStatus('success');
    } catch (err) {
      if (err.name === 'AbortError') return;
      setStatus('error');
    }
  }, [fetchFn, minChars]);

  const debouncedSearch = useMemo(() => debounce(search, debounceMs), [search, debounceMs]);

  return { query, setQuery: (v) => { setQuery(v); debouncedSearch(v); }, results, status };
}

Lazy-loaded field components: if a field type (e.g., rich text editor) is heavy, load it via React.lazy only when that field type is used in the schema. Form section virtualization: for very long forms, virtualize sections (not individual fields) to keep the DOM lean.

Key Design Decisions

1. Independent Widget Architecture: Each widget (KPI card, chart, table) fetches its own data independently. If the "revenue" chart fails, the "active users" card still renders. Use React Query with per-widget queryKey — each widget manages its own loading/error/empty states. Never share a single query for all widgets — this couples their lifecycles and a single failure takes down the whole dashboard.

2. Time Range as Query Parameter: The selected time range (24h, 7d, 30d, custom date range) is part of every widget's query key. When the user changes the time range, all widgets refetch with the new range. Use URL search params (?range=7d&start=2026-01-01) so the dashboard URL can be shared/bookmarked. Debounce custom date range selection (300ms) to avoid N refetches while the user picks dates.

3. Chart Library Selection: Use recharts for most charts (React-native, composable, good defaults, ~80KB gzipped). Use visx (Airbnb) for custom chart types and animations (more flexible, more code). Use Nivo for complex Sankey/bubble/candlestick charts. Key metric SVG rendering: charts should render on the server (SSR) for the initial page load — this requires a chart library that supports SSR (recharts does not; Nivo and visx do). For real-time updates, use lightweight canvas-based rendering: uPlot (~40KB, 10x faster than chart.js for 10k+ data points).

4. Auto-Refresh Strategy: Use React Query's refetchInterval. Different widgets can have different refresh intervals: KPI cards (30s), charts (60s), tables (5min). Add a manual "Refresh All" button that invalidates all queries. Use WebSocket push for critical metrics that need sub-second updates (downtime alerts, error rates).

Senior Insight — Dashboard Performance at Scale

A dashboard with 20+ charts rendering 10k+ data points each will be slow. Solutions: (1) Downsample data on the server — the API returns 200 data points (not 10k) for a line chart; the server aggregates to fit the chart width. (2) Canvas-based rendering for high-frequency data — recharts (SVG) is slow for 10k+ points; switch to uPlot (canvas) for time-series. (3) Lazy-loaded widgets — widgets below the fold (not visible on screen) don't fetch data until they scroll into view (IntersectionObserver + enabled: false in React Query). (4) Worker-based calculations — move data aggregation to a Web Worker so the main thread stays free for rendering. (5) Cache with hash keys — identical queries (same endpoint, same params) are deduplicated by React Query automatically — leverage this for widgets that share data.

Key Design Decisions

1. Horizontal Content Rows (Netflix-style): Netflix's iconic horizontal scrolling rows are implemented with overflow-x: auto + scroll-snap-type: x mandatory. Key optimization: render only visible rows + 1 row above/below (lazy rendering via IntersectionObserver). Each row has a "scroll left/right" button — on click, scroll by one card width using scroll-behavior: smooth. Card hover preview: on hover, show a rich card overlay (title, description, rating, year) — this requires a delayed hover trigger (200ms) to avoid flickering during fast scrolling.

2. Adaptive Bitrate Streaming (ABR): The browser requests a .m3u8 (HLS) or .mpd (DASH) manifest from the CDN. The manifest lists available quality levels (360p, 720p, 1080p, 4K) and their chunk URLs. The player (HLS.js, Shaka Player, or native MSE) automatically selects quality based on network speed and buffer health. Startup optimization: request the lowest quality segment first (instant playback), then upgrade to match bandwidth. Seek optimization: when the user seeks to a position, request the closest keyframe (sync point) — not every frame is seekable.

3. Resume Playback: Save { videoId, position, timestamp } to IndexedDB every 5 seconds while playing. On mount, check if there's a saved position for the current video — if so, show a "Resume from 12:34" button. The position is synced across devices via the server API when the user pauses or navigates away. Watch history: track completed percentage for each video to show "Continue Watching" rows.

4. Search with Autocomplete: Same pattern as Q18 (Autocomplete) but scoped to content search. Search index includes titles, actors, genres, and descriptions. Search result page: show results grouped by category ("Movies", "TV Shows", "Actors"). Use client-side fuzzy matching for typo tolerance.

Senior Insight — Netflix vs YouTube Architecture Differences

Netflix: UI-first, heavy React, SSR for initial load (Next.js-like), service workers for offline downloads. Card hover preview is the key UX differentiator — it requires pre-fetching trailer metadata. YouTube: Light DOM (custom elements, no heavy framework), YouTube.com is built with the Polymer library (Web Components) — they optimize for fast initial load (render a searchable page first, hydrate progressively). YouTube's key UX: infinite watch — auto-play next recommended video. Both use: HLS/DASH for ABR, CDN for video segments (Netflix uses Open Connect — its own CDN deployed at ISP edge), IndexedDB for watch position, and service workers for background fetching. Common interview trap: candidates design the player without discussing DRM (Widevine, PlayReady) or the licensing server — for premium content (Netflix, Prime), the player must request a license key from a DRM server before decrypting content segments.

React — Video Player with HLS.js and Resume
import Hls from 'hls.js';

function VideoPlayer({ src, videoId }) {
  const videoRef = useRef(null);
  const [position, setPosition] = useState(0);

  useEffect(() => {
    const video = videoRef.current;
    if (!video) return;

    let hls;
    if (Hls.isSupported()) {
      hls = new Hls({ enableWorker: true });
      hls.loadSource(src);
      hls.attachMedia(video);
    }

    // Save position every 5 seconds
    const interval = setInterval(() => {
      const pos = video.currentTime;
      savePosition(videoId, pos);  // IndexedDB write
      setPosition(pos);
    }, 5000);

    return () => {
      hls?.destroy();
      clearInterval(interval);
    };
  }, [src, videoId]);

  useEffect(() => {
    const saved = getSavedPosition(videoId);  // IndexedDB read
    if (saved > 30) {  // Resume if more than 30s watched
      videoRef.current.currentTime = saved;
    }
  }, [videoId]);

  return <video ref={videoRef} controls />;
}
Memory Trick: "Video Streaming = Horizontal rows (CSS scroll-snap) + HLS/DASH (adaptive bitrate) + CDN (Netflix Open Connect) + Resume playback (IndexedDB every 5s) + DRM (Widevine license server). Netflix = heavy React + hover preview. YouTube = lightweight Web Components + infinite auto-play."

URL Shortener
Beginner		 POST /shorten → generate unique ID (base62: 7 chars = 3.5T URLs) → store in DB (key: shortId, value: longUrl) → 301 redirect on GET. Cache hot URLs in Redis. Hash collision? Rate Limiter
Intermediate		 Token Bucket (burst-allowing) or Sliding Window Log (precise). Per-user rate limit stored in Redis: INCR user:{id}:requests + EXPIRE 60. Return 429 + Retry-After header when exceeded. Token Bucket: permits bursts, simple. Sliding Window: more accurate but more memory. Distributed rate limiting? Use Redis Cluster + Lua scripts for atomicity. Rate limit on frontend too? Yes — show "rate limited" UI before 429, use local token bucket with occasional server sync.
API Gateway
Intermediate		 Single entry point for all microservices. Routes requests based on path (/users/* → user-service). Handles: auth (JWT validation before forwarding), rate limiting, logging, request/response transformation, circuit breaking. BFF pattern (Backend For Frontend): separate gateway for web vs mobile — each returns data shaped for its client. GraphQL federation: Apollo Gateway combines multiple subgraphs into single schema. Gateway vs Service Mesh: gateway = edge (external), mesh = internal (sidecar proxy).
File Upload Service
Intermediate		 Client → Presigned URL (GET from server) → Direct S3/Blob upload → Server notification on completion. Parallel chunked upload for large files (5MB chunks). Virus scanning: trigger Lambda on S3 upload → scan file → tag as clean/infected. Chunking: parallel upload 5MB chunks via tus-js-client; server reassembles.
Instagram Feed / Twitter Timeline
Intermediate		 Fan-out on write (celebrity) + Pull on read (regular). Pre-compute feed for active users: when user A posts, write post ID to all followers' feed lists. For celebrities (100M+ followers), followers pull on read. Cache feed in Redis sorted set (by timestamp). Fan-out on write: write amplification for celebrities — solution: separate approach for high-follower accounts. Pull on read: higher read latency — solution: cache. Hybrid: pre-compute feed for "tier 1" (daily active followers within 500), pull for rest. Ranking: machine learning model scores each post; client renders sorted by score + timestamp.
Uber / Ride Booking
Advanced		 Rider → WebSocket (location update) → Geospatial index (Redis GEO / QuadTree) → Find nearest drivers → Push notification to top 3 drivers → First to accept wins → Ride lifecycle (arrived, en-route, completed, payment). Geospatial index: Redis GEOADD + GEORADIUS for finding drivers within 1km. Surge pricing: dynamic multiplier based on driver availability / request rate. ETA: compute route duration from driver's location to pickup (Google Maps API or OSRM self-hosted). Offline mode: rider can request even with poor connectivity — request queued locally, dispatched on reconnect.
Google Drive / Dropbox
Advanced		 Local file system watcher (chokidar) → detect changes → chunk file (4MB) → compute hash → upload changed chunks only (delta sync) → server stores chunks in blob storage → metadata in SQL DB. Conflict resolution: last-writer-wins or CRDT (Google Docs-style). Delta sync: upload only changed bytes, not the entire file — reduces bandwidth 100x for large files with small edits. Chunk deduplication: same chunk hash = stored once server-side (user A and user B uploading the same cat photo share one blob). Offline edits: queue changes locally via IndexedDB, sync on reconnect with merge strategy. Version history: store chunk tree per version — cheap to keep 30 days of history.
Amazon / E-Commerce
Advanced		 Product page: SSR (SEO) + CDN cache (stale-while-revalidate). Search: Elasticsearch for product index. Cart: Redis (ephemeral, fast) + SQL (persist on login). Recommendations: ML-based collaborative filtering + real-time "users also bought" from order history. Product page SSR: critical for SEO — render on server, cache on CDN. Cart persistence: anonymous cart in localStorage/IndexedDB → merged with server cart on login. Inventory: show real-time stock count via WebSocket push. Checkout flow: multi-step (cart → shipping → payment → confirmation), each step validates before proceeding. Order tracking: status machine (ordered → confirmed → shipped → out for delivery → delivered) with push notifications on state change.
Payment Gateway
Advanced		 Client → Payment form (PCI-DSS compliant, never touch card data directly) → Tokenization service (Stripe/Adyen) → Your server (idempotency key) → Payment processor → Webhook callback → Update order status. Idempotency key prevents double charges. NEVER handle raw card data on your server — use Stripe Elements or hosted payment page (PCI-DSS Level 1 compliance required otherwise). Idempotency: client generates a unique key per payment attempt; if the request fails (network error), retry with same key — processor detects duplicate and returns the previous result. 3D Secure: redirect to bank for authentication on high-value transactions. Refund flow: API call to processor, async completion via webhook. Reconciliation: daily batch comparison of your records vs processor's settlement report.
Video Conferencing (Zoom)
Expert		 WebRTC (peer-to-peer) for 1:1 calls → SFU (Selective Forwarding Unit) server for group calls (3+ participants). SFU receives each participant's video/audio stream and selectively forwards to others (reduces client bandwidth). Signaling server (WebSocket) for room management, offer/answer exchange, and ICE candidate negotiation. WebRTC: browser-native P2P media, no plugins needed. SFU vs MCU: SFU forwards streams (higher server bandwidth, lower client CPU), MCU mixes streams (lower client bandwidth, higher server CPU, introduces delay). Zoom uses SFU. Screen sharing: separate WebRTC stream with higher resolution. Virtual background: WASM-based ML segmentation on client side (not server). Recording: server-side mix + record to S3, or client-side record via MediaRecorder API.
Real-Time Collaboration (Google Docs)
Expert		 Operational Transform (OT) or CRDT (Conflict-free Replicated Data Type). Each character operation (insert/delete at position) is broadcast to all connected clients. Operations are transformed against concurrent operations to converge to the same document state. WebSocket for real-time broadcast. OT vs CRDT: OT is older (Google Docs), requires a central server for transformation. CRDT is newer (FigJam, Liveblocks), peer-to-peer, no central server needed. Position tracking: use unique IDs for every character (not index-based) — indices change as others type. Cursor presence: broadcast cursor position + selection range as the user types (throttled to 100ms). Undo/redo: each client maintains its own undo stack of operations — undo is also broadcast as an operation.
Recommendation System
Advanced		 Collaborative filtering (users like you also liked X) + Content-based filtering (similar to what you watched/bought) + Hybrid. Offline batch computation (Spark/Airflow) computes candidate sets daily → stored in Redis for online serving → real-time ranking model scores candidates → top 20 returned. Cold start problem: new users get popular items, new items get random exploration. Real-time signals: clicks, likes, purchases update the user's embedding vector incrementally (not full recompute). A/B testing: serve 2 recommendation algorithms to different user segments — compare CTR, conversion, dwell time. Diversity: don't recommend 10 Marvel movies — diversify by genre, director, era. Explicit feedback (ratings) + implicit feedback (clicks, watch time).
Notification Pipeline
Advanced		 Event → Message Queue (Kafka/SQS) → Fan-out to channels: Push (FCM/APNs), Email (SES/SendGrid), SMS (Twilio), In-app (SSE/WebSocket). Each channel has a dedicated worker that formats the message and sends via the provider's API. Retry queue for failures (exponential backoff, max 3 retries). Deduplication: same event → multiple channels; dedupe by event ID + channel type. Template rendering: each notification uses a Handlebars template with event data — server-side rendered before sending. Quiet hours: don't send push notifications 10pm-8am (configurable per user). Rate limiting: max 5 push notifications per hour per user — batch non-urgent notifications into a daily digest. Analytics: track delivery rate, open rate, click rate per channel per user.
Distributed Cache
Expert		 Redis Cluster: data sharded across multiple nodes (16384 hash slots). Each key hashed to a slot → slot mapped to a node. Replication: each shard has 1 master + N replicas. Cache eviction: LRU (most common), LFU, TTL-based. Cache-aside (lazy loading): read → miss cache → load from DB → populate cache. Write-through: write to cache first, then DB — ensures consistency. Cache invalidation: the hardest problem in CS. Strategy: TTL (eventual consistency) + manual invalidation on data mutation (delete cache key when DB row updated). Cache stampede: when a hot key expires and 1000 requests simultaneously hit the DB — solution: "mutex" — first request locks, fetches, populates cache; others wait. Write-around vs Write-through: write-around (skip cache, invalidate) is simpler for mostly-read workloads. Redis vs Memcached: Redis supports data structures (sorted sets, lists), persistence, replication; Memcached is simpler, faster for pure key-value.
Ticket Booking (BookMyShow)
Expert		 Show page → Select seats (grid UI with max 8 seat selection) → Reserve seats (10min lock via Redis) → Payment → Confirm. Redis stores seat availability as a bitmap — SETBIT show:{id}:seats {seatIndex} 1 for booked. Atomic seat reservation via Lua script (check all seats available → mark as reserved → set TTL 10min). Seat locking: reserve seats in Redis with 10min TTL — if payment not completed, TTL expires and seats are released. Concurrency: two users selecting the same seat — Lua script ensures atomicity: only the first succeeds. Seat map UI: SVG-based grid, each seat is a colored rectangle (available=green, reserved=yellow, booked=red). Real-time updates: WebSocket push when seats are booked — all users viewing the same show see availability update instantly. Pricing: different zones have different prices — front rows, VIP, balcony. Bulk booking: group bookings with adjacent seat preference (best-effort adjacency).
