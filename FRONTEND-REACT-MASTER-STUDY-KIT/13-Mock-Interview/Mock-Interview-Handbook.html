Explain the event loop in JavaScript. What happens when you call setTimeout(fn, 0)?
Intermediate
What interviewer is evaluating: Understanding of async execution model, microtask vs macrotask queues, and why setTimout(fn, 0) doesn't execute immediately. Tests whether you debug async race conditions or just guess.

Model Answer: The event loop is the mechanism that allows JavaScript (single-threaded) to handle async operations. It consists of: Call Stack (executes sync code), Task Queue / Macrotask Queue (setTimeout, setInterval, I/O, UI rendering), Microtask Queue (Promise.then/catch/finally, queueMicrotask, MutationObserver). The loop runs: execute all sync code on the call stack → drain the microtask queue completely → optionally render UI → take ONE macrotask → repeat.

setTimeout(fn, 0) schedules fn into the macrotask queue. Even with 0ms delay, fn won't run until: (1) the call stack is empty, (2) all pending microtasks are drained. So between setTimeout(fn, 0) and fn executing, any queued microtasks (Promise callbacks) will run first. This is why setTimeout(..., 0) is used to defer execution to the next iteration of the event loop — useful for yielding to the browser to paint or handle user input during heavy computation.

Common Mistake

"setTimeout(fn, 0) runs the function immediately" — this shows you don't understand async ordering. Always mention the microtask queue. If you forget microtasks, the interviewer assumes you've never debugged Promise ordering issues.

What's a closure? Write a function that creates a counter with private state.
Beginner
What interviewer is evaluating: Can you explain closures in your own words (not just a definition)? Can you demonstrate practical use? The counter is table stakes — the interview might push further into module patterns, data hiding, and React hooks.

Model Answer: A closure is created when a function "remembers" and can access variables from its outer (enclosing) scope, even after that outer function has finished executing. It's JavaScript's mechanism for data privacy and the foundation of the module pattern.

The counter with private state: the inner function closes over count — nobody outside can read or modify it except through the returned methods. This is how React's useState works conceptually: the state value is held in a closure managed by React's fiber reconciler.

Counter with Private State via Closure
function createCounter(initial = 0) {
  let count = initial;  // Private — inaccessible from outside

  return {
    increment() { return ++count; },
    decrement() { return --count; },
    getValue() { return count; },
    reset()    { count = initial; return count; },
  };
}

const counter = createCounter(5);
counter.increment();  // 6
counter.count;        // undefined — private!
3
What's the difference between var, let, and const? Explain hoisting and the Temporal Dead Zone.
Beginner
What interviewer is evaluating: Hoisting beyond "var moves to the top." Do you understand the TDZ? Can you explain why let/const have a TDZ? This separates devs who memorized from devs who understand the spec.

Model Answer: All three are hoisted, but differently. var: Hoisted and initialized to undefined. You can access a var before its declaration and get undefined (not an error). let/const: Hoisted but NOT initialized. The period between the start of the scope and the actual declaration is the Temporal Dead Zone (TDZ). Accessing a let/const variable in the TDZ throws a ReferenceError. const additionally requires initialization at declaration and prevents reassignment (but not mutation of objects/arrays).

The TDZ exists to catch bugs — accessing a variable before declaration is almost always a mistake. Browsers implemented this deliberately to help developers; it's not a spec curiosity. Use const by default, let when reassignment is needed, and never var in modern code.

TDZ Demonstration
console.log(a);  // undefined (var is hoisted + initialized)
var a = 5;

console.log(b);  // ReferenceError: Cannot access 'b' before initialization
let b = 10;        // b is hoisted but in TDZ until this line

Promise.all vs Promise.allSettled vs Promise.race vs Promise.any — when to use each?
Intermediate
What interviewer is evaluating: Practical async orchestration knowledge. Every production app makes parallel API calls. Do you know which combinator to use when?

Model Answer: Promise.all: All succeed → array of results. Any reject → immediately rejects. Use for independent, all-required data: fetch user profile + settings + permissions — if any fail, the page can't render. Promise.allSettled: Waits for all to finish (success or failure). Returns array of {status, value/reason}. Use for independent, non-blocking data: dashboard with 5 widgets — one failing shouldn't break the others. Promise.race: Resolves/rejects with first to settle. Use for timeouts: race a fetch against a timeout promise. Promise.any: Resolves with the first successful promise. Rejects only if all fail (with AggregateError). Use for redundant requests: fetch from primary CDN, fallback to secondary — whichever responds fastest wins.

Intermediate
What interviewer is evaluating: Can you write generics beyond Array<T>? Do you understand constraints (extends), keyof, and how generics compose? This is a senior-level discriminator.

Model Answer: Generics are type parameters that make functions, classes, and interfaces reusable across different types while preserving type safety. Instead of any (which loses type info), generics capture the type and use it consistently.

Generic pick + keyof constraint
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  return keys.reduce((acc, key) => ({ ...acc, [key]: obj[key] }), {} as Pick<T, K>);
}

6
this keyword — explain call, apply, bind, and arrow function behavior.
Intermediate
What interviewer is evaluating: this is the most misunderstood JS concept. The interviewer wants to see you explain the 4 binding rules and arrow function behavior clearly. Bonus: mention that arrow functions don't have their own this — they capture it from the enclosing lexical scope.

Model Answer: The value of this is determined by how a function is called, not where it's defined (for regular functions). Four rules in priority order: (1) new binding: when called with new, this is the new instance. (2) Explicit binding: call, apply, bind set this explicitly. call passes args individually, apply as an array, bind returns a new function with permanently bound this. (3) Implicit binding: when called as obj.method(), this is obj. (4) Default binding: in non-strict mode, this is the global object (window); in strict mode, this is undefined.

Arrow functions break these rules: they don't have their own this. They capture this from the surrounding lexical scope at creation time. This is why arrow functions are perfect for React class component event handlers and callbacks — no need for .bind(this).

7
Explain prototypal inheritance. How does it differ from classical inheritance?
Advanced
What interviewer is evaluating: Can you explain the core mechanism JavaScript uses for inheritance? The __proto__ chain, Object.create, and how class syntax is just sugar over prototypes. Tests whether you understand what's happening under the hood.

Model Answer: In classical inheritance (Java, C++), classes are blueprints and objects are instances — you create an object from a class. In prototypal inheritance (JavaScript), objects inherit directly from other objects via the prototype chain. Every object has an internal [[Prototype]] link (accessible via __proto__ or Object.getPrototypeOf). When you access a property, JS walks the prototype chain until it finds it or reaches null (the top).

The class syntax introduced in ES6 is syntactic sugar over prototypes. class Dog extends Animal creates a prototype chain: Dog.prototype.__proto__ === Animal.prototype. The key difference: prototypal inheritance is more flexible — you can change an object's prototype at runtime, create objects without classes (Object.create(null)), and share behavior through delegation (composition) rather than rigid hierarchies.

10
Write a debounce function from scratch. Then explain when you'd use leading vs trailing edge.
Intermediate

Model Answer: Debounce delays execution until the caller stops invoking for a specified delay. Trailing edge (default): invoke at the end — perfect for search autocomplete (wait until user stops typing). Leading edge: invoke on the first call, then block subsequent calls — perfect for button clicks (prevent double-submit: fire immediately, ignore rapid clicks). Both: first call fires immediately, last call fires after the burst — used for window resize (immediate feedback + final accurate call).

Debounce — Production-Ready
function debounce(fn, delay, opts = {}) {
  const { leading = false, trailing = true } = opts;
  let timerId = null;
  let lastArgs, lastThis;

  const invoke = () => { fn.apply(lastThis, lastArgs); lastArgs = lastThis = null; };

  function debounced(...args) {
    lastArgs = args; lastThis = this;
    if (timerId) clearTimeout(timerId);
    else if (leading) invoke();
    if (trailing) timerId = setTimeout(() => { timerId = null; invoke(); }, delay);
  }

  debounced.cancel = () => { clearTimeout(timerId); timerId = lastArgs = lastThis = null; };
  return debounced;
}

1
Explain React's reconciliation algorithm. What is the Virtual DOM and why does it exist?
Intermediate
What interviewer is evaluating: Can you explain the "why" behind React's architecture, not just the "what"? Tests whether you understand the performance problem the Virtual DOM solves.

Model Answer: The Virtual DOM is an in-memory JavaScript object representation of the real DOM. React uses it to solve the core problem: direct DOM manipulation is expensive — every DOM write triggers layout, paint, and composite. Instead of touching the real DOM on every state change, React: (1) Creates a new Virtual DOM tree in memory (cheap, pure JS objects). (2) Diffs it against the previous Virtual DOM tree using a reconciliation algorithm (O(n) heuristics: different element types → full rebuild, same type → update props only, lists need key for stable identity). (3) Computes the minimal set of real DOM operations needed (batch update). (4) Applies them in a single synchronous commit phase.

The Virtual DOM is not "faster than the real DOM" — operations on it are faster, but React also has to apply changes to the real DOM eventually. The value is: (a) declarative programming model — you describe what the UI should look like, React figures out how to get there, (b) cross-platform abstraction — the same reconciliation works for React Native, React PDF, React 3D, (c) batching — multiple state updates in one event handler produce one commit.

2
What problem do React hooks solve? Compare a class component lifecycle to useEffect.
Intermediate
What interviewer is evaluating: Do you understand the motivation behind hooks? Can you articulate the problems with class components (this binding, HOC wrapper hell, scattered logic) and how hooks solve them?

Model Answer: Class components suffered from three fundamental problems: (1) Scattered logic: Related logic was split across componentDidMount, componentDidUpdate, and componentWillUnmount. A single concern (e.g., subscribing to chat messages) had code in 3 different lifecycle methods. (2) Wrapper hell: Sharing stateful logic required Higher-Order Components or Render Props, creating deeply nested component trees that were hard to debug. (3) this confusion: Event handlers needed .bind(this) or arrow functions, confusing new developers. Hooks solve these: useEffect colocalizes setup and cleanup, custom hooks share logic without wrapper components, and there's no this.

useEffect mapping: useEffect(fn) without deps → runs after every render (like componentDidMount + componentDidUpdate combined). useEffect(fn, []) with empty array → runs once (componentDidMount). useEffect(fn, [dep]) → runs when dep changes. The cleanup function returned from useEffect replaces componentWillUnmount.

3
useMemo vs useCallback vs React.memo — when does each actually prevent re-renders?
Intermediate
What interviewer is evaluating: Can you explain the "referential equality" problem? Do you know that misuse of these hooks can make performance worse? Tests practical experience over documentation reading.

Model Answer: React.memo: Wraps a component. If props haven't changed (shallow comparison), skip re-render. Best for "pure" components that render often with the same props. useMemo: Memoizes a computed value. The computation only re-runs if dependencies change. Best for expensive calculations (sorting/filtering large arrays, derived data). useCallback: Memoizes a function reference. Returns the same function instance unless dependencies change. Best when passing callbacks to memoized child components (prevents them from re-rendering).

Anti-patterns: Wrapping every function in useCallback adds overhead without benefit — the memoization itself has a cost. Only use these hooks when: (a) you have measured a performance issue, or (b) the value is a dependency of another hook that would cause cascading effects. Premature optimization with these is the most common React performance mistake.

4
Explain React Fiber. What problem did it solve that the old Stack Reconciler couldn't?
Advanced
What interviewer is evaluating: Fiber is the architectural change that enabled concurrent React. Can you explain the scheduling problem, time-slicing, and priority-based rendering?

Model Answer: The old Stack Reconciler processed the Virtual DOM tree synchronously in a single pass — once reconciliation started, it couldn't be interrupted. This meant: (a) large component trees blocked the main thread (janky animations, unresponsive inputs), (b) React couldn't prioritize urgent updates (user typing) over less urgent ones (data fetching results).

Fiber re-architected reconciliation as a linked list of "units of work" (fiber nodes). Core innovations: (1) Incremental rendering: work can be split into chunks and spread across multiple frames. (2) Pause/resume: React can pause work to handle a higher-priority update, then resume. (3) Priority levels: user interactions (clicks, typing) get higher priority than data fetching. (4) Concurrent Mode / Features: Suspense, useTransition, useDeferredValue all depend on Fiber's ability to interrupt and reprioritize work. The requestIdleCallback-like scheduling is how React cooperates with the browser's event loop.

5
useRef — give me 3 practical use cases beyond accessing DOM elements.
Intermediate

Model Answer: (1) Mutable values that shouldn't trigger re-renders: tracking previous values (previous props/state for comparison), interval IDs, animation frame IDs — things you need to persist across renders but aren't visual state. (2) Stale closure workaround: storing the latest value of a prop or state in a ref so callbacks (setInterval, event listeners) always read the current value without re-creating the callback. This is the core pattern used in the production bug fix from earlier. (3) Imperative handle exposure: useImperativeHandle + forwardRef to expose methods from a child to a parent (focus input, scroll to section, trigger animation) — the escape hatch when the declarative model doesn't fit.

useRef for avoiding stale closures
function useLatest(value) {
  const ref = useRef(value);
  ref.current = value;  // Always keep ref in sync, no re-render
  return ref;
}

// Usage: callback always reads the latest props without re-creating itself
function ChatRoom({ roomId }) {
  const latestRoomId = useLatest(roomId);

  useEffect(() => {
    const interval = setInterval(() => {
      fetchMessages(latestRoomId.current);  // Always current
    }, 5000);
    return () => clearInterval(interval);
  }, []);  // No roomId dependency — interval never restarts
}
6
What are React Server Components? How do they differ from SSR?
Advanced
What interviewer is evaluating: This is the future of React. Do you understand RSC vs SSR? SSR renders the component tree to HTML on the server (runs once), then hydrates on the client. RSC runs components exclusively on the server — they never ship to the client. Client components run in both places.

Model Answer: SSR (Server-Side Rendering): React renders the component tree to HTML on the server. The HTML is sent to the client. Then React hydrates — attaching event listeners and making the page interactive. The same component code runs on both server and client. Bundled JavaScript for ALL components is still sent to the client.

RSC (React Server Components): Server Components never run on the client. Their JavaScript is never sent to the browser. They can directly access databases, file systems, and backend services — no API layer needed. Benefits: (a) Zero bundle size impact for server-only components (imagine a markdown renderer that stays on the server), (b) Direct backend access — no REST/GraphQL layer for data fetching, (c) Automatic code splitting — client boundaries define split points. The tradeoff: Server Components can't use state, effects, or browser APIs — they're pure render functions.

Custom hooks — write a useFetch hook with loading, error, data, and abort support.
Intermediate
useFetch — Production Quality
function useFetch<T>(url: string) {
  const [state, setState] = useState<AsyncState<T>>({ status: 'loading' });

  useEffect(() => {
    if (!url) return setState({ status: 'idle' });

    const controller = new AbortController();
    setState({ status: 'loading' });

    fetch(url, { signal: controller.signal })
      .then(res => { if (!res.ok) throw new Error(`HTTP ${res.status}`); return res.json(); })
      .then(data => setState({ status: 'success', data }))
      .catch(err => {
        if (err.name !== 'AbortError') {
          setState({ status: 'error', error: err });
        }
      });

    return () => controller.abort();  // Cleanup on unmount or url change
  }, [url]);

  return state;
}

Error Boundaries — what they are, what they can't catch, and how to structure them.
Intermediate

Model Answer: Error Boundaries are React components that catch JavaScript errors in their child component tree, log those errors, and display a fallback UI instead of crashing the whole app. They catch errors during: (a) rendering, (b) lifecycle methods, (c) constructors. They do NOT catch: (a) event handlers (use try/catch or Promise.catch), (b) async code (use .catch() or Error Boundary + state), (c) server-side rendering errors, (d) errors in the Error Boundary itself. Strategic placement: wrap route-level components, widget-level components, and third-party integrations. Avoid wrapping the entire app in one boundary — a single error shouldn't take down the header, sidebar, and all content simultaneously.

Error Boundary (Class — hooks don't support componentDidCatch yet)
class ErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, errorInfo) {
    logErrorToService(error, errorInfo);  // Datadog / Sentry
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback || <h1>Something went wrong.</h1>;
    }
    return this.props.children;
  }
}
9
useReducer vs useState — when should you reach for useReducer?
Intermediate

Model Answer: useState is best for independent, simple state values. useReducer shines when: (1) Complex state shape: objects with multiple interdependent fields (form with 10 fields + validation state). (2) Next state depends on previous state: counters, toggles — reducer makes the transition explicit. (3) Multiple state updates in one action: submitting a form sets loading=true, clears errors, disables the button — one dispatch instead of 3 setState calls. (4) Testability: reducers are pure functions — testable without React. The heuristic: if a state update touches more than 2 state variables simultaneously, use useReducer. It also keeps the state transitions predictable when the component grows.

10
How would you optimize a React app that renders a list of 10,000 items?
Advanced

Model Answer: (1) Windowing/Virtualization: Libraries like react-window or @tanstack/virtual render only the visible items + a small buffer. A 10K-item list with 20px row height means only ~40 items are in the DOM at any time. (2) React.memo + useCallback: Wrap each list item in React.memo and memoize callbacks so items don't re-render when their data hasn't changed. (3) useMemo for derived data: If you're filtering/sorting, memoize the filtered list so it doesn't recompute on every render. (4) useDeferredValue: For search/filter on the list, use useDeferredValue to keep the input responsive while the list updates in the background. (5) Web Worker for heavy processing: Offload filtering/sorting of 10K items to a Web Worker so the main thread stays free for rendering. (6) Paginate if possible: The best optimization is not rendering 10K items. Pagination or infinite scroll with a virtual list is the ideal solution.

Build a Typeahead / Autocomplete Component
Advanced

Requirements: (1) Debounced API call (300ms), (2) Keyboard navigation (Arrow Up/Down, Enter, Escape), (3) Highlight matching text in suggestions, (4) Loading and empty states, (5) Click outside to close, (6) ARIA attributes for accessibility (combobox role, aria-activedescendant, aria-expanded).

Typeahead — Key Implementation Points
// State: query, suggestions[], activeIndex, isLoading, isOpen
// Flow: onChange → debounce → fetch suggestions → render dropdown
// Keyboard: onKeyDown → ArrowDown: increment activeIndex, Enter: select, Escape: close
// Outside click: useRef on wrapper + useEffect with document click listener
// ARIA: input[role=combobox][aria-expanded][aria-autocomplete=list],
//        ul[role=listbox], li[role=option][aria-selected]

function Typeahead({ fetchSuggestions }) {
  const [query, setQuery] = useState('');
  const [suggestions, setSuggestions] = useState([]);
  const [activeIndex, setActiveIndex] = useState(-1);
  const [isOpen, setIsOpen] = useState(false);
  const [isLoading, setIsLoading] = useState(false);
  const wrapperRef = useRef(null);
  const listRef = useRef(null);

  const debouncedFetch = useMemo(
    () => debounce(async (q) => {
      setIsLoading(true);
      const results = await fetchSuggestions(q);
      setSuggestions(results);
      setIsLoading(false);
      setIsOpen(results.length > 0);
      setActiveIndex(-1);
    }, 300),
    [fetchSuggestions]
  );

  const handleChange = (e) => {
    const val = e.target.value;
    setQuery(val);
    debouncedFetch(val);
  };

  const handleKeyDown = (e) => {
    switch (e.key) {
      case 'ArrowDown':
        e.preventDefault();
        setActiveIndex(i => Math.min(i + 1, suggestions.length - 1));
        break;
      case 'ArrowUp':
        e.preventDefault();
        setActiveIndex(i => Math.max(i - 1, -1));
        break;
      case 'Enter':
        if (activeIndex >= 0) selectSuggestion(suggestions[activeIndex]);
        break;
      case 'Escape':
        setIsOpen(false);
        break;
    }
  };

  // Outside click handler using wrapperRef — omitted for brevity
  // Highlight matching text: split suggestion by query, wrap matches in <mark>
  // Empty state: "No results for '{query}'"
  // Loading state: spinner inside dropdown
}
What They're Testing

States covered: idle, loading, results, empty, error. Interactions: click, keyboard, blur. Accessibility: ARIA roles and live regions. Edge cases: fast typing (debounce), stale responses (ignore if query changed), empty query (close dropdown).

Implement a Virtualized List
Expert
Requirements

Render a scrolling list of 100K items without performance degradation. Only render items visible in the viewport + a small overscan buffer. Support variable height items (measure after render). The user should not notice that items are being recycled.

Virtualized List — Core Algorithm
function VirtualList({ items, itemHeight, overscan = 5 }) {
  const [scrollTop, setScrollTop] = useState(0);
  const [containerHeight, setContainerHeight] = useState(0);
  const containerRef = useRef(null);

  useEffect(() => {
    const el = containerRef.current;
    setContainerHeight(el.clientHeight);
    const observer = new ResizeObserver(() => setContainerHeight(el.clientHeight));
    observer.observe(el);
    return () => observer.disconnect();
  }, []);

  const handleScroll = useCallback(
    throttle(() => {
      setScrollTop(containerRef.current.scrollTop);
    }, 16),  // ~60fps
    []
  );

  // Visible range calculation
  const startIndex = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan);
  const endIndex = Math.min(
    items.length,
    Math.ceil((scrollTop + containerHeight) / itemHeight) + overscan
  );

  const visibleItems = items.slice(startIndex, endIndex);
  const totalHeight = items.length * itemHeight;
  const offsetY = startIndex * itemHeight;

  return (
    <div
      ref={containerRef}
      onScroll={handleScroll}
      style={{ height: 600, overflow: 'auto' }}
    >
      <div style={{ height: totalHeight, position: 'relative' }}>
        <div style={{ transform: `translateY(${offsetY}px)` }}>
          {visibleItems.map((item, i) => (
            <div key={startIndex + i} style={{ height: itemHeight }}>
              {item}
            </div>
          ))}
        </div>
      </div>
    </div>
  );
}
Bonus Points

Variable height: maintain a Map<index, height> and use getBoundingClientRect() after render to measure actual heights, accumulating offsets. Intersection Observer for lazy image loading within virtualized items. Mention that this is what libraries like react-window and @tanstack/virtual do.

Design a Notification System

Requirements

Build a notification system supporting: (1) Multiple types: success, error, warning, info, (2) Auto-dismiss with configurable duration, (3) Stacking (max 5 visible), (4) Animations (slide in, fade out), (5) Pause timer on hover, (6) Action buttons (Undo, Retry), (7) Global store accessible from anywhere.

Notification System — Store + Provider Pattern
// store.ts — Zustand for simplicity
import { create } from 'zustand';

let nextId = 0;

export const useNotificationStore = create(set => ({
  notifications: [],

  addNotification: (notification) => {
    const id = ++nextId;
    // Config defaults
    const config = {
      duration: 5000,
      type: 'info',
      ...notification,
      id,
    };

    set(state => ({
      // Max 5 — remove oldest if exceeding
      notifications: [...state.notifications, config].slice(-5),
    }));

    if (config.duration > 0) {
      setTimeout(() => useNotificationStore.getState().removeNotification(id), config.duration);
    }

    return id;
  },

  removeNotification: (id) =>
    set(state => ({ notifications: state.notifications.filter(n => n.id !== id) })),
}));

// Usage: toast.success('File saved', { action: { label: 'Undo', onClick: undo } })
Architecture Notes

Use a fixed-position container (top-right) with pointer-events: none so the overlay doesn't block clicks, but pointer-events: auto on notifications themselves. CSS transitions for enter/exit (slide-in-from-right, fade-out). Pause timers on hover: set a ref flag isHovered, clear the timeout on hover, restart on mouse leave. Action buttons: render inside the notification with onClick handlers that call back into the store or trigger side effects. For React Native: use Animated API instead of CSS transitions.

How do you handle a situation where a teammate's code quality is consistently below the bar?
Advanced

Model Answer: (1) Never assume malice or laziness — assume a skill gap, unclear expectations, or pressure to ship fast. (2) Start with a private, specific, and kind conversation: "I noticed the last 3 PRs had the same patterns — missing error states, no tests for the unhappy path. Can we pair on the next one? Salary Negotiation Strategy & Questions to Ask
P1
The Negotiation Script

Before the offer: Never give a number first. When they ask about salary expectations, say: "I'm focused on finding the right role and team. I'm confident that if we're a mutual fit, we'll find a fair number. What's the budgeted range for this role?" This makes them anchor first.

After receiving an offer: "Thank you — I'm really excited about the team and the role. Let me review the full package and get back to you in [24-48 hours]." Never accept on the spot. You need time to evaluate equity, benefits, and counteroffer if you have competing offers.

Counteroffer script: "Based on my research and [competing offer / market data], I was targeting [X base + Y equity]. Is there flexibility on the base or equity? I'm ready to sign if we can get to [target number]." Always justify with data, never with "I feel I deserve more."

Total compensation levers (in order of negotiability): (1) Sign-on bonus — easiest, comes from a different budget, (2) Equity / RSUs — often flexible, (3) Base salary — harder because it sets precedent for raises, (4) Performance bonus percentage — usually fixed by level.

10 Questions to Ask the HR/Recruiter
  1. "What does the career progression look like from this level? What separates 'meets expectations' from 'exceeds expectations'?"
  2. "How does the performance review cycle work? What metrics are used to evaluate engineers?"
  3. "What's the on-call expectation for this role? How frequent are incidents and what's the typical page volume?"
  4. "How does the team handle tech debt? Is there dedicated time or is it ad-hoc?"
  5. "What's the ramp-up expectation for the first 90 days? What would success look like at 3, 6, and 12 months?"
  6. "How does the team make technical decisions? Is there an RFC process or architecture review board?"
  7. "What's the ratio of greenfield to maintenance work on this team?"
  8. "How is the engineering organization structured? Who does this role report to and who reports to them?"
  9. "What's the remote/hybrid policy? How does the team handle async communication across time zones?"
  10. "What's the biggest challenge the team is facing right now that I could help solve?"
Red Flags to Watch For

(1) "We work hard and play hard" = expect 60-hour weeks. (2) Vague answers about on-call or tech debt = they're hiding something. (3) "We're like a family" = poor boundaries. (4) No clear career ladder = you'll stagnate. (5) High turnover mentioned casually — ask: "What's the average tenure on this team?" (6) "We'll figure out the process as we go" = chaos. (7) The offer has an exploding deadline (< 48 hours) = pressure tactic. (8) They can't explain what the next 6 months look like = no roadmap.
