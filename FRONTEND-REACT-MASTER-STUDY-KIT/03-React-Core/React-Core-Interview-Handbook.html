Q1 What is React's Virtual DOM, and how does reconciliation work? Intermediate P1
Short Answer

The Virtual DOM is a lightweight JavaScript representation of the real DOM. When state changes, React creates a new Virtual DOM tree, diffs it against the previous one (reconciliation), and computes the minimal set of DOM mutations needed. This batched approach avoids expensive direct DOM manipulation and makes React fast even for complex UIs.

Easy Explanation

Imagine you're remodeling a room. Instead of tearing down walls and rebuilding everything from scratch whenever you want to move a chair, you sketch the new layout on paper first, compare it with the current layout, and only move the pieces that actually changed. React's Virtual DOM is that sketch — it figures out the smallest number of changes needed, then applies just those changes to the real room (the browser DOM).

Real-World Example

When you toggle a todo item's completion status, React doesn't rebuild the entire todo list. Instead, it compares the old VDOM tree with the new one, sees that only one <li> changed its class, and updates exactly that element's classList — nothing else gets touched.

Why Asked

Interviewers want to know you understand what React actually does under the hood, not just that it's "fast." This separates devs who copy-paste from those who can debug performance issues. If you can explain reconciliation, you can explain why keys matter, why mutations are bad, and why React.memo sometimes helps.

Common Mistake

Saying "Virtual DOM is faster than the real DOM." The Virtual DOM is slower than direct, surgical DOM manipulation. Its advantage is that developers write declarative "what should the UI look like" code while React handles the imperative "make it so" part efficiently — better than a developer writing manual DOM updates for complex UIs.

Senior Insight

Reconciliation uses a heuristic O(n) diffing algorithm with two key assumptions: (1) elements of different types produce different trees, (2) developers can hint at stable identity via the key prop. This is why React doesn't try to be perfectly optimal — full tree diffing is O(n³), which would be unusable. Instead, React makes pragmatic tradeoffs that are fast enough for real-world UIs.

Code Example
Reconciliation in Action
// State change triggers re-render
const [todos, setTodos] = useState([{ id: 1, text: 'Learn React', done: false }]);

const toggleDone = useCallback((id) => {
  setTodos(prev => prev.map(todo =>
    todo.id === id ? { ...todo, done: !todo.done } : todo
  ));
}, []);

// React diffs old VDOM vs new VDOM
// Only the toggled <li> gets a DOM update

Summary
  • Virtual DOM = JavaScript object mirroring real DOM structure (lightweight, ~100x faster to diff than real DOM ops)
  • Reconciliation = diffing algorithm comparing old and new VDOM trees
  • O(n) heuristic: different types → full replace; same type → update props; keys guide list diffing
  • React batches VDOM updates and applies minimal DOM mutations in a single commit phase
Q2 What is JSX, and how does it get transformed into JavaScript? Beginner P1
Short Answer

JSX is a syntax extension for JavaScript that looks like HTML but compiles to React.createElement() calls (or jsx() / jsxs() with the React 17+ automatic transform). Babel or TypeScript handles this compilation, converting angle-bracket markup into plain function calls that produce the Virtual DOM tree.

Easy Explanation

Your browser doesn't understand <div className="app">Hello</div> — it only understands JavaScript. JSX is like shorthand: you write HTML-ish code, and Babel (the translator) turns each tag into a createElement('div', { className: 'app' }, 'Hello') call. It's syntactic sugar that makes component code readable.

Key Distinction

JSX is not a templating language like Handlebars or EJS. It's a syntax extension that compiles directly to JavaScript — which means you can use the full power of JavaScript inside it (expressions, functions, maps, ternaries). The curly braces {} aren't template interpolation; they're JavaScript expression boundaries.

Why Asked

If you've only used JSX without understanding the compilation step, you'll struggle to debug "why isn't this rendering," misunderstand key prop errors, or misuse expressions vs statements in JSX. This question tests whether you understand what you're actually writing.

Code Example
JSX → Classic Transform (React 16)
// You write:
const element = <h1 className="greeting">Hello, world!</h1>;

// Babel compiles to:
const element = React.createElement(
  'h1',
  { className: 'greeting' },
  'Hello, world!'
);
React 17+ Automatic JSX Transform
// With the new transform, no React import needed!
// Babel injects: import { jsx as _jsx } from 'react/jsx-runtime';
const element = _jsx('h1', {
  className: 'greeting',
  children: 'Hello, world!'
});
Why the New Transform Matters

The React 17+ JSX transform eliminates the need to import React at the top of every JSX file, reduces bundle size slightly, and paves the way for future features like Server Components where createElement has different semantics.

Follow-up Questions

  • What's the difference between jsx() and jsxs() in the new transform?
  • How does JSX handle boolean, null, and undefined children?
  • Can you write React without JSX? Show me how.
  • How does the new JSX transform affect Server Components?
Memory Trick: "JSX is HTML in your JS, Babel turns it into function calls, React turns those into DOM." — Three layers: syntax → compile → runtime.
Summary
  • JSX = syntactic sugar for React.createElement() (classic) or jsx()/jsxs() (automatic)
  • Compiled by Babel/TypeScript during build, not at runtime
  • Attributes are camelCase (className, onClick, htmlFor)
  • Expressions in {} must evaluate to a value — no statements (if, for, while)
  • React 17+ transform: no import React needed in JSX files
Q3 useState Deep Dive — Closure trap, functional updater, and batching Intermediate P1
Short Answer

useState returns a state value and an updater function. The state value is a snapshot captured at render time — the famous "closure trap." The functional updater setState(prev => newVal) reads the latest state from React's internal queue, avoiding stale closures. Since React 18, state updates are automatically batched in all contexts (timeouts, promises, event handlers).

Easy Explanation

Think of useState like taking a Polaroid photo. When your component renders, React takes a snapshot of all state values. That snapshot is frozen — if state changes later, your current render's closure still sees the old photo. The functional updater is like asking, "What's the current state right now?" instead of looking at the old photo.

The Closure Trap — Most Common Pitfall

Calling setCount(count + 1) three times in a row only increments by 1, not 3. Why? count is a const — it's the value from the current render's snapshot. Each call reads the same snapshot value. The fix: setCount(prev => prev + 1), which reads from React's internal pending state queue.

Code Example
Closure Trap vs Functional Updater
function Counter() {
  const [count, setCount] = useState(0);

  const handleClickWrong = () => {
    setCount(count + 1); // count = 0
    setCount(count + 1); // count STILL 0 (same render snapshot)
    setCount(count + 1); // count STILL 0 → result: 1
  };

  const handleClickRight = () => {
    setCount(prev => prev + 1); // prev = 0 → queues 1
    setCount(prev => prev + 1); // prev = 1 → queues 2
    setCount(prev => prev + 1); // prev = 2 → result: 3
  };

  return <div>Count: {count}</div>;
}
Batching Deep Dive

Before React 18, only state updates inside React event handlers were batched. Updates in setTimeout, Promise.then(), or native event listeners would trigger separate re-renders. React 18 introduced automatic batching everywhere via createRoot. If you absolutely need to opt out (rare), use flushSync().

  • When would you use flushSync and why is it discouraged?
  • How does the "state as a snapshot" mental model help avoid bugs?
  • What's the difference between lazy initializers (useState(() => expensive())) and passing a value directly?
  • How do you handle objects/arrays in state without mutation?
Memory Trick: "setState(value) reads from the wall (snapshot). setState(fn) reads from the queue." — Always use the function form when new state depends on old state.
Summary
  • State is a snapshot frozen at render time — closures capture that value
  • Functional updater prev => newVal always reads the latest value from React's queue
  • React 18 batches all state updates automatically (event handlers, timeouts, promises)
  • Lazy initializer useState(() => compute()) runs only on first render
  • Never mutate objects/arrays in state — always create new references
Q4 useEffect Deep Dive — Dependencies, cleanup, and preventing infinite loops Intermediate P1
Short Answer

useEffect runs side effects after React commits to the DOM. The dependency array controls when the effect re-runs: [] = mount only, [dep1, dep2] = on mount and whenever dep changes, omitted = after every render. The cleanup function runs before re-execution and on unmount. Infinite loops happen when effects update state that's in their dependency array without a guard condition.

Easy Explanation

Picture useEffect as a note you leave for React: "After you finish painting the screen, do this thing." The dependency array is a checklist — React checks if any items changed since last time. If yes, it runs your effect again. The cleanup function is like: "Before you do the next thing (or leave), clean up from the last one."

Real-World Example

Subscribing to a chat room: when the user switches from room #general to room #random, you want to unsubscribe from #general and subscribe to #random. The dependency is roomId. The cleanup function handles unsubscribing. Without cleanup, you'd accumulate WebSocket connections to every room the user visited.

Infinite Loop Causes & Fixes

Cause 1: Object/array in deps recreated every render: useEffect(fn, [{ id: 1 }]) — new reference each time. Fix: useMemo or extract primitives.
Cause 2: Function in deps recreated every render. Fix: useCallback or move function inside effect.
Cause 3: Effect sets state, state is in deps, no stable condition. Fix: add guard clause or use functional updater.

Code Example
Proper Data Fetching with AbortController
function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const controller = new AbortController();

    async function fetchUser() {
      try {
        const res = await fetch(`/api/users/${userId}`, {
          signal: controller.signal,
        });
        if (!controller.signal.aborted) {
          setUser(await res.json());
        }
      } catch (err) {
        if (err.name !== 'AbortError') throw err;
      }
    }

    fetchUser();

    return () => controller.abort(); // Cleanup: cancel on unmount/dep change
  }, [userId]);

  if (!user) return <Spinner />;
  return <div>{user.name}</div>;
}
useEffect vs Event Handlers — The Mental Model

Ask yourself: "Is this code running because the component rendered?" If yes, it's an Effect. If it runs because a user clicked a button, it should be in an event handler. React's own docs now recommend reaching for useEffect as a last resort, not a first instinct. Many "effects" are actually event-driven logic in disguise.

  • What's the difference between useEffect and useLayoutEffect?
  • How do you handle race conditions when multiple effects fire rapidly?
  • Why is useEffect not ideal for data fetching in React 18+?
  • What happens if you omit the dependency array entirely?
Memory Trick: "Effect runs AFTER paint. Cleanup runs BEFORE next effect. Dependencies answer 'when should I re-sync?'" — Think of useEffect as a synchronization mechanism, not a lifecycle method.
Summary
  • Effects run after commit (post-paint), not during render
  • Cleanup runs before re-execution AND on unmount
  • Dependency array: React compares with Object.is — objects/functions cause re-runs
  • Always use AbortController for fetch cleanup to prevent memory leaks
  • Prefer event handlers over effects; effects are for external synchronization
Q5 useRef Deep Dive — DOM refs, mutable values, and forwardRef Intermediate P1
Short Answer

useRef creates a mutable object { current: initialValue } that persists across renders. Unlike state, changing .current doesn't trigger re-renders. Primary use cases: (1) accessing DOM elements directly, (2) storing mutable values that shouldn't cause re-renders (timers, previous values, instance variables), (3) avoiding stale closures in callbacks. forwardRef lets parent components access a child's DOM node or custom imperative handle.

Easy Explanation

State is like a whiteboard — every time you write on it, everyone looks up and sees the new value. Refs are like a sticky note in your pocket — you can change it anytime, but nobody else notices or reacts to it. It's your personal scratchpad that survives between renders without causing commotion.

Ref vs State — When to Use Each
ScenarioUseWhy
Data that should update the UIuseStateTriggers re-render
DOM element accessuseRefRead DOM node directly
Timer/interval IDsuseRefPersist without re-render
Previous value trackinguseRefStore last render's value
Event handler stable referenceuseRef + useEffectAvoid stale closures
Code Example
Input Focus + Previous Value + forwardRef
// forwardRef: parent gets access to child's input
const Input = React.forwardRef<HTMLInputElement, Props>((props, ref) => {
  return <input ref={ref} { ...props} />;
});

function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T>();
  useEffect(() => { ref.current = value; });
  return ref.current; // Returns previous value (before current render)
}

function Parent() {
  const inputRef = useRef<HTMLInputElement>(null);
  const countRef = useRef(0); // Mutable counter, no re-render

  const handleClick = () => {
    inputRef.current?.focus();
    countRef.current += 1;
    console.log(`Focused ${countRef.current} times`);
  };

  return <Input ref={inputRef} placeholder="Type here" />;
}
Ref Callback Pattern (Often Overlooked)

You can pass a function to ref: ref={(node) => { ... }}. This fires when the element mounts and unmounts (node = null). Useful when you need to run setup/teardown logic on a DOM element — measuring size, initializing a third-party library, or managing a list of dynamic refs.

Q6 Why are keys important in React lists, and why is index an anti-pattern? Beginner P1
Short Answer

Keys help React identify which items in a list have changed, been added, or been removed during reconciliation. Without stable keys, React re-renders more DOM nodes than necessary or, worse, reuses component state incorrectly. Using array index as key is an anti-pattern because when the list order changes, the same index points to a different item, causing React to mismatch state and DOM nodes.

Easy Explanation

Imagine you label 10 boxes with numbers 0–9 based on their position. If you remove box #3, all boxes shift: box #4 becomes #3, #5 becomes #4, etc. Now every label is wrong. If instead each box had a unique name label ("shoes", "books", "toys"), removing one box doesn't affect the others' identities. Index keys are position labels; stable IDs are identity labels.

Why Index Keys Break Component State

Consider a list of <TodoInput /> components each with local state (the input text). If you delete the first item, index-based keys cause React to think item[0] just changed props rather than being removed — the first component's state (and DOM node) is reused for the second item, and the last component is unmounted. Result: the wrong text stays in the wrong input field.

Code Example
Stable Keys Prevent State Corruption
// Bad: index as key
{todos.map((todo, index) => (
  <TodoItem key={index} todo={todo} />
))}

// Good: stable unique ID
{todos.map((todo) => (
  <TodoItem key={todo.id} todo={todo} />
))}

// Acceptable edge case: static list that NEVER reorders
{labels.map((label, i) => (
  <option key={i} value={label}>{label}</option>
))}
UUIDs vs nanoid vs Database IDs

Avoid generating keys on the fly: key={Math.random()} or key={crypto.randomUUID()}. This creates a new key every render, forcing React to unmount and remount every item — the worst possible outcome. Keys must be stable across renders. Use database IDs, content hashes, or nanoid generated once at item creation time.

Follow-up Questions
  • What happens if two list items have the same key?
  • How does React use keys internally during the reconciliation diffing algorithm?
  • Why does key not appear in props even though you pass it to a component?
  • When is using index as key actually harmless?
  • How do keys affect React's ability to preserve component state across reorders?
Memory Trick: "Keys are not props — they're identity cards for React's diffing algorithm. Index says 'position X.' Stable ID says 'item Y.'" — If the list order changes, index is a lie.
Summary
  • Keys tell React which DOM nodes to reuse during reconciliation
  • Index as key = broken when list reorders, filters, adds, or removes items
  • Stable, unique IDs from your data model are the gold standard
  • Never generate keys during render (Math.random, Date.now, crypto.randomUUID)
  • Keys must be unique among siblings — they can repeat across different lists
Q7 Controlled vs Uncontrolled Components — When to use each Intermediate P1
Short Answer

A controlled component derives its value from React state — the component doesn't maintain its own internal value. Every keystroke triggers onChange → setState → re-render. An uncontrolled component lets the DOM manage its own state and accesses it via refs when needed (typically on submit). Controlled is the React-recommended approach for most scenarios; uncontrolled is simpler for basic forms and file inputs.

Easy Explanation

Controlled: React is a helicopter parent — every keystroke must go through state, React knows the value at all times. Uncontrolled: React is a hands-off parent — it only checks the form values when you submit, trusting the DOM to hold them in the meantime. One gives you more control; the other gives you less boilerplate.

The Hybrid Approach — React Hook Form

React Hook Form uses uncontrolled inputs with ref-based registration, giving you the best of both worlds: no re-renders on every keystroke (performance) with full form state tracking and validation. This is the production-recommended pattern for complex forms.

Code Example
Controlled vs Uncontrolled Side-by-Side
// CONTROLLED: React owns the value
function ControlledForm() {
  const [email, setEmail] = useState('');
  const [isValid, setIsValid] = useState(true);

  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    const val = e.target.value;
    setEmail(val);
    setIsValid(/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(val));
  };

  return <input value={email} onChange={handleChange} />;
}

// UNCONTROLLED: DOM owns the value, read on submit
function UncontrolledForm() {
  const inputRef = useRef<HTMLInputElement>(null);

  const handleSubmit = (e: FormEvent) => {
    e.preventDefault();
    console.log(inputRef.current?.value);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input defaultValue="" ref={inputRef} />
      <button type="submit">Submit</button>
    </form>
  );
}

Memory Trick: "Controlled = React is the boss (value from state). Uncontrolled = DOM is the boss (value from ref)." — <input value={x}> must have onChange; <input defaultValue={x}> doesn't.
Summary
  • Controlled: value from React state, onChange updates state — single source of truth
  • Uncontrolled: value lives in DOM, accessed via ref — less code, better perf for simple cases
  • File inputs are always uncontrolled (browser security)
  • React Hook Form uses uncontrolled + refs for performant, validated forms
  • Never mix controlled and uncontrolled on the same input (React warns)
Q8 Context API — How it works, performance pitfalls, and when NOT to use it Intermediate P1
Short Answer

Context provides a way to pass data through the component tree without manually threading props at every level. A Provider holds the value; any descendant useContext(MyContext) reads it. Performance pitfall: when context value changes, every consumer re-renders — even if they only use a subset of the context. This makes Context unsuitable for high-frequency state (theme is fine; form field values are not).

Easy Explanation

Props are like passing a note hand-to-hand through a crowd — every person in the chain has to touch it, even if they don't care about it. Context is like putting the note on a public bulletin board — anyone who wants it can look directly, and the people in between don't need to know about it. But the catch: if you change the bulletin board, everyone who was looking has to check it again.

The Context Re-render Trap

This is the most common Context performance issue: wrapping your entire app in a single context that holds all global state. Any change to any field re-renders every consumer. Split contexts by domain (AuthContext, ThemeContext, CartContext) and keep values that change independently in separate providers.

Code Example
Split Contexts to Avoid Unnecessary Re-renders
// BAD: Single context, everything re-renders on any change
const AppContext = createContext<{ user: User; theme: Theme; cart: CartItem[] }>(null!);

// GOOD: Separate contexts, consumers only re-render for their slice
const AuthContext = createContext<User | null>(null);
const ThemeContext = createContext<Theme>('light');
const CartContext = createContext<CartState>(null!);

// BONUS: Stable value object via useMemo to prevent re-renders
function CartProvider({ children }: { children: ReactNode }) {
  const [items, setItems] = useState<CartItem[]>([]);
  const value = useMemo(() => ({ items, setItems }), [items]);
  return <CartContext.Provider value={value}>{children}</CartContext.Provider>;
}
Context vs State Management Libraries

Context is NOT a state management replacement. It's a dependency injection mechanism. State management libraries (Zustand, Jotai, Redux Toolkit) offer selector-based subscriptions — components only re-render when their specific slice changes. Context can't do this natively. For high-frequency state, reach for a library; for low-frequency global config (theme, locale, auth), Context is perfect.

Follow-up Questions
  • How do you prevent re-renders when only part of a context changes?
  • What's the difference between Context and Redux/Zustand?
  • Can you use multiple providers of the same context? How does nesting work?
  • How does the children prop pattern help avoid context re-renders?
  • When would you use useContext vs prop drilling?
Memory Trick: "Context is a megaphone, not a telephone. Everyone hears the message, whether they need it or not." — Great for themes, terrible for typing in a form.
Summary
  • Context solves prop drilling by providing a direct data channel
  • Every consumer re-renders when context value changes — no selector mechanism
  • Split contexts by update frequency: theme (rare) separate from form state (frequent)
  • Always wrap context value in useMemo to prevent unnecessary consumer re-renders
  • For high-frequency global state, use Zustand/Jotai/Redux over raw Context
Q9 Component Lifecycle with Hooks — Mount, update, and unmount equivalents Intermediate P1
Short Answer

Hooks replace class component lifecycle methods with a unified model based on synchronization. useEffect(fn, []) = mount (componentDidMount); useEffect(fn, [deps]) = mount + update when deps change (componentDidUpdate); cleanup return from useEffect = unmount (componentWillUnmount). useLayoutEffect runs synchronously after DOM mutations but before paint — equivalent to the old componentDidMount/componentDidUpdate timing.

Easy Explanation

Think of your component's life like a hotel stay. Mount = checking in (set up your room, plug in devices). Update = housekeeping visits (tidy up, replace towels). Unmount = checking out (unplug devices, leave no trace). Hooks combine these into one mental model: "I need this thing to be in sync with these dependencies — set it up when I arrive, update it when deps change, and tear it down when I leave."

Real-World Example

A live stock ticker: mount → open WebSocket connection with stock symbol; update → symbol changes, close old WS and open new one; unmount → close WS connection. In hooks, this is one useEffect with symbol in the dependency array, and a cleanup function that closes the connection.

Code Example
Lifecycle with Hooks — Chat Room Subscription
function ChatRoom({ roomId }: { roomId: string }) {
  const [messages, setMessages] = useState<Message[]>([]);

  // Mount + Update + Unmount in ONE effect
  useEffect(() => {
    // MOUNT (and UPDATE when roomId changes)
    const connection = createConnection(roomId);
    connection.onMessage(setMessages);
    connection.connect();

    return () => {
      // UNMOUNT (cleanup before next effect or final unmount)
      connection.disconnect();
    };
  }, [roomId]); // Re-run effect when roomId changes

  // Derive data during render (replaces getDerivedStateFromProps)
  const unreadCount = messages.filter(m => !m.read).length;

  return <MessageList messages={messages} />;
}
Key Mental Shift

Stop thinking in terms of "mount/update/unmount" timelines. Think: "My effect synchronizes this external system with these React dependencies." This reframing eliminates entire categories of lifecycle-timing bugs. React's new docs explicitly teach this synchronization model over the lifecycle model.

Q10 React.memo, useMemo, useCallback — When they help and when they hurt Intermediate P1
Short Answer

React.memo skips re-rendering a component if its props haven't changed (shallow comparison). useMemo caches a computed value between renders. useCallback caches a function reference. They hurt performance when used unnecessarily: each carries overhead (comparison cost, memory allocation). Use them only when: (1) a component re-renders often with the same props, (2) a computation is expensive, or (3) a stable reference is needed for dependency arrays in other hooks.

Easy Explanation

Memoization is like bookmarking a recipe page. If you cook the same dish every day, a bookmark saves time. If you cook different dishes every day, the bookmark is wasted effort. React.memo says "don't re-render this component unless its ingredients (props) changed." But checking whether ingredients changed also takes work — so only bookmark things you cook frequently.

The "Memo All The Things" Anti-Pattern

Wrapping every component in React.memo and every callback in useCallback often makes your app slower. Each memo adds shallow comparison overhead. If a component almost always receives new props, the comparison is wasted CPU and the memo wrapper is dead code. Memoize strategically: start with the expensive operations, profile, then target specific components.

Code Example
Strategic Memoization
// React.memo: Only re-renders when props change
const ExpensiveList = React.memo(function ExpensiveList({ items }: { items: Item[] }) {
  return items.map(item => <ListItem key={item.id} item={item} />);
});

// useCallback: Stable reference for memo'd child props
function Parent({ userId }: { userId: string }) {
  // Without useCallback, handleDelete is new every render
  // → ExpensiveList re-renders even though items didn't change
  const handleDelete = useCallback((id: string) => {
    api.deleteItem(id);
  }, []); // Stable: no dependencies

  // useMemo: Expensive derived data
  const filtered = useMemo(() => {
    return allItems.filter(i => i.userId === userId)
      .sort((a, b) => b.date - a.date);
  }, [allItems, userId]);

  return <ExpensiveList items={filtered} onDelete={handleDelete} />;
}
The Downside — Memory & GC Pressure

Every useMemo / useCallback allocates memory to cache the value and its dependency array. On components that render thousands of times (like virtualized list items), this accumulated allocation can increase GC pauses. React's upcoming Compiler (React Forget) aims to automate memoization decisions, making manual memoization largely unnecessary.

Q12 Error Boundaries — Catching render errors and React 19 changes Intermediate P1
Short Answer

Error Boundaries are React components that catch JavaScript errors in their child component tree during rendering, lifecycle methods, and constructors. They use componentDidCatch(error, info) for logging and static getDerivedStateFromError(error) to render a fallback UI. React 19 introduces a functional alternative where you can use <ErrorBoundary fallback={<UI />}> without needing a class component.

Easy Explanation

Error boundaries are like circuit breakers in your house. If one room has an electrical fault, the breaker trips for just that circuit — the rest of the house stays powered. Similarly, if one widget crashes, an error boundary catches it and shows a fallback UI, keeping the rest of the page functional instead of a white screen of death.

What Error Boundaries Do NOT Catch

Error boundaries don't catch: event handler errors (use try/catch), async code errors (use .catch() or try/catch inside the effect), errors in the error boundary itself, or server-side rendering errors. They only catch errors during React's render phase and lifecycle methods.

Code Example
Class Error Boundary (All React Versions)
class ErrorBoundary extends React.Component<Props, State> {
  state: State = { hasError: false, error: null };

  static getDerivedStateFromError(error: Error): State {
    return { hasError: true, error };
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    logErrorToService(error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? <h1>Something went wrong.</h1>;
    }
    return this.props.children;
  }
}

// Usage: wrap risky UI sections
<ErrorBoundary fallback={<ErrorUI />}>
  <Dashboard />
</ErrorBoundary>
Error Boundary Placement Strategy

Don't wrap your entire app in one boundary — a single product card crash shouldn't take down the navbar. Place boundaries at key isolation points: around each route, around each major widget, and at the top level as a last-resort catch. This is called the "error boundary wall" pattern.

Q14 Conditional Rendering — Patterns, pitfalls, and best practices Beginner P1
Short Answer

React conditionally renders UI using standard JavaScript: && for simple conditions, ternary ? : for if/else, and if-statements for complex logic extracted before the return. Key pitfall: count && <Component /> renders 0 when count is zero — because 0 is falsy but React renders it as text. Always use count > 0 && or !!count && for number conditions.

Easy Explanation

React doesn't have special template conditionals like v-if or ng-if. You use plain JavaScript: if you want to show something only under certain conditions, you write that logic with &&, ? :, or a good old if statement. The magic is that React knows to skip rendering null, undefined, true, and false — so your conditionals naturally produce nothing when conditions aren't met.

The 0 Gotcha — Most Common Bug

React renders false, null, and undefined as nothing, but it does render 0 as text. So {items.length && <List />} will render the number "0" when the array is empty. Always convert to boolean: {items.length > 0 && <List />} or {!!items.length && <List />}.

Code Example

// 3. If/else extracted (best for complex logic)

  if (status === 'loading') return <Spinner />;
  if (status === 'error')   return <ErrorView />;
  if (status === 'empty')  return <EmptyState />;
  return <DataView />;
}

  error:   <ErrorView />,
  empty:  <EmptyState />,
  success: <DataView />,
} as const;

Q15 Rules of Hooks — Why order matters in React's Fiber architecture Intermediate P1
Short Answer

Hooks must be called in the exact same order on every render. React relies on call order (not names) to associate hook calls with their internal state. Internally, React uses a linked list in the Fiber node — each hook call advances a cursor. If a hook is skipped or called conditionally, the cursor desynchronizes, and state from useState A gets applied to useState B. The eslint-plugin-react-hooks enforces this at compile time.

Easy Explanation

Imagine you have numbered lockers and you always open them in the same order: locker 1 = name, locker 2 = age, locker 3 = email. If one day you skip locker 2, now locker 2 thinks it's age but actually contains email data. React's hooks work the same way — they use position, not label, to find their stored data. You must call hooks in the same order every time.

The Fiber Linked List Implementation

Each Fiber node has a linked list of hooks. When you call useState(initial), React checks: is this the first render? If yes, create a new hook node in the list. If no, advance the cursor to the next existing node and return its memorized state. This is why hooks can't be conditional — React has no way to map "this hook call" to "that stored state" other than position.

Code Example
Correct vs Broken Hook Usage
// BROKEN: Hook called conditionally — order changes!
function BrokenComponent({ isAdmin }) {
  if (isAdmin) {
    const [adminData] = useState(null); // Hook #2 (sometimes)
  }
  const [name] = useState('');                 // Hook #1 or #2 — unpredictable!
}

// FIXED: Always call hooks, conditionally use the value
function FixedComponent({ isAdmin }) {
  const [name] = useState('');        // Always hook #1
  const [adminData] = useState(null); // Always hook #2

  if (isAdmin) return <AdminView data={adminData} />;
  return <UserView name={name} />;
}
The Two Rules

1. Only call hooks at the top level — not inside loops, conditions, or nested functions.
2. Only call hooks from React functions — functional components or custom hooks, not regular JavaScript functions.

  • Can you call hooks inside useMemo or useCallback?
Memory Trick: "Hooks are a phone chain, not caller ID. React knows which hook you're calling by your position in line, not by your name." — Never break the chain with conditions or loops.
Summary
  • Hook call order must be identical on every render
  • React stores hook state in a linked list on the Fiber node, indexed by call order
  • Conditional hooks break the cursor alignment → wrong state for wrong hook
  • eslint-plugin-react-hooks catches violations at lint time
  • React 19's use() hook breaks this rule intentionally — it can be called conditionally

Q21 React Portals — Rendering outside the parent DOM hierarchy Intermediate P2
Short Answer

Portals let you render a React child into a different DOM node outside the parent component's DOM hierarchy — while preserving the React component tree context (props, state, events bubble through the React tree, not the DOM tree). Created via createPortal(children, domNode). Essential for modals, tooltips, dropdowns, and toast notifications where CSS stacking context or overflow clipping would otherwise break the UI.

Easy Explanation

Normally, React renders a component's children inside its own DOM element. But sometimes you need a child to break out of its parent's CSS jail — like a dropdown menu that gets clipped by the parent's overflow: hidden, or a modal that must overlay everything. Portals are your escape hatch: the component logic stays where it belongs (in the React tree), but the actual DOM output lands wherever you say (typically document.body or a dedicated <div id="portal-root">).

Real-World Example

A date picker component rendered inside a overflow: hidden sidebar panel. Without portals, the calendar popover gets cut off by the sidebar's boundaries. With a portal rendering the popover to document.body, the calendar flows freely over the entire viewport, but all event handling, state, and lifecycle remain controlled by the date picker component. Same pattern applies to modal dialogs, dropdown menus, and tooltips in overflow-constrained containers.

Common Mistake

Assuming portals break event bubbling. Events bubble through the React component tree, not the DOM tree. A click on a portal-rendered modal will still bubble up to the parent React component that rendered the portal, making it possible to catch events inside the parent's handler even though the DOM node lives elsewhere. This is a feature, not a bug — but it surprises many developers.

Senior Insight

Accessibility is the hidden complexity of portals. A portal-rendered modal must: (1) trap focus within the modal while open, (2) close on Escape key, (3) restore focus to the trigger element when closed, (4) have an accessible name via aria-labelledby. The <dialog> element and React 19's upcoming <Dialog> component aim to solve these natively. Until then, libraries like @radix-ui/react-dialog handle all of this correctly.

Code Example
React — Modal with createPortal
import { createPortal } from 'react-dom';

  if (!open) return null;

  const portalRoot = document.getElementById('portal-root');
  if (!portalRoot) return null;

  return createPortal(
    <div className="modal-backdrop" onClick={onClose}>
      <div className="modal-content" onClick={e => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    portalRoot
  );
}

function App() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button onClick={() => setOpen(true)}>Open Modal</button>
      <Modal open={open} onClose={() => setOpen(false)}>
        <h2>Hello from a Portal!</h2>
      </Modal>
    </>
  );
}

Q22 React Router — Client-side routing in SPAs Intermediate P2
Short Answer

React Router is the standard declarative routing library for React SPAs. It maps URL paths to React components using a nested route tree. v6+ uses <BrowserRouter>, <Routes>, <Route>, <Link>, and hooks like useParams, useNavigate, and useLocation. The core mechanism: intercept URL changes via the History API, match the URL against the route tree, and render the matching component tree without a full page reload.

Easy Explanation

In a traditional multi-page app, clicking a link triggers a full page load — the browser requests HTML from the server, the page refreshes, and you lose all client-side state. React Router prevents this. It intercepts link clicks, updates the URL in the address bar using the History API, and renders the corresponding React component instead of fetching a new page. The app never reloads — it feels instant, and all state (Redux store, form inputs, scroll position) is preserved.

Real-World Example

E-commerce app: /products → ProductList, /products/123 → ProductDetail, /cart → Cart, /checkout → Checkout flow (nested routes: /checkout/shipping, /checkout/payment, /checkout/confirmation). A protected layout route wraps authenticated pages: <Route element={<ProtectedLayout />}>...</Route> with an auth check that redirects to /login via <Navigate /> if not authenticated.

Common Mistake

Using <a href> instead of <Link> inside the app causes full page reloads — destroying React state and negating the SPA benefit. Always use <Link to> for internal navigation. Another mistake: not configuring the server to serve index.html for all routes — without it, direct URL access or refresh on /products/123 returns a 404. This requires a catch-all server rule.

Senior Insight

React Router v6 introduced nested routes with <Outlet />, enabling persistent layouts without re-mounting the parent. Loaders and actions (data-router APIs) shift data fetching to the router level — they fetch data before the component renders, eliminating the "loading spinner waterfall" problem. For complex apps, use createBrowserRouter with loaders/actions instead of the declarative <BrowserRouter> — it enables proper error handling via <ErrorBoundary> per route and data revalidation on mutations.

Q23 What causes a React component to re-render? How do you prevent unnecessary re-renders? Intermediate P1
Short Answer

A React component re-renders when: (1) its state changes (useState/useReducer setter called), (2) its parent re-renders (React re-renders all children by default), (3) its context value changes (all consumers re-render), or (4) forceUpdate is called. Preventing unnecessary re-renders: React.memo (prevents re-render when props haven't changed), useMemo/useCallback (stable references for child props), lifting state down (keep state close to where it's needed), and moving expensive subtrees to separate components so they don't re-render with the parent.

Easy Explanation

Imagine a restaurant kitchen — every time a waiter puts a new order on the board (state change), every chef (component) in the kitchen starts cooking. Most chefs didn't need to — the order was for the salad station (only that component really needs to work). React.memo is like putting a "don't bother me unless my ingredients change" sign on a chef's station. Without it, React is generous — it tells everyone to cook, just to be safe.

Real-World Example

A product listing page with 50 filter checkboxes. Without optimization, clicking any filter re-renders every filter chip AND every product card AND the pagination component. With React.memo on product cards + useCallback on the filter toggle handler + state lifted into a useReducer that only updates the filter state (not the entire app state), clicking a checkbox only re-renders the affected filters — not all 50 products. This turned a 120ms render into 8ms.

Common Mistake

Putting React.memo everywhere thinking it always helps. Memoization has cost — prop comparison itself takes time. For simple components with cheap renders, React.memo often slows things down. The rule: measure first, memoize second. Also: defining inline objects/arrays as props (<Child config={{ a: 1 }} />) breaks React.memo — they're new references every render. Always stable-ize reference-typed props with useMemo if the child is memoized.

Senior Insight — Re-render Debugging Workflow

When debugging unnecessary re-renders: (1) Install why-did-you-render or use React DevTools "Highlight updates when components render." (2) Check if the parent re-rendered — if the parent re-renders, children re-render unless memoized. (3) Check if props changed — inline functions/objects create new references every render. (4) Check if context value changed — context updates re-render ALL consumers, not just the one that reads the changed value. Split context into multiple providers for independent concerns. This question appears in nearly every interview — Deloitte, EY, Swiggy, MakeMyTrip, Primathon, Amazon (2025-2026).

Q24 Authentication Flow in React — How do you implement login, token management, and protected routes? Advanced P2
Short Answer

Standard auth flow: (1) User logs in via a form → API validates credentials → server returns a JWT token. (2) Store the token — httpOnly cookie (more secure, prevents XSS) or localStorage (simpler but XSS-vulnerable). (3) On every API request, send token via Authorization: Bearer <token> header. (4) On page load, check token validity (decode + expiry check) and redirect to login if expired. (5) Protect routes with a wrapper component that checks auth state and redirects. Most production apps use AuthContext to provide user, login, logout to the entire tree, plus axios interceptors to auto-attach tokens and handle 401 responses (redirect to login on expiry).

Easy Explanation

Think of a JWT token like a VIP wristband at a festival. You show your ID at the entrance (login form) and get a wristband (JWT). As long as the band is on your wrist (not expired), you can enter any area without showing ID again. When the band expires or you leave (logout/token expiry), you go back to the entrance. The "protected route" wrapper is like a bouncer at each entrance — checks for the wristband and redirects you to the ticket booth if you don't have one.

Real-World Example

E-commerce dashboard: User navigates to /admin/orders. The ProtectedRoute component checks AuthContext — no user found → redirect to /login?redirect=/admin/orders. User logs in via email/password → API returns { token, user } → stored in AuthContext + persisted to localStorage → redirect back to /admin/orders. Every API call to /api/orders includes the token via an axios interceptor. If the token expired (401 response), the interceptor logs the user out and redirects to login. Auth flow is one of the most commonly asked React implementation questions — Deloitte 2026 explicitly asked for complete auth flow from login to token storage to security.

Senior Insight — httpOnly Cookie vs localStorage

localStorage + Authorization header: Easier to implement but vulnerable to XSS — an attacker's script can read localStorage.getItem('token') and steal the session. httpOnly cookie: The browser automatically sends it with requests — JavaScript cannot read it, making it immune to XSS. However, you need CSRF protection (SameSite=Strict + CSRF token). For most production apps, use httpOnly cookies with refresh tokens: short-lived access token (15 min) in memory, long-lived refresh token (7 days) in httpOnly cookie. On page refresh, the refresh token is sent to /auth/refresh to get a new access token. This balances security (short-lived in-memory tokens) with UX (no frequent logins). Also: always use PKCE flow for OAuth2, never store secrets in client code.

Code Example
React — Complete Auth Context + Protected Route
import { createContext, useContext, useState, useEffect } from 'react';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // On mount: check if token exists and is valid
    const token = localStorage.getItem('token');
    if (token) {
      fetch('/api/auth/me', { headers: { 'Authorization': `Bearer ${token}` } })
        .then(res => res.ok() ? res.json() : null)
        .then(setUser)
        .finally(() => setLoading(false));
    } else {
      setLoading(false);
    }
  }, []);

  const login = async (email, password) => {
    const res = await fetch('/api/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, password }),
    });
    const data = await res.json();
    localStorage.setItem('token', data.token);
    setUser(data.user);
  };

  const logout = () => {
    localStorage.removeItem('token');
    setUser(null);
  };

  return <AuthContext.Provider value={{ user, login, logout, loading }}>{children}</AuthContext.Provider>;
}

export function ProtectedRoute({ children }) {
  const { user, loading } = useAuth();
  if (loading) return <Spinner />;
  if (!user) return <Navigate to="/login" replace />;
  return children;
}
Memory Trick: "Auth = Login → Token → Storage → Headers → Protect. JWT = wristband. httpOnly cookie = safer. ProtectedRoute = bouncer. AuthContext = single source of auth truth."
Q25 When is useEffect the wrong tool? — Derived state, event handlers, and the mental model for side effects Intermediate P1
Short Answer

useEffect is the wrong tool whenever: (1) the value can be derived during render (computed from existing state/props — just compute it directly), (2) the work belongs in an event handler (button click should update state + make API call directly, not trigger an effect), (3) you're synchronizing state with state (state → effect → setState = unnecessary re-render cascade), or (4) the logic is about user interaction (form submission, navigation, toggling). useEffect synchronizes React with external systems (browser APIs, WebSocket, document.title, analytics, subscriptions). If there's no external system involved, you probably don't need an effect. React docs explicitly say: "useEffect is a last resort." This question separates senior from junior engineers in 2026 interviews.

Easy Explanation

Think of useEffect like a fire alarm — it's designed for emergencies (talking to the outside world: APIs, localStorage, analytics). But many developers use it like a light switch — flipping state based on other state. That causes a cascade: state changes → render → effect runs → sets more state → another render → another effect. Instead, compute derived values during render directly. If a user clicks a button, handle it in the onClick handler, not in an effect watching a "submitted" state.

Real-World Example

❌ Bad: A component that filters a product list: useEffect(() => { setFilteredProducts(products.filter(p => p.category === category)); }, [products, category]); — this causes an extra render (effect runs after paint, sets state, re-renders). ✅ Good: const filteredProducts = useMemo(() => products.filter(p => p.category === category), [products, category]); — computed during render, no extra cycle. ❌ Bad: Form submit in useEffect watching a "submitting" state. ✅ Good: Call handleSubmit directly in the button's onClick. Scrimba 2026 guide explicitly calls this out: "When is useEffect the wrong tool? Whenever the value can be derived during render, or the work belongs in an event handler."

The Most Common useEffect Misuse

The pattern useEffect(() => { fetchData().then(setData); }, []); on mount is the most common misuse — it should be in a library like React Query or a custom hook with proper loading/error states. useEffect is not a data-fetching tool. It's a synchronization tool. Data fetching is a side effect that belongs in: (a) a framework like React Query (with caching, deduplication, refetching), (b) a custom hook that encapsulates the fetching lifecycle, or (c) Server Components (Next.js) where data is fetched before rendering and never causes client waterfalls.

Senior Insight — The Two Rules for useEffect

Rule 1: If you can compute it during render, do it during render. Derived state, filtered lists, formatted dates — compute directly. Use useMemo only if the computation is expensive. Rule 2: If it responds to a user action, put it in the event handler. Form submission, navigation, toggling — do it onClick/onSubmit, not in useEffect. Effects are for synchronizing with systems outside React: browser APIs (document.title, navigator), third-party widgets (maps, charts), subscriptions (WebSocket, event listeners), and analytics. Following these two rules eliminates 80% of effect bugs. React 19's useOptimistic and useFormStatus further reduce the need for useEffect in form/action scenarios.

Code Example
React — useEffect: Correct vs Wrong Usage
// ❌ WRONG: Derived state in useEffect — causes extra render
function ProductList({ products, category }) {
  const [filtered, setFiltered] = useState([]);
  useEffect(() => {
    setFiltered(products.filter(p => p.category === category));
  }, [products, category]);
  return <div>{filtered.map(p => <p>{p.name}</p>)}</div>;
}

// ✅ CORRECT: Derive during render — no extra render cycle
function ProductList({ products, category }) {
  const filtered = products.filter(p => p.category === category);
  return <div>{filtered.map(p => <p>{p.name}</p>)}</div>;
}

// ❌ WRONG: Event logic in useEffect
function SubmitForm() {
  const [submitted, setSubmitted] = useState(false);
  useEffect(() => {
    if (submitted) api.submit(data).then(...);
  }, [submitted]);
  return <button onClick={() => setSubmitted(true)}>Submit</button>;
}

// ✅ CORRECT: Event logic in the event handler
function SubmitForm() {
  const handleSubmit = () => { api.submit(data).then(...); };
  return <button onClick={handleSubmit}>Submit</button>;
}

// ✅ CORRECT: useEffect for external system sync
useEffect(() => {
  const ws = new WebSocket(url);
  return () => ws.close();  // Cleanup — disconnects WebSocket on unmount
}, [url]);
Memory Trick: "useEffect = external systems only. Not derived state (compute during render). Not event handlers (put it onClick). Not state-to-state sync (unnecessary cascade). If it's not synchronizing with something outside React, it doesn't belong in useEffect."
Q26 What are Pure Components? — Shallow-compare rendering with React.PureComponent and React.memo Intermediate P2
Short Answer

A Pure Component skips re-rendering when its props and state haven't changed, using a shallow comparison. For class components, extend React.PureComponent instead of React.Component. For function components, wrap with React.memo. Both perform a shallow compare of props (and state, for PureComponent) — if every top-level value is Object.is-equal, React bails out of rendering.

Easy Explanation

Imagine a chef who only re-cooks a dish when the order ticket actually changes. A regular component re-cooks on every ticket print — even if the order is identical. A Pure Component glances at the new ticket, compares it line by line with the last one, and only fires up the stove when something differs.

Real-World Example

A static sidebar with navigation links inside a dashboard that re-renders every second from a live clock. Without purity, all 30 nav links re-render 60 times a minute for nothing. Extending PureComponent (or wrapping with memo) means the sidebar renders once and stays quiet — only the clock ticks.

Common Mistake

Passing inline objects, arrays, or arrow functions as props to a Pure Component (<PureChild config={{ a: 1 }} onClick={() => ...} />). New references are created every parent render, so the shallow compare always fails and the "optimization" does nothing — worse, it adds comparison overhead. Stabilize reference-typed props with useMemo/useCallback, or the purity is defeated.

Senior Insight

Shallow compare is the whole contract — and its biggest footgun. Mutating state in place (this.state.items.push(x)) keeps the same array reference, so a PureComponent will not re-render and your UI goes stale. Purity forces immutable updates, which is exactly why it pairs with Redux-style state management. Also note: PureComponent only exists for classes; in function components memo is the equivalent (props only — there is no component state to compare, since hooks own that).

Code Example
React — PureComponent (class) and memo (function)
import { Component, memo } from 'react';

// Class: shallow-compares props AND state automatically
class NavSidebar extends React.PureComponent {
  render() {
    return <nav>{this.props.links.map(l => <a key={l.id} href={l.href}>{l.label}</a>)}</nav>;
  }
}

// Function: shallow-compares props only
const NavSidebarFn = memo(({ links }) => {
  return <nav>{links.map(l => <a key={l.id} href={l.href}>{l.label}</a>)}</nav>;
});
Memory Trick: "Pure = compare ticket before cooking. PureComponent for classes (props + state), memo for functions (props only). Never mutate — mutation blinds the comparison."
